# 付属ファイルの書式規約

スキルの `SKILL.md` に添える付属ファイル（`references/`・`examples/`・`sample/` など）の書式を定める。
付属ファイルは SKILL.md から必要なときだけ開かれる。読む側が迷わず目的の箇所に着けることを優先する。

## 適用範囲

| 対象 | 適用 |
|------|------|
| `skills/<name>/` の付属ファイル | 適用する |
| `.claude/skills/<name>/` の付属ファイル（リポジトリ管理スキル） | 適用する |
| `.agents/skills/` の vendored スキル | 対象外（上流の規約に従う。`samples/` などの表記を本規約に揃えない） |

既存ファイルの改名は本規約の導入だけを理由にしない。`skills/init-claude-specialist/tests/structure.test.mjs` が
`sample/` 配下をパスで読むため、特に `sample/` は改名しない。

## ディレクトリの役割

| ディレクトリ | 置くもの |
|-------------|---------|
| `references/` | 根拠・参照資料（出典台帳、背景知識、要点と詳細） |
| `examples/` | スペシャリスト skill の制作例。1 依頼 1 ファイル |
| `sample/` | 手順型スキルや scaffold の雛形。`{{ }}` 置換型、または複製して書き換える見本 |
| `scripts/`・`tests/` | 実行物と、その検査 |

役割の違うものを混ぜない。根拠を `examples/` に、雛形を `references/` に置かない。

## ファイルの冒頭

Markdown の付属ファイルは、H1 の題名と、用途を 1 段落で書いた概要から始める。概要には「何のためのファイルか」と
「いつ開くか」を書く。

### examples/

H2 の並びを次のとおり固定し、最後を出典の節で締める。

| 順 | 見出し | 内容 |
|----|--------|------|
| 1 | `## 依頼` | 架空の製品・依頼文・想定ユーザー |
| 2 | `## 目的の一文` | 作るものの目的を 1 文で |
| 3 | `## 削るもの` | 入れない要素・理由・削り方（表） |
| 4 | `## 構成` | 全体の組み立て |
| 5 | `## 仕様` | 値・規則（出典ありと本 skill の目安を分ける） |
| 6 | `## 文言` | 実際に使う文面 |
| 7 | `## コード断片` | 実装の最小例 |
| 8 | `## 初見検証` | 何に注意するか・何を操作できるか・どう操作するかを、初見の人に確かめる表 |
| 9 | `## 点検` | 完了前の確認項目 |
| 10 | `## この例の出典` | 使った出典の番号と台帳へのリンク |

- 既存の例のとおり、H2 の並びは変えない。節の中での `###` の追加（「根拠の範囲（先に読む）」など）は可
- 題材は架空にする。実在の製品・企業を模倣しない

### sample/

用途と置換規則を先に書いてから本文（雛形）を示す。

- 置換型は、概要で「どの手順が使うか」「どこへ配置するか」「`{{ }}` を何で置き換えるか」を書く
- ファイル自体が雛形で、冒頭に H1 と概要を置けないもの（frontmatter 始まりの `SKILL.sample.md`・`agent.sample.md`）は、
  冒頭の YAML コメントで用途と注意を書く（例外）

## 相互リンク

- SKILL.md に索引（表）を置き、すべての付属ファイルへそこから届くようにする。付属ファイルが少数なら、本文での列挙でもよい
- 付属ファイルどうしは相対パスで結ぶ（例: `../references/sources.md`）
- 要点と詳細に分けた場合は、要点から詳細へリンクする。詳細から要点へ戻すリンクは任意とする
- 索引に載っていない付属ファイルを作らない。追加・削除時は索引も更新する

## 出典台帳

出典を持つスキルは、台帳をスキル 1 件につき 1 つ置く（既定は `references/sources.md`）。

- 番号（S01 など）は振り直さない。欠番は欠番のままにする
- 1 件は `### S01 発言者や媒体` の見出しと、固定の項目で書く。項目名と並びは台帳の中で揃える
  - 必須: 引用原文（引用ブロック）、`媒体・日付`、`URL`、`取得日`、`検証区分`
  - 書くことがあるときだけ: `備考`
  - 運用上の追加項目（`本体掲載`・`使用箇所` など）は任意とする
- 本文からは番号で参照する（例: S01）。本文に引用を載せる場合も番号を添える
- 台帳は通読せず、番号で検索して該当の項目だけ読む前提で書く。冒頭に凡例（検証区分の意味）を置き、末尾に未検証・調査の限界の節を置いてよい
- 配布されない調査メモの内部 ID（作業用の通し番号など）を台帳・本文に残さない。台帳の番号だけを根拠の参照に使う

## 長さ

1 回の読み取りで読み切れる長さを目安とする。目安は 2,000 行以下、日本語中心なら 2 万字程度まで（トークン換算は目安）。

超える場合は、次のどちらかで対処する。

1. 要点と詳細に分ける。要点を先に読ませ、詳細は必要な節だけ開く（例: `design-history.md` と `design-history-eras.md`）
2. 冒頭に節の索引を置き、見出しを固定して、必要な節だけ読める形にする

台帳のように、番号で検索して使うファイルは長さの例外とする。

## スペシャリスト skill の付属ファイル

スペシャリスト skill の付属ファイルにも、`./tool-neutral-skills.md`（ツール固有名・置換変数を書かない）と
`./specialist-authoring.md` の誠実性の原則が適用される。
