# デザイン史: 端末の業務画面から、表計算・ERP・Web の自動生成・管理テンプレート・デザインシステムを経て、現在へ

管理画面・業務画面（表・一覧・詳細・入力・ダッシュボード）の見た目と作り方が、どんな制約のもとで、どう変わってきたかをまとめたファイル。年表の暗記用ではなく、「いま採ろうとしている慣習や既定の見た目は、どんな制約から生まれたか」を確かめるための材料である。要点（見取り図・繰り返すパターン・媒体別の問い）と、時代別の詳細を 1 ファイルに置いた。中心の問いは次の 1 つ。

> その慣習を生んだ制約は、今回の画面・利用者でも成り立つか。

成り立つなら、慣習は今も根拠を持つ。成り立たないなら、見た目だけが残っている可能性がある。出典が薄い時代は、薄いと書く。

このファイルを開くのは、相談者が背景を求めたとき、制作の着手前（「媒体別の使い方」の節）、慣習や既定の由来が不明のとき、の 3 つである。

| 知りたいこと | 開く場所 |
|---|---|
| 全体像・横断の型 | 「見取り図」「繰り返すパターン」 |
| 画面の種類ごとに確かめる問い | 「媒体別の使い方」 |
| 端末・表計算・金融端末の高密度・ERP・Web の自動生成・管理テンプレート・デザインシステムとダッシュボード・現在の由来 | 「時代別の詳細」の 1〜8 |
| 年が出典どうしで合わない項目 | 「年が食い違う・注意する出典」 |
| 空白・未検証 | 「確認できなかったもの」 |

## 読み方と記法

- 時点: 記述は出典ごとの取得日の時点（`sources.md` の各項目を見る）。ライブラリの既定値は別ファイル `library-defaults.md` に置いた
- 各時代の 4 項目: 当時の制約 / 応答 / 副作用と反動 / 今の判断への示唆。4 項目めの「示唆」はすべて「本 skill の整理（推測）」で、出典が述べた因果ではない。因果（「A だから B になった」）は、出典が述べている場合だけ S 番号つきで書く。「当時の制約」を出典が述べていない時代は、「整理（推測）」または「出典なし」と書く
- 区分は `sources.md` の凡例に従う（A 原典、B 第三者の転載、C 論評・批判、R 記者・機関・運営者の地の文、U 未検証）。B・C・R は区分を明記して要旨にし、英語の逐語で本人の発言としては示さない。R を研究結果の根拠にはしない
- 年・日付: S 番号を添えた論旨上の年は、その引用ブロックに含まれるものに限る。記事の公開日は「〜年の記事」と書き、媒体・日付の項による。Wikipedia（区分 R）は年と事実の確認だけに使い、設計の意図や理由の根拠にしない
- 英語の逐語は区分 A の出典だけで、1〜2 文に限る。日本語は要旨で、本人の発言ではない
- 回答での使い方: 頼まれない限り、歴史を講釈しない。判断の根拠として 1 行で使う

## 回答での使い方（例）

- 相談「DB の表をそのまま一覧にした管理画面を、作業向けに直したい」: モデルから管理画面を自動で作る仕組みの公式文書自身が、作業を中心にした画面にしたいなら、自前の画面を書くよう述べる（S172、S173）。自動生成は出発点にとどめる。
- 相談「全部載せたダッシュボードを作りたい」: ダッシュボードとポータルの混同を指摘した 2004 年の記事（S169）、必要な情報が早く明確に届かない画面は飾っても使われないという 2006 年の白書（S168）がある。判断に使う指標だけを集めよ、という 2009 年の記事もある（S170）。
- 相談「熟練者向けに詰め込んだ高密度の画面にしたい」: 高密度の代表例として語られる金融端末の運営側は、急な画面の変更が利用者の仕事を乱しうると、2017 年の記事で述べる（S190）。密度の上限は利用者で変わる、という 2024 年の記事もある（S150）。
- 相談「表計算みたいな画面にしたい」: Lotus 1-2-3 は 1980 年代を通じて標準の表計算だった（S178。R）。それが業務画面の型になったかは本 skill の整理（推測）で、出典は述べていない。慣れた操作を引き継ぐ価値と、画面の目的に合うかは別の問いである。

## 繰り返すパターン（本 skill の整理）

次の型は、出典を横断して読み取ったもので、出典が述べた法則ではない。例外は多い。

1. 部品が増えると、取捨選択が置き去りになる: 部品として表や一覧が整うほど、「何を列に出すか」は部品が決めなくなる。公式文書が、自動生成と作業を中心にした画面を分ける（S172、S173）。
2. 慣れた型は、次の画面の期待になる: 表計算の行と列が広く使われ（S178。Lotus 1-2-3 は 1980 年代を通じて標準の表計算。R）、業務画面の期待になったと読めるのは本 skill の整理（推測）である。表が比較を助ける点は NN/g も述べる（S041、S044）。出典は、この因果を述べていない。
3. 高密度は、利用者と頻度で成り立つ: 金融端末の運営側は、情報が多いことを狙いと述べる（S189）。一方、密度の上限は利用者で変わるとも言われる（S150）。
4. 見た目の古さと、設計の合理性は別の問い: 外部の論評は古さを推測で語る（S156。C）。運営側の記事は、変更の速さに注意を向ける（S190、S191）。
5. 余白と密度は周期で揺れる: ソフトウェアが疎になっているという観察（S147）と、密度を上げる立場（S151。C、S152）が並ぶ。
6. 指標と画面は、飾りより判断で選ぶ: 飾りの量計より、必要な情報が早く明確に届くこと（S168）。判断に使う指標だけを集める（S170）。
7. 近道は追加の入口である: 近道は、熟練者が使い、ほかの人が無視できる別の入口（S143）。

## 媒体別の使い方

制作の着手前に、画面の種類ごとに次の問いを確かめる。

| 画面の種類 | 確かめる問い | 開く時代 |
|---|---|---|
| 一覧・表 | 比較・並べ替え・操作のどれが主か。表計算の慣れを引き継ぐ価値があるか。DB の列を並べただけになっていないか | 2・5・7 |
| 大量入力 | 固定の順序とキー操作で速くしたい作業か。熟練者の入力速度を要件に入れたか | 1・4 |
| 高密度の画面 | 利用者は毎日使い、習熟するか。変更は熟練者の仕事を止めないか | 3・8 |
| 詳細・編集 | 役割と作業を中心に切ったか。モデルの項目の並びを見せていないか | 4・5 |
| ダッシュボード | 単一の作業に答えるか。判断に使う指標だけか | 7 |
| 部品・テンプレートの導入 | 一貫性を目的にしているか。作業に合う列と詳細は設計し直したか | 6・7 |
| 近道・検索型の入口 | 通常の操作を残したか。近道が唯一の入口になっていないか | 8 |

## 時代別の詳細

### 1. 端末の業務画面（1970 年代〜）

- 当時の制約: IBM の 3270 は、遠隔の大型計算機に、1970 年代前半の技術でつなぐ前提で設計された（S179。R）。1971 年に IBM が出した（S192。R）。1 キーごとに計算機を割り込ませない設計で、1970 年代の大型機 1 台が 1 万 7,500 台までの端末を支えた例が挙がる（S180。R。Wikipedia の記述で、IBM の一次資料とは未照合）
- 応答: 整理（推測）: 画面を項目（フィールド）に区切り、まとめて送る固定書式だったと考えられる。入力の順序・必須項目・型が画面の定義に埋め込まれ、利用者は決まった順にキーで進む
- 副作用と反動: 整理（推測）: 固定書式は速いが、書式の外にある作業に弱い。画面の設計意図を書いた当時の設計者の発言は取れていない
- 今の判断への示唆（本 skill の整理）: 「大量の入力を決まった順で速く」には、固定の順序・キーボードで完結・自動送りが今も有効である。ただし本ファイルの出典は制約（S180）までで、設計意図ではない。国内の会計事務所向けの記帳画面では、テンキーだけで業務を完結できることが要求だった（S140。N=1 の事例）

### 2. 表計算の普及（1978〜1985 年）

- 当時の制約: 電卓と紙の集計表が業務の道具だった。Bricklin は、電子表計算の発想を 1978 年春に得たと述べる（S176）
- 応答: VisiCalc は 1979 年半ばに 100 ドル未満で売り出された（S177。R）。Lotus 1-2-3 は 1980 年代を通じて標準だった（S178。R）。Excel は 1985 年 9 月 30 日に発売された（S193。R）
- 副作用と反動: 整理（推測）: 行と列に数字が並び、セルを直接編集する画面が、業務の一覧・集計の既定の期待になったと読める。NN/g が、表は比較を助け、4 つの作業を支えるべきと述べる（S041、S044）背景に、この慣れがあるかもしれない。出典は、この因果を述べていない
- 今の判断への示唆（本 skill の整理）: 業務の利用者は、並べ替え・絞り込み・列の固定・コピーを前提に持つことが多い。表で足りる画面をカードにするなら、比較のしにくさを払う（S044）。取り込みの確認画面に表計算風の表示を使う国内の部品もある（S271。要旨・逐語引用なし）

### 3. 金融端末の高密度（1982 年〜）

- 当時の制約: Bloomberg Terminal は 1982 年 12 月に市場へ出た（S181。R）。1 画面に複数のデータ流を並べ、複数のモニターで使われる、と語られる（S150 は、4 台のモニターの机の債券トレーダーを、密度の閾値が高い例に挙げる。端末の画面構成の一次資料は未取得）
- 応答: 運営側の UX ブログは、情報過多こそが狙いと述べる（S189。2017 年の記事）。外部の記事は、一貫性を徹底しないと、画面に愛着を持つ利用者を満足させられない、という経営者の言葉を再引用する（S032。B。2013 年の記事。誌の一次は未照合）
- 副作用と反動: 外部の論評は、熟練を誇れる画面だから受け入れられていると推測する（S033。B、S156。C。いずれも推測で、実証ではない）。一方、運営側は、急な画面の変更が熟練者の仕事を乱しうること（S190）、変化は遅すぎても速すぎても不信を生むこと（S191）を述べる
- 今の判断への示唆（本 skill の整理）: 高密度は、熟練者の頻繁な利用で成り立つ。見た目が古いことと、設計が合理的でないことは別の問いで、本ファイルは後者の一次証拠を持たない（運営側の他のページは自動取得が拒否された）。密度の上限は利用者で変わる（S150）

### 4. クライアントサーバーの業務アプリと ERP（1990 年代〜 2010 年代）

- 当時の制約: SAP R/3 は 1992 年 7 月に発売された（S182。R）
- 応答: 2013 年の記事は、SAP の製品は大企業の運営での役割で知られるが、使いやすさでは必ずしも知られていない、と書く（S183。R。記者の地の文で、SAP 側の主張ではない）。記事の題名は、SAP が使いやすさを打ち出した製品群を発表した件を扱う（媒体・日付の項。引用ブロックには無い）。SAP 自身の設計原則は未照合
- 副作用と反動: 整理（推測）: 巨大な業務システムを「機能の一覧」ではなく「役割と作業」で切り直す動きとして読める。ただし記事は記者の観察で、SAP 内部の理由ではない
- 今の判断への示唆（本 skill の整理）: 画面の単位を DB の表ではなく、役割と作業にする、という向きは、Django の公式文書の「process-centric」な画面（S173）と同じである。国内でも、役職ごとに業務の範囲が違い、組織ごとに業務フローの正解が違う、と述べる記事がある（S128）

### 5. Web の管理画面と自動生成（1998〜2005 年）

- 当時の制約: phpMyAdmin は、MySQL の PHP による Web の画面として、1998 年に作り始められた（S175）。Django は、新聞社の Web 部門（World Online）の、報道の締切に追われる実務の必要から育ち、2005 年夏にオープンソースになった（S174）
- 応答: モデル（DB の表）から管理画面を自動で作る。Django の公式文書は、admin の推奨される用途を、組織の内部の管理ツールに限り、全体の画面の土台にするものではないと述べる（S172）
- 副作用と反動: 公式文書自身が、DB の表と項目の実装の詳細を隠す、作業を中心にした画面が要るなら、自前の画面を書くべきだと述べる（S173）。整理（推測）: DB の列が並ぶだけの画面が量産された状況への、作り手側の自己点検として読める。出典は「量産」までは述べていない
- 今の判断への示唆（本 skill の整理）: 自動生成は出発点にとどめる。列の選び方・先頭列・既定の並び・詳細の入り方を、業務の作業に合わせて設計し直す（S042、S043、S047、S029）。国内の記事も、DB の値をそのまま出した結果、列が多すぎる「カオスな表」を挙げる（S296）。既定のままだと弱い点は `library-defaults.md` に整理した

### 6. Bootstrap 系の管理テンプレート（2010 年代）

- 当時の制約: Twitter の初期の社内ツールは、洗練された親しみやすいデザインを欠き、開発や改善を速く進めにくかった（S184）。始まりの年は、Otto が 2011 年初めと語る（S185）。ほかの資料には 2010 年中頃とするものがあり、食い違う（後述）
- 応答: 部品を一貫した視覚言語でまとめ、社内ツールで使い、共有のコードにして文書化した（S184。2012 年の記事）
- 副作用と反動: 整理（推測）: 公開された部品集の上に、管理画面のテンプレートが多数作られた。出典は「画一化」を述べていない。「テンプレートの画一的な見た目」への一次の批判は、確保できなかった（検索では売り手の資料が中心）。事実として扱わない
- 今の判断への示唆（本 skill の整理）: 一貫性は目的であって、作業に合った設計の代わりではない（S172、S173 と同じ向き）。国内の記事も、美しく設計された部品を使っても、使い方で画面の印象が大きく変わると述べる（S294）

### 7. デザインシステムの時代と、ダッシュボードの流行・反動（2004 年〜）

- 当時の制約: 製品が増え、画面の一貫性・速度・コストが問題になる。Ant Financial は、企業向け製品を多数抱えていた（S187）。一方、Few は 2004 年の記事で、ダッシュボードとポータルを同じものとみなす誤解が、双方の特性を奪うと述べる（S169）
- 応答: Material Design の初版は、2014 年 6 月 25 日に発表された（S186。R）。Ant Design は、企業向け製品に、4 つの価値（Natural・Certain・Meaningful・Growing）を置いた（S188）。Few は 2006 年の白書で、必要な情報を明確に早く届けない画面は、メーターや信号を飾っても使われないと述べる（S168）。NN/g は 2017 年の記事で、ダッシュボードを単一の作業に絞り（S057）、時間が重要な作業の運用型を挙げる（S058）。Carbon は、行の高さを 5 段で定める（S136）
- 副作用と反動: Ries は 2009 年の記事で、多くの分析パッケージの既定が、虚栄の指標の報告に偏ると指摘し（S171）、決定に使う指標だけを集めよと述べる（S170）。余白の取りすぎへの反動は、ソフトウェアが疎になっているという 2024 年の観察（S147）と、2026 年の批判（S151。C）に見える。Linear は 2024 年の刷新で、ナビゲーション要素の階層と密度を上げた（S152）
- 今の判断への示唆（本 skill の整理）: 部品として提供されると、表の既定の見た目（行の高さ・密度）が標準化される一方、「何を列に出すか」「何を削るか」は部品が決めない（出典はこの因果を述べていない）。何でも載せるダッシュボードは、目的の単一性（S057）と判断への使用（S170）で削る。密度は、利用者と頻度で決める（S150）。既定の密度の立場は出典どうしで割れる（S135。Polaris は S272 の要旨・逐語引用なし）

### 8. 現在（2020 年代: 近道・検索型の入口・AI）

- 当時の制約: 画面の数と機能が増え、ボタンに載らない。NN/g は、熟練者向けに近道を、追加の入口として置くことを勧める（S143。2024 年の記事）。複雑な業務のアプリは、非線形の作業・熟練者・重大な判断を支える（S145）。複雑さは設計の失敗ではなく、複雑化が失敗である（S249）。ただし、複雑なアプリの作り手が、最適でなくても旧来の手法に従う、という観察もある（S159）
- 応答: コマンドパレットは、ボタンやドロップダウンに値しない機能を足せて、近道を発見しやすくする、と Superhuman が述べる（S154、S155。2019 年の記事。自社の主張）。AI エージェント向けに公開された skill は、構造や指標に偏る例が取得できた（`library-defaults.md`）
- 副作用と反動: 整理（推測）: 近道の増加は発見性の問題を生む。NN/g は、すべての操作に近道が要るわけではないと述べる（S144）
- 今の判断への示唆（本 skill の整理）: 検索型の入口（パレット）と、画面上の通常の操作を両方持つ。キーボードで完結する作業を要件に入れる（S141）。AI が生成した画面の設計の根拠は、本ファイルでは空白である
