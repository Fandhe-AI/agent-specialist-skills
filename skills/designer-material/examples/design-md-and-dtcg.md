# 例: DESIGN.md と DTCG の JSON の対応（トークンと理由を 1 ファイルに持つ形式）

トークンと理由を 1 ファイルに持つ形式（DESIGN.md）と、DTCG の JSON の対応を並べ、値の持ち主と生成の向きを決める例。トークンは `design-tokens-minimal.md` と同じ架空の製品「ハリマ帳」のものを使う。「トークンの理由も残したい」「DESIGN.md を使いたい」「他社サイトから抽出した DESIGN.md を渡す案が出た」という相談を受けたときに開く。題材は架空で、実在の製品名・ロゴの模倣は含まない。

## 依頼

- 製品: 請求書発行 SaaS「ハリマ帳」（架空。`design-tokens-minimal.md` と同じ。名称が実在の製品と衝突しないかは確認していない）。トークンは、DTCG の JSON（同ファイル）が既にある
- 依頼文: 「トークンの理由を 1 ファイルに残したい。DESIGN.md という形式を使えるか。他社のサイトから抽出した DESIGN.md を渡して、その見た目に寄せる案も出ている」
- 使い手: 開発者 6 人・デザイナー 1 人（確認が取れないので置いた前提）
- 前提（置いた）: 形式は alpha で、変わりうる（S93）。DESIGN.md を扱う道具は、この例では実行していない

## 目的の一文

値の持ち主を JSON か DESIGN.md のどちらか 1 つに決めたうえで、DTCG の JSON と同じトークンを、理由と一緒に DESIGN.md の 1 ファイルで読める形にする。

## 削るもの

| 削るもの | 理由・削り方 |
|---|---|
| 実在のサイトから抽出した DESIGN.md を「この見た目で作って」と渡す使い方 | 勧めない。理由は「仕様」の末尾の 3 点 |
| typography・components などのグループと、ほかの節（名前は未照合） | 本例は色・角丸・余白の 3 グループと、3 つの節（Overview・Colors・Do's and Don'ts）だけ。ほかは必要になるまで書かない。文字は designer-typography が導入されていれば案内する |
| ダークの割り当てを DESIGN.md の中で持つこと | 切り替えを表す項目が、取得した範囲に無い。別ファイルに分ける案（本 skill の整理）にとどめる |
| 変換ツール・CI の運用 | 向きと対応だけを示す。変換の道具は実行しておらず、出力は未検証 |
| JSON と DESIGN.md の両方を手で保守すること | 値の持ち主を 1 つに決める（下の「構成」） |

## 構成

```text
system.tokens.json   DTCG の JSON。`design-tokens-minimal.md` と同じ 10 の役割・2 段の角丸・6 段の余白（ライトの割り当て）
DESIGN.md            トークン（先頭の YAML）と理由（本文の散文）。同じ内容。ライトの割り当てだけ
```

値の持ち主と、生成の向きは 2 案ある（本 skill の整理）。

| 案 | 持ち主 | 生成の向き | 手で書くもの |
|---|---|---|---|
| A | DESIGN.md | DESIGN.md から DTCG の JSON へ。README は、DTCG への書き出しの命令を載せる（S93）。本例では未実行で、出力は未検証 | DESIGN.md のトークンと理由の両方 |
| B | JSON（`design-tokens-minimal.md` のとおり） | JSON から DESIGN.md の YAML へ。この向きの道具は、取得した README の CLI の節に見つからず（S93）、自作の手順になる。仕様は tokens.json などと相互に変換しやすいと述べるが、道具や向きの詳細は書かない（S94） | JSON と、DESIGN.md の理由の節 |

- どちらにするかは、組織で決める（本 skill の整理）。どちらでも、手で直すのは持ち主のファイルだけで、もう一方は生成する（S65 の要旨と同じ考え方）
- 既に JSON があり、部品も JSON から生成している場合は B が自然だが、生成の手順を作る手間が要る（本 skill の整理）

### 本 skill の整理と推測

| 項目 | 内容 | 理由・状態 |
|---|---|---|
| 数字のキー | 例では、余白のキーを `"1"`〜`"8"` にして、JSON の `sys.space.*` の名前に合わせた | 数字だけのキーが有効かは、取得した引用に無い（推測）。確かめるまでは `xs` などの名前にする手もある |
| ダークの割り当て | 別ファイルに持つ案 | 切り替えの項目が、取得した範囲に無い。ファイルの名前・結合の仕方は本 skill の案 |
| ref から sys への別名 | 本例は 10 の役割を値で持ち、別名の層を持たない | `colors` の中で色が別の色を参照する書き方は、取得した範囲で確認できない |

### 対応表

2 つの文書の記述を並べた本 skill の整理である。

| 項目 | DESIGN.md | DTCG（`design-tokens-minimal.md` の JSON） | 根拠 |
|---|---|---|---|
| ファイルの形 | Markdown 1 ファイル。先頭の YAML にトークン、本文に散文 | `*.tokens.json`。理由を持つ場所は、グループの `$description`（任意の文字列）など | S93・S94、S71 |
| 色の値 | CSS の色の文字列。hex が推奨の既定で、`oklch()` も書ける | `colorSpace`・`components`・`hex` のオブジェクト | S94・S93、S95 |
| 寸法 | `8px` のような単位つきの文字列 | `{ "value": 8, "unit": "px" }` | S94、S71 |
| 参照 | `{colors.accent}`。多くのグループで、1 つの値を指す | `{sys.color.accent}`。参照先の `$value` に解決される | S94、S71 |
| グループの名前 | colors・typography・rounded・spacing・components などのグループ名で書く | 任意の入れ子。本例は ref・sys | S94、S71 |
| グループ名の対応（本例） | `colors`・`rounded`・`spacing` | `sys.color`・`sys.radius`・`sys.space`（`rounded` は `radius`、`spacing` は `space` に当たる。JSON 側の名前は `design-tokens-minimal.md` の選択） | S94、本 skill の整理 |
| ref から sys への別名 | 取得した範囲で確認できない | `{ref.color.leaf}` のエイリアス | S94、S71 |
| ライトとダーク | 切り替えを表す項目が、取得した範囲に無い | 本例は `system.dark.tokens.json`。結合の仕組みは未照合 | S93・S94 |
| 理由 | 散文の節。節の名前と順序は仕様が決める | 持つ場所が小さい（`$description`）。長い理由は別の文書 | S93、S71 |

### 実在のサイトから抽出した DESIGN.md を使わない理由

実在のサイトから抽出した DESIGN.md を渡して「この見た目で作って」と頼む使い方は、勧めない（本 skill の整理）。理由は 3 つ。

1. 実在の製品・企業の外観を写すことになる。本 skill は外観の模倣を出さない。参照から抜くのは、技法と判断だけにする
2. 抽出した値は結果の一覧である。理由の節も、元の作り手の意図でなく、抽出した側の推測になる（推測）。目的・相手・トーンを決める手順を飛ばして、他人の既定へ寄る
3. 抽出元の権利・商標・利用条件を、本 skill では判断できない。確認は担当者が行う

代わりに、自分の目的の一文から DESIGN.md を書く。参照は、技法と判断を 1 行ずつ抜いて、理由の節に書く。

## コード断片

以下は例のファイルの中身で、H2 は例の構成ではない。形式は alpha で、本例のファイルは仕様の表記に沿って書いたが、検査する道具は通していない（未検証。YAML の構文だけは読み込めることを確認した）。

`````md
---
version: alpha
name: ハリマ帳
description: 請求書を発行する経理担当者のための、静かで読み間違えない画面
colors:
  bg: "#ffffff"
  surface: "#f4f5f3"
  text: "#1d221e"
  text-muted: "#555c56"
  border: "#767e77"
  accent: "#1b6b4f"
  accent-hover: "#14523c"
  on-accent: "#ffffff"
  danger: "#b42318"
  on-danger: "#ffffff"
rounded:
  sm: 4px
  md: 8px
spacing:
  "1": 4px
  "2": 8px
  "3": 12px
  "4": 16px
  "6": 24px
  "8": 32px
---

## Overview

経理担当者が、1 日に何十枚もの請求書を確認する。派手さより、金額と状態を見間違えないことを優先する。

## Colors

色は役割で持つ。緑は accent 系（accent・accent-hover）だけで、主な操作とリンクに使う。

- accent: 主な操作とリンク。背景との比は 6.44（基準 4.5）
- danger: エラーの文字。色だけで伝えず、文言も添える
- ダークは別の割り当てで持つ。役割の名前は変えない

## Do's and Don'ts

- 部品は役割の名前だけを参照する。16 進値を直接書かない
- 値と理由は、持ち主のファイルだけを直す。役割を足したいときは、理由と使う画面の数を添えて相談する
- 1 回しか使わない色を、ここへ足さない
`````

## 初見検証

DESIGN.md の案内を読んだだけの新しい開発者に、3 つの問いを確かめる。

| 問い | 期待する答え | 確認する場所 |
|---|---|---|
| 何に注意するか | 値の持ち主は 1 つだけ。もう一方は生成する。他人の DESIGN.md を写さない | 運用の案内（文言） |
| 何を操作できるか | 持ち主のファイルのトークンと理由だけを直す。部品は役割の名前だけを参照する | 見本の Do's and Don'ts の節（2 行目まで） |
| どう操作するか | 役割を足したいときは、理由と使う画面の数を添えて相談する | 運用の案内の最後の 1 文・見本の Do's and Don'ts の節の最後の行 |

3 問のいずれかに答えられない場合は、節を増やさず、案内の文面を見直す。

## 点検

- 持ち主: 値の持ち主が JSON か DESIGN.md のどちらか 1 つに決まり、生成の向きと、その道具の有無（案 A の書き出しは未実行、案 B の道具は自作）を書いた
- 入力: 実在のサイトから抽出した DESIGN.md を、入力に使っていない。参照は技法と判断だけ
- 値: DESIGN.md のトークンの値が、`design-tokens-minimal.md` の hex と一致している。余白のキーが数字であることは、推測として書いてある
- 理由: 色の役割ごとに、使う場所と数値が書かれている。数値は計算し直せる（本 skill の計算）
- ダーク: DESIGN.md に切り替えの項目が無いことを書き、別ファイル案は本 skill の整理と明記した
- 推測の明示: 形式は alpha で変わりうる。DESIGN.md の検査の道具と、DTCG への書き出しは実行していない。数字のキーの有効性・変換の向きの運用は、実案件で使う道具の文書で確かめる。採用後の効果は、この例からは分からない
