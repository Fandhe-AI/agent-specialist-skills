# 例: ボタン 40 種類を 2 人・半年でデザインシステムへ寄せる移行計画

3 つのプロダクトに散らばった不揃いなボタンを、棚卸しからデザインシステムの 1 部品へ寄せる計画の例。ガバナンス・貢献モデル・バージョニング・採用の測り方まで、2 人の体制で回る大きさに絞って決める。制作の着手前に開く。題材は架空の会社で、実在の製品・組織の模倣は含まない。数字のうち棚卸しの結果は、この例のための仮定である。

## 依頼

- 会社: 工作機械の部品を扱うケルネ工業（架空）。プロダクトは 3 つ（受注・在庫・請求。Web アプリ。別々のチームが作った）
- 依頼文: 「ボタンが 40 種類もある。半年でデザインシステムに寄せたい。体制は 2 人（デザイナー 1・フロントエンド 1）。計画を作って」
- 想定する読み手: 各プロダクトのリード 3 人と、経営の窓口 1 人。デザインシステムを初めて聞く人もいる
- 前提（置いた）: 2 人はシステム作業に週 2 日ずつ充てられる（半年 26 週で約 104 人日。本 skill の目安）。リブランドの予定は無い

## 目的の一文

半年後、3 つのプロダクトの新規画面が同じボタン部品を使い、必要な違いだけが残り、変更の判断者と窓口が決まっている。

## 削るもの

| 削るもの | 理由 |
|---|---|
| 全部品を一度にシステム化 | 最初は使用回数の多い 1 部品（ボタン）。ほかは順番に（本 skill の整理） |
| 全画面の一括置き換え | 新旧を混在させて段階的に移す（S81）。新規と、すでに触る画面から |
| 見た目の刷新（リブランド） | 移行と刷新を同時にやると、差分の原因が分からなくなる（本 skill の整理） |
| 大きな文書サイト | 大きな公開サイトは小さな案件には要らない、と Frost は述べる（S57）。仕様書は 1 部品 1 ページ |
| Federated（各チームが部品を持ち寄る）体制 | 2 人では成り立ちにくい（推測）。体制の 3 モデルは S60（区分 B の要旨）。まず Centralized に近い形で始める。Salesforce は Centralized と Federated を併用した例（S61） |
| 採用率 100% の目標 | 採用率は成功を示さない（S59）。先行指標を併用する |
| デザインツールのライブラリだけで完了とすること | 静的なデザインツールの中の部品だけではデザインシステムでない（S64、区分 B の要旨）。コードの部品と運用が要るのは本 skill の整理 |
| 専任のガバナンス委員会 | 週 1 回 30 分の判断の枠で足りる（本 skill の目安）。ただし維持には専任のチームが要り、一度で終わらない、と NN/g は書く（S62）。週 2 日 × 2 人の前提は、この指摘との緊張が残るリスクである（点検を参照） |

## 構成

```text
M1 棚卸し       全部品の画面写真を集め、分類する。ワークショップを 1 回
M2 最小の土台   重複していた値だけをトークンにする。判断者・窓口・貢献基準を文書にする
M3 Button 実装   仕様 1 ページと部品を作り、Trial で出す。互換層を置く
M4 パイロット   受注の新規画面に使う。使って出た指摘を直す
M5 展開         在庫・請求の新規画面に広げる。旧ボタンの非推奨を表示する。Trial → Stable
M6 振り返り     指標を読み、旧ボタンの削除の可否と、次の部品を決める
```

| 月 | 成果物 | 次へ進む条件（本 skill の目安） |
|---|---|---|
| M1 | 棚卸しの表（画面・セレクター・役割・差の種類）。分類の結果 | 3 チームの全員が不揃いを見た（S49）。実際の差とずれているだけの差が分かれている |
| M2 | トークン（色・文字・角丸・間隔の実際に重複した値）。体制・貢献基準の文書 | 変更・新規要望・廃止・承認者の問いに答えが出ている（S51） |
| M3 | Button の仕様と実装。版 0.x（Trial）。互換層 | 仕様書だけで、別チームの開発者が置ける |
| M4 | パイロット画面。指摘の一覧 | 1 製品で、新規画面のボタンが新部品だけ |
| M5 | 3 製品での利用。非推奨の表示。Stable の版 | Trial の期間を過ぎ、否定的な反応が無い（S75 の運用に倣う） |
| M6 | 指標の読み。次の部品の候補（使用回数順） | 次の半年の計画を決めた |

### 棚卸しの仮定（架空の結果）

| 分類 | 種類の数 | 扱い |
|---|---|---|
| 必要な違い（主・副・枠線・テキスト・破壊的） | 5 | 残す。役割として仕様に書く |
| 必要な違い（サイズ。標準・小） | 2 | 残す。主・副などと組み合わせる |
| ずれているだけ（色・角丸・余白・文字の太さが画面ごとに違う） | 27 | トークンの参照へ寄せ、旧クラスは互換層で見た目を揃える |
| 重複（同じ役割で別名。アイコンのみ・リンク風を含む） | 6 | 統合。アイコンのみは別部品として後に回す |

この表の合計は 40。数字は仮定で、実際の棚卸しの結果で置き換える。「必要な違い」まで潰さない。破壊的な操作（削除・解約）の見た目は残す（本 skill の整理）。

## 仕様

体制・貢献・版・採用の測りの決め。出典のある事実には S 番号を付ける。付けていない値と決めは、本 skill の目安・整理（出典なし）で、組織の規模に合わせて置き換える。

### 体制・貢献・版の決め

| 論点 | 決め（本 skill の整理） | 根拠 |
|---|---|---|
| 体制 | Centralized に近い形。2 人が部品を持ち、各チームは提案を出す。人が増えたら Federated へ | S60（B の要旨）。併用の例は S61 |
| 変更の判断者 | 仕様はデザイナー、実装はフロントエンド。意見が割れたら、利用画面の多い製品のリードに相談 | S51 の問い |
| 窓口 | 1 つの依頼フォーム（チケット）。自由なチャットでの依頼は受け付けない | 本 skill の目安 |
| 貢献の受け入れ | 5 項目を縮約: 2 製品以上で使う証拠・既存と重複しない・利用者に試した・既存のトークンを再利用・複数の画面で使える | S74（GOV.UK の 5 項目に倣う） |
| 状態 | Trial（試行）と Stable（安定）。Trial は 2 か月。否定的な反応が無ければ Stable | S75 に倣う。2 か月は本 skill の目安（GOV.UK の 6 か月は転用しない） |
| 廃止 | 非推奨の表示 → 2 版のあいだ警告 → 削除（MAJOR で）。手順と期間は本 skill の目安 | S75 は、変化に適応しない部品を非推奨にする、と述べるのみ |
| 版 | MAJOR.MINOR.PATCH | S82 |
| 製品側の拡張 | 部品の CSS を上書きしない。自分の接頭辞（`app-`）で足す | S76 |
| 一貫の考え方 | 同じ言葉・パターンを使うが、画一にしない。ブランドの違いはテーマで出す | S72・S24 |

版の区分は MAJOR・MINOR・PATCH（S82）。何を互換性の破壊とみなすかは、本 skill の整理として、次のとおり決める（見た目の変更を MAJOR にするかは、チームで決める点）:

| 変更 | 版 |
|---|---|
| 属性（props）の削除・改名、トークンの削除・改名、互換層の削除 | MAJOR |
| バリアントの追加、トークンの追加、色の値の変更（リリースノートに書く） | MINOR |
| コントラスト不足の修正、不具合の修正 | PATCH（値が 1 か所にあれば、各チームへ個別に通知せず反映できる、という発想は S65） |

### 採用の測り方

| 種類 | 指標 | 測り方 | 備考 |
|---|---|---|---|
| 遅行 | 旧ボタンの使用箇所の数 | コードの検索（下のコマンド）。毎月 | 採用率だけでは成功を示さない（S59） |
| 遅行 | ボタンのバリアントの数 | 棚卸しの表の再集計。M1 と M6 | 目標値は本 skill の目安（出典なし） |
| 先行 | 新規画面の仕様レビューの前に、システムの担当へ相談が来た割合 | チケットの日付と、画面のレビューの日付 | S59 の問い（どれだけ早く呼ばれるか）に沿う指標で、式は本 skill の整理 |
| 先行 | 依頼から回答までの日数 | チケットの記録 | 目標値は決めない。M1 の実測を基準にする |

自己評価の調査では、デザインシステムを successful と回答した割合は 31%、very successful は 8%（159 件の自己評価。S58）。成功は簡単ではないという参考で、本計画の目標値ではない。

## 文言

| 場所 | 文言 | 理由 |
|---|---|---|
| 計画の 1 行目 | 半年で、新規画面のボタンを 1 つの部品に揃えます。既存の画面は、触るときに順に移します。 | 全画面を直す約束にしない |
| 依頼フォームの題 | 新しい見た目が要る・既存の部品が合わない | 「提案」でなく状況を書かせ、判断の問い（S51）に沿わせる |
| 非推奨の表示（開発者向け） | `.btn-green` は非推奨。`ds-button` の `data-variant="primary"` を使う。M6 以降の MAJOR で削除 | 置き換え先と期限を 1 行で |
| リリースノート | Button 0.4.0: 小サイズを追加。旧クラスの見た目は変わらない | 何が変わり、何が変わらないかを言う |
| 却下の返信 | 既存の「副」と重複しています。違いが要る理由を教えてください | 却下でなく、重複しないこと（S74）の確認を依頼する |

## コード断片

棚卸しの 1 件（JSON。1 画面・1 セレクターにつき 1 件）と、旧クラスを数えるコマンドと、互換層の CSS。外部の CDN・スクリプト・計測は使わない。色の値は M2 で決めるので、この例では持たない。

```json
{
  "product": "受注", "screen": "order-list", "selector": ".btn-green",
  "role": "primary", "differs": ["bg", "radius"],
  "verdict": "drift", "maps_to": "ds-button[data-variant=primary]", "uses": 14
}
```

`verdict` は `essential`（必要な違い）・`drift`（ずれているだけ）・`duplicate`（重複）のどれか。`uses` の合計から、使用回数の多い順を出す。

```sh
#!/bin/sh
# 旧ボタンの class を数える（読み取りのみ）。使い方: ./count-legacy-buttons.sh src
grep -rhoE 'btn-[a-z0-9-]+' --include='*.html' --include='*.tsx' -- "${1:?対象のディレクトリを渡す}" \
  | sort | uniq -c | sort -rn
```

```css
/* 互換層。M3 で置き、M6 以降の MAJOR で削除する。旧クラスの見た目を、新しいトークン経由に揃える。
   ds-button は button 要素に付けるクラスで、役割は data-variant で指定する。
   形（角丸・最小の大きさ）は全役割で共通、色は役割ごとに分ける */
.ds-button, .btn-green, .btn-save, .btn-primary-v2, .btn-delete {
  border-radius: var(--ds-radius-control);
  min-block-size: var(--ds-size-target-min);
}
.ds-button[data-variant="primary"], .btn-green, .btn-save, .btn-primary-v2 {
  background: var(--ds-button-primary-bg);
  color: var(--ds-button-primary-fg);
}
/* 破壊的な操作は必要な違いなので、別に持つ */
.ds-button[data-variant="destructive"], .btn-delete {
  background: var(--ds-button-destructive-bg);
  color: var(--ds-button-destructive-fg);
}
@media (prefers-reduced-motion: reduce) { .ds-button { transition: none; } }
```

- トークンは 2 段（システムのトークンと、部品のトークン）から始め、必要が出たら具体値の層（reference）を足す（本 skill の目安）。`design-tokens-minimal.md` が値の層と役割の層から始めるのと中身が違うのは、組織の事情の違いによる。本例は旧クラスの多い 3 製品の移行で、旧クラスを部品のトークンへ寄せる互換層が要る。Material の公式は reference・system・component の 3 階層で、部品のトークンはシステムのトークンを参照する（S23）。階層を足す理由は、使う人の数で言えるときだけ
- `--ds-size-target-min` の値は M2 で決める。最低線は 24 × 24 CSS px 以上（WCAG 2.2。S85。例外の条件は未転記）。それより大きくする値は本 skill の目安

## 初見検証

計画書を初めて読む各プロダクトのリード 3 人に、説明なしで読んでもらい、3 つを尋ねる。

| 問い | 期待する答え | 確認する場所 |
|---|---|---|
| 何に注意するか | 「M1 の棚卸しに全員が参加する」「既存の画面は触るときに移す」 | 計画の 1 行目、M1 の行 |
| 何を操作できるか・頼めるか | 依頼フォームから、新しい見た目や部品を頼める | 体制・貢献の表の窓口 |
| どう進めるか | 次の 2 週間で、自分のチームが何をするか言える | 月ごとの表の成果物 |

3 問のうち答えられないものがあれば、文書を足さず、決めを減らして位置を見直す。

## 点検

- 棚卸しから始めている。トークンは、実際に重複した値だけから作る（S49）
- 新旧を混在させ、一括の置き換えにしていない（S81）
- 体制のモデルが人数に合い、人が増えたときの次の形を書いてある（S60・S61）
- 変更・廃止・新規要望・承認者の問いに答えがある（S51）。貢献の基準と状態がある（S74・S75）
- 成功の指標が、採用率に当たるもの（旧ボタンの数）だけでなく、先行指標を含む（S59）
- 「必要な違い」を潰していない。破壊的な操作の見た目が残る
- 2 人のうち 1 人が抜けても続くよう、仕様書とチケットに判断が残る。単一障害点（1 つの不具合が複数の製品に及ぶ）の批判がある（S63、区分 C。筆者の意見）ので、版を固定して使える形にする
- アクセシビリティ: 文字と背景のコントラストは 4.5:1 以上、UI 部品は 3:1 以上（S83・S84）。値を決めたら、[ダークテーマの方針書](./dark-theme-dynamic-color-policy.md)の計算式で測る
- 体制の緊張: 週 2 日 × 2 人（約 104 人日）は仮定で、維持に専任のチームが要るという指摘（S62）とは緊張する。M2 で、遅れたときに削る範囲（アイコンのみ部品・小サイズなど）を先に決めておく
- 推測の明示: 棚卸しの数・2 か月・週 2 日・目標値は、この例の仮定と本 skill の目安で、実際の組織のデータではない。採用の遅れの原因は、棚卸しと聞き取りの前には断定できない
