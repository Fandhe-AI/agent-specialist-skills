# デザイン史: Material とデザインシステムの変遷

制作とレビューの判断に歴史を使うための参照。年表の暗記用ではなく、「いま作っているシステムや慣習は、どんな制約から生まれたか」を確かめるための材料である。スタイルガイドからデザインシステムへ、写実からフラットへ、Material の誕生とテーミング、トークンの制度化、Material You、Material 3 Expressive、実装基盤の整理を、時代ごとに同じ 4 項目で書いてある。中心の問いは次の 1 つ。

> その慣習を生んだ制約は、今回の媒体・利用者・体制でも成り立つか。

成り立つなら、慣習は今も根拠を持つ。成り立たないなら、様式だけが残っている可能性がある。

このファイルを開くのは、相談者が背景を求めたとき、制作の着手前（「媒体別の使い方」の節）、レビューで「慣習の由来」の項目が不明のとき、の 3 つである。Apple 側の転換（iOS 7 の理由など）は、designer-apple が導入されていれば、その参照が扱う。本ファイルは Material・Microsoft・デザインシステム側の事情に絞り、Apple は S90 を接続点として 1 件だけ引く。

## 読み方と記法

- 時点: 本ファイルの記述は 2026-11-15 時点（出典の取得日）。出典の詳細（引用原文・日付・URL・検証区分）は `sources.md` を参照する。
- 各時代の 4 項目: 当時の制約 / 応答 / 副作用と反動 / 今の判断への示唆。4 項目めの「示唆」はすべて「本 skill の整理」で、出典が述べた因果ではない。因果（「A だから B になった」）は、出典が述べている場合だけ S 番号付きで書く。
- 区分は `sources.md` の凡例に従う（A 原典、B 再掲・孫引き、C 批判・論評、R 記者・機関の地の文、U 未検証）。B・C・R は区分を明記し、要旨で書く。逐語を本人の発言として示すのは区分 A だけ。U は事実として使わず、末尾の一覧にだけ置く。
- 当事者の述べた理由・記者や批評家の説明・本 skill の整理を分けて読む。人事・社内事情と方針転換の因果は断定しない。
- 日付の欄の日付（記事・告知の日付）は、その出典の公開日。引用に年の無い出来事の年の根拠には使わない。Wayback Machine の保存コピーの日付は公開日ではない。
- 研究の結果（Expressive）は Google 自身の報告で、原論文は未取得。「Google の研究が示唆した」と書く。
- 年が出典どうしで食い違うものは、両側を併記する（7 件。「年が食い違う出典」）。
- 英語の逐語引用は区分 A の出典だけで、1〜2 文に限る。日本語は要旨で、本人の発言ではない。
- 回答での使い方: 頼まれない限り、歴史を講釈しない。判断の根拠として 1 行で使う。例: 「採用率 100% を目標にしたい」という相談には、採用率が 90〜100% でも非効率が残るチームを見たという Dan Mall の観察（S59。本人の逸話的な観察）を 1 行で添える。

## 時代ごとの詳細

### 1. スタイルガイドからパターンライブラリへ（〜2010 年代前半）

- 当時の制約: 設計の成果物が静的な文書で、作った後に実装と食い違いうる。Frost は、スタイルガイドが PSD や PDF などの静的な成果物と同じごみ箱に行く危険を書く（S50）。スタイルガイドの古い例として、1976 年の NASA Graphics Standards Manual を NN/g が挙げる（S62）。Curtis は、Sun.com の living style guide（当時はコンポーネントライブラリと呼んだ）を振り返る（S60、区分 B）。
- 応答: パターンライブラリ（別名: front-end style guides・UI libraries・component libraries）が、設計の土台になりつつあった、と Frost は書く（S54）。Frost の方法論は、UI を Atoms・Molecules・Organisms・Templates・Pages の 5 段階で見る思考モデルである（S48）。
- 副作用と反動: 呼び名が揺れた（S54）。スタイルガイドは成果物、デザインシステムは roadmap と backlog を持つ生きた製品、という整理が出た（Curtis の言葉を Frost が引く。S52、区分 B の要旨）。
- 今の判断への示唆（本 skill の整理）: 「文書を作る」計画ではなく、担当と更新手順を持つ製品として扱う計画にする。最初の一歩は部品の棚卸し（interface inventory。S49）。

### 2. Bootstrap（2011）

- 当時の制約: Twitter の初期、エンジニアは慣れた任意のライブラリを使い、アプリ間の不揃いが拡張・保守を難しくした（S86）。
- 応答: 出典の述べる因果として、Bootstrap はこの課題への答えとして始まり、最初の Hackweek で急速に進み、社内で使える安定版になった（S86、Mark Otto、2011-08-19）。その後、最初の公開版 1.0 として公開された（S86）。
- 副作用と反動: Rupert は、どの案件にも Bootstrap を使うのではなく、案件ごとの小さな Bootstrap を作ることだ、と述べたと Frost が引く（S53、区分 B の要旨）。Bootstrap 製のサイトの見た目が似るという通説の出典は取得していない（未検証）。
- 今の判断への示唆（本 skill の整理）: 既製のフレームワークは速さを買うが、自分たちの文脈の部品は別に要る。既製を土台に自社のトークンと部品で上書きする二層にするかを、先に決める。

### 3. 写実からフラットへ（Metro と iOS 7、2010〜2015）

- 当時の制約（Microsoft 側、出典の述べる理由）: Windows Phone チームは、Windows Mobile の設計の路線が持続不能だと判断し、他のモバイルや PC の UI でなく、国際様式（Müller-Brockmann ら）や Vignelli の NY の路線図などを参照した（S87、2011-02-17）。最初の UI は何であるかを伝える必要から机のような直接的な表現が適切だったが、今は要らないのに、多くのソフトがその道を進んでいる、と述べる（S87）。
- 応答: Metro の原則は Clean・Light・Open・Fast／Alive in Motion／Celebrate Typography／Content, Not Chrome／Authentically Digital。最後の原則は、現実の素材を模す光沢や陰影を避けることを指す（S87）。Apple は iOS 7（2013-06-10）で、Ive が、真の単純さは混乱や装飾が無いことよりずっと多くに由来し、複雑さに秩序をもたらすことだと述べた（S90。Apple 側の理由の詳細は、designer-apple が導入されていれば、その参照を開く）。
- 副作用と反動（NN/g の批判と実験。S88・S89、ともに区分 A）: NN/g は、Metro と Windows 8（同記事の言う 2011 年）がフラット化の普及に影響したとし、フラットは流行の見た目のために利用者のニーズを犠牲にしやすいと批判する（S88）。視線計測では、シグニファイアの弱い版は課題中に見る時間が平均 22% 長く、注視が 25% 多かった（S89、2017。デスクトップのコンピューターで、71 人）。
- 今の判断への示唆（本 skill の整理）: 写実の削減は、読みやすさや内容の主役化という理由で支えられる。ただし、押せる手がかりまで削ると探す時間が増える。フラットか否かでなく、手がかりの強さを問う。

### 4. Material の誕生（2014）

- 当時の制約（Google 側の回想）: Gibson は、2012 年に入社したとき Art Department は 6 人のチームで、約 200 の製品を支えていたと書く。当時デザインシステムは一般的でなく、Kennedy という刷新は上位の Google の Web 製品に限られた（S09、本人の回想）。
- 応答: 素材の比喩は、紙とインクの研究に着想を得た、触覚的な現実に根ざしたもの（S01）。目標は、古典的なデザイン原則と技術の革新を総合した視覚言語と、プラットフォームと画面サイズをまたぐ単一の体系（S02）。印刷由来の要素が階層・意味・焦点をつくる、モーションは利用者の操作を起点にする、という原則もあった（S03）。素材の厚さは 1dp、影は相対的な高さから生じる（S04）。8dp のベースライングリッド（S07）。Android 5.0（API 21）が対応した（S08）。Gibson は、発表から 1 年で 100 万を超える製品が使ったと書く（S09、本人の記述）。
- 副作用と反動: 規則が厳密で似た見た目を生むという批判（S44、2015、区分 C。同記事は結論として lazy designers の問題とも書く）。同記事の筆者は、Material は flat design から進化したと書き、flat design には役割が明確に定まっていない UI 要素があった、と述べる（C。S44 の範囲で、Material が何かを改善したとまでは書いていない）。Apple 側の論者は、iOS アプリに Material を持ち込むと iOS の慣習とずれると批判した（S46、2016、C）。
- 今の判断への示唆（本 skill の整理）: 比喩（紙）が規則（影・厚さ・モーション）を一貫させた。一方、比喩に従う規則は他の媒体では不要になりうる。Material を採るなら、比喩を理解したうえで必要な規則を選ぶ。初版の数値（elevation の dp など。S05）は歴史的な値で、現行の値として使わない。

### 5. 画一化への応答（Material Theming、2018）

- 当時の制約: 初版の指針が似たアプリを量産した、という Google 側の認識を Engadget が伝える（S11、区分 R。記者の要約で、Google の言葉ではない）。ブランド側からは、プラットフォームが画一になるという批判があった（S45、C）。
- 応答: ブランドに合わせて Material を体系的にカスタマイズする枠組み（S10）。Duarte は取材で、小さな開発者でも自分のデザインシステムを Material を土台に作れるよう、デザインシステムを作るためのデザインシステムを持つという趣旨を述べた（原文は "we have a design system for making design systems"）。この発表で最も重要だったのはスタイルと機能の分離（原文は "the separation of style from function"）だったとし、発表の場で “2” と宣言することには意味がなかったという趣旨も述べた（S12、2018-05-11。日本語は要旨で、逐語は `sources.md`）。
- 副作用と反動: カスタマイズできることと、似ないことは別である（本 skill の整理）。
- 今の判断への示唆（本 skill の整理）: トークン（色・書体・形）を差し替える層と、挙動・構造を共通にする層を分ける。差別化は後者を崩さずに前者で行う。

### 6. デザインシステムの制度化とトークン（2015〜2025）

- 当時の制約: 大組織で数百人のデザイナーが多数の製品を作り、一人ひとりに「何をすべきか」を指示できなくなった（Curtis、S60、区分 B の要旨）。複数のプラットフォーム（Web・iOS・Android）へ視覚情報を揃えて届ける必要があった（S65）。
- 応答: 体制の 3 モデル（Solitary・Centralized・Federated。S60）。Salesforce は Centralized と Federated の併用（S61、2015-10-13）。トークンは、視覚情報をデータとして持ち、各プラットフォームの形式へ自動で生成する仕組みとして Salesforce で生まれた、と Jina Anne は述べる（S65、2019-11-19 の回想。年は述べない）。2015-10-13 の Salesforce の記事は、視覚的な Design Tokens と資産の可視化に言及し、Design Tokens という語を使っている（S61。用語の初出を示すものではない）。仕様は、トークンの名が Salesforce のデザインシステムチームに由来すると書く（S69）。DTCG は 2025 年に最初の安定版 2025.10 を発表した（S68、2025-10-28）。区分は Final Community Group Report で、W3C 標準ではない（S69）。
- 副作用と反動: Frost は、デザインシステムの摩擦として、混沌と厳格の間の位置決めを書く（S55）。Sparkbox の 2021 年の調査では、自己評価で successful が 31%、very successful が 8%（159 件。S58）。Storybook の記事はこれを大半の崩壊と言い換えたが、強すぎる読みである（S56）。批判側は、デザインシステムは単一障害点で、設計の判断を部品の組み立てに還元しうると書く（S63、C）。Dan Mall は、採用率は成功を示さないと書く（S59、本人の逸話的な観察）。
- 今の判断への示唆（本 skill の整理）: 組織の規模（1 チームか多数か）で体制モデルを選ぶ。トークンは「交換形式」と「運用ルール」を分けて考える（DTCG は形式を定め、組織の運用は定めない。S70）。成功の指標は採用率だけにしない。

### 7. Material You（2021）

- 当時の制約: 出典が述べる直接の制約は取得していない。Fast Company の記者は、Material が初期の野心から逸れた、と整理する（S42、R）。
- 応答: Android 12 Beta（2021-05-18）で、Material You を単一のデザイン言語として発表した（S15）。dynamic color は壁紙や選択色から配色を作り（S16）、HCT 色空間を使う（S17）。トークンは reference → system → component の 3 階層（S23）。配色は 5 つのキーカラーから、各 13 トーン（S19）。ただし、この 3 点（HCT・3 階層・キーカラー）は現行の文書（2026-11-15 取得）の記述で、2021 年時点で同じだったかは確認していない。
- 副作用と反動: dynamic color は、ブランド色と利用者の壁紙の色のどちらを優先するかという選択を生む（本 skill の整理。出典は取得していない）。
- 今の判断への示唆（本 skill の整理）: ブランドの固定色が必要な部分（ロゴ・状態色）と、利用者の色に従う部分を分ける。ダークテーマは色の反転ではなく、トーンの割り当てで作る。

### 8. Material 3 Expressive（2025）

- 当時の制約（Google の説明）: 研究インターンの調査から、なぜどのアプリも似ていて退屈なのか、という議論が起きた（S34）。
- 応答: 46 件の研究・18,000 人超の参加者（S35）。色・形・大きさ・モーション・containment を使う（S35）。ブログは、主要な UI 要素を最大 4 倍速く見つけたと書き、メールを送る課題で、ボタンへの視線が 4 倍速かったと述べる（S36）。CHI ’26 の要旨は、48 人・10 アプリで、旧 Material 比で注視が 33% 速く、課題完了が 20% 速かった（S39）。Cho は、やりすぎの案が好まれたことに驚いたと述べた（S40、Dezeen。2025-05-28）。
- 副作用と反動・疑義: 好みの最大 87% は 18〜24 歳の数字で、全体ではない（S35）。穏やかな版を好む強い少数派がいた（S38）。プレイリストをばらばらの画像にした案は新しく見えたが、使いやすさは下がった（S37）。批評家は、ボタンの見分けにくさなどを懸念した（S43、C）。研究は Google 自身の報告で、原論文は未取得、独立の追試は見つけていない。ブログの最大 4 倍と要旨の 33% は、最大値と全体値の違いがあり、同じ研究かも明記されていないので、直接比べられない。
- 今の判断への示唆（本 skill の整理）: 「研究で証明された」ではなく「Google の研究が示唆した」と書く。採るなら、主要な操作を大きく目立たせる部分を取り、ラベルの削減や型を崩すレイアウトは避ける。穏やかな選択肢を残す。

### 9. 実装基盤の整理（2024〜2026）

- 当時の制約（出典の述べる理由）: Web 版の Material Web Components は、Material 側が Google 社内の大規模フレームワーク Wiz の支援に集中し、担当のエンジニアを再配置したため、保守モードに入った（S27、2024-06-10）。
- 応答: Android は Compose First。Views のコンポーネントは保守モードで、新機能は入らないが、廃止の予定もない（S29、2026-05-19）。Views 版の Material Components も保守モード（S28）。Web 版も README が保守モードを明記する（S26）。
- 副作用と反動: 新規採用の選択肢が狭まる。Web の公式の Material は新機能が入らないため、自社の部品で Material の考え方（トークン階層）を実装する判断が増える（本 skill の整理）。
- 今の判断への示唆（本 skill の整理）: Android の新規は Compose と Material 3。Web は Material Web に依存せず、トークンの考え方と DTCG 形式を採る選択肢を比べる。

## 繰り返すパターン

次の型は、時代を横断して読み取った本 skill の整理で、出典が述べた法則ではない。例外は多い。

1. 成果物から製品へ。静的な文書は実装と食い違い（S50）、更新の担当を持つ製品として扱う整理が出た（S52、区分 B の要旨。S62）。
2. 厳密な規則は画一化の批判を呼び、層を分けて応える。初版の指針が似たアプリを量産したという認識（S11、R）に、Theming が応えた（S10）。Google 自身も、なぜ似ていて退屈かを Expressive の出発点にした（S34）。公共分野の GOV.UK は、同じ言葉・パターンを使うが拘束衣ではない、と原則に書く（S72）。
3. 装飾を削ると、押せる手がかりが消え、反動が来る。写実の削減は理由を持つが（S87）、手がかりの弱い版は注視が増えた（S89）。Expressive の研究も、基本の型を崩すと使いやすさが下がったと自ら書く（S37）。
4. 値を 1 か所に持ち、複数の媒体へ配る。トークンは、視覚情報をデータとして持つ仕組みとして生まれ（S65）、交換形式が安定版になった（S68）。形式と運用は別で（S70）、運用は組織が決める。
5. 実装基盤は動く。Web 版・Views 版の保守モード（S26〜S28）は、特定の実装に依存した設計の危うさを示す。トークンと原則は、実装が変わっても持ち越せる（本 skill の整理）。
6. 自己報告の研究は、条件を分けて読む。Expressive の数字は、母集団も最大値か全体値かも異なる（S35・S36・S39）。
7. 採用は測りにくい。採用率だけでは成功を示さず（S59）、自己評価の調査でも成功と答えた割合は 4 割弱にとどまる（S58。自己評価）。

## 媒体別の使い方

制作の着手前に、該当する媒体の問いを歴史から引き、その慣習の由来を確かめる。問いは判断を助ける材料で、結論ではない。

### トークン設計（`../examples/design-tokens-minimal.md`）

1. 階層を足す理由は、使う人の数で言えるか。公式の階層は 3 つ（S23）。
2. 値を 1 か所に持ち、複数の媒体へ生成する必要があるか。変数の置き換えで足りるか（S65）。
3. 交換形式が要るか。DTCG は W3C 標準ではなく、形式のみを定める（S69・S70）。
4. ダークテーマは役割へのトーンの割り当てか。M2 の #121212 を引いていないか（S13・S18）。

### Android の画面（`../examples/android-compose-adaptive.md`）

1. Compose と Material 3 で作るか。Views は保守モードで、新機能は入らない（S28・S29）。
2. 窓の大きさの区分で切り替えているか。向きや端末名に頼っていないか（S30）。
3. 一覧と詳細を、窓の大きさで並べて見せているか（S33）。
4. 操作対象は 48dp 以上か（S31）。

### コンポーネント仕様（`../examples/component-spec-button.md`）

1. 仕様書は、更新の担当を持つ製品の一部か。作って終わりになっていないか（S50）。
2. 貢献の受け入れ基準と、状態（試行・安定）の表記を持つか（S74・S75）。
3. 利用側の拡張の流儀（別の接頭辞を使う）を書いたか。部品への上書きに頼らせていないか（S76）。
4. 版の付け方で、何を互換性の破壊とみなすか決めたか（S82）。

### ダークテーマ・dynamic color（`../examples/dark-theme-dynamic-color-policy.md`）

1. ブランドの固定色と、利用者の色の優先順位を決めたか（本 skill の整理）。
2. 生成された配色のコントラストを測ったか。基準は 4.5:1 と 3:1（S83・S84）。
3. dynamic color に対応しない端末の代替を用意したか。Android 12 で追加された機能で（S16）、それ以前の端末には無い（本 skill の整理）。
4. 初版や M2 の値（#121212 など）を、M3 の値として引いていないか（S13）。

### 移行計画（`../examples/design-system-migration-plan.md`）

1. 棚卸しから始めたか（S49）。
2. 新旧を混在させ、段階的に移行する計画か（S81）。
3. 体制のモデルは、人数に合っているか（S60・S61）。
4. 成功の指標は、採用率だけでなく先行指標を含むか（S59）。
