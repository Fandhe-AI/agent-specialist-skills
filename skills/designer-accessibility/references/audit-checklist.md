# 監査の手順と、画面の型ごとの確かめ方

画面や部品を達成基準の番号で判定し、報告書にするときの手順と、画面の型ごと（フォーム・モーダル・メニュー・タブ・コンボボックス・データ表・図・動画・認証・トースト）の確かめ方をまとめる。「監査して」「この画面は WCAG に適合しているか」「スクリーンリーダーで確かめる手順は」と相談されたとき、`../SKILL.md` の判断の型の 2・3 から開く。各型は、実測できるものと、支援技術と人が要るものを分ける。出典の詳細は `sources.md`。「本 skill の整理」と書いた箇所は、出典が述べていない応用である。

## 1. 監査の手順

1. 範囲を決める。対象の画面・状態（初期・入力中・エラー・空・読み込み中・完了・時間切れ）と、確かめる環境（ブラウザー・OS・支援技術とその版）を書く。最初は、確かめやすい 1 画面の主な操作 1 つから始める（SmartHR の手引きの要旨。S246。画面単位への言い換えは本 skill の整理）
2. 基準の版とレベルを決める。既定は WCAG 2.2 の AA（S039）。国内の試験結果の表記は JIS X 8341-3:2016（中身は WCAG 2.0。S094・S102）で、版を分けて書く（`jp-law.md`）。AAA をサイト全体の一律の方針にしない（S007）
3. 方式を決める。方法論は WCAG-EM（S139）。国内の試験は WAIC の試験実施ガイドライン（S097）。ページ数が多いときは代表ページを選ぶ。総ページ数が 100 ページを超えるときは、WAIC は方式 d) を推奨し、合計 40〜50 ページ程度を試験対象にするとよいとする（S097）
4. 自動検査は入口にする。検出なしは適合も使えることも意味しない（S136）。ツールは判断を助けるだけで、アクセシビリティを決められない（S137）。簡易点検に通っても重大な障壁は残りうる（S138）。自動で判断できない検査がある（S143）
5. 実測する（「3. 実測できるものと、支援技術が要るもの」）。
6. 支援技術で確かめる。組み合わせは、調査の版と年を付けて決める（S116・S119）。慣れていない人が試すと、逆効果になりうる（S125）。視覚障害だけに偏らない（S126）
7. 記録する。結果を「適合・不適合・該当なし・未確認」で書き、確かめた方法（実測・読み上げ・設計書の上だけ）を添える
8. 報告する（下の骨格）。直し方は、まず HTML の要素、足りない所だけ ARIA（S047）
9. 利用者と確かめる。障害のある利用者に、実際の作業をしてもらう。結果は一般化しない（S191・S192）。参加者の募集と進め方は designer-ux-research（導入されていれば）と共同する

### 結果の書式

| 区分 | 意味 | 書くこと |
|---|---|---|
| 適合 | 範囲内の全ての画面・状態で基準を満たす | 確かめた方法 |
| 不適合 | 満たさない | 場所・再現手順・直し方 |
| 該当なし | その基準の対象が無い | 対象が無い理由 |
| 未確認 | 確かめていない・確かめられない | 理由と、確かめる方法 |

- 未確認を適合と書かない。支援技術で確かめていなければ、その旨を書く
- 達成基準を満たすことと、Techniques のとおりにすることは別である。Techniques は参考で、適合の基準は達成基準（S033）。注記・例・図も非規範（S005）

### 報告書の骨格

| 節 | 書くこと |
|---|---|
| 対象と版 | 対象の画面・状態・基準の版・レベル・試験日 |
| 環境 | ブラウザー・OS・支援技術とその版・拡大鏡の倍率（S117 は少なくとも 4 倍まで試す） |
| 要約 | 達成基準ごとの結果の件数（適合・不適合・該当なし・未確認） |
| 項目 | 番号・結果・場所・再現手順・直し方・確かめた方法 |
| 未確認 | 実際の読み上げ・音声操作・利用者による理解など。確かめる方法とあわせて |
| 限界 | 自動検査の結果は適合の証拠でない（S136）。少人数の結果は一般化しない（S192） |

## 3. 実測できるものと、支援技術が要るもの

分け方は本 skill の整理である。実測は、描画したブラウザーの版と日付を添えて記録する（本 skill の環境では、ヘッドレスの Chrome 157、2026-11-16。他の環境は未検証）。

### 実測できる

| 項目 | 確かめ方 | 基準・出典 |
|---|---|---|
| アクセシビリティツリー | 名前・役割・状態・値を一覧にする。必須・無効・押下・展開の状態が出るかを見る | 4.1.2（S030）。出ない状態は不適合か未確認として記録する |
| キーボードの順路 | Tab・Shift+Tab・矢印・Enter・Space・Esc で全機能を操作し、順路と焦点の移り先を記録する | 2.1.1（S018）。Tab は部品の間、矢印は部品の中が慣習（S071） |
| 焦点の見え方 | 焦点の印の比（隣接色に対して 3:1）と、固定要素に部品の全体が隠れないか（一部だけ隠れるのは AAA の 2.4.12） | 2.4.7・2.4.11・1.4.11（S021・S022・S016） |
| コントラスト | WCAG の式（S013）で計算。丸めない（S037）。関数は `../examples/audit-report-transit-status.md` の「コントラストの計算」 | 1.4.3・1.4.11（S011・S016） |

### 支援技術と人が要る

| 項目 | 確かめ方 | 注意 |
|---|---|---|
| 実際の読み上げ | VoiceOver・NVDA・JAWS・TalkBack で、ラベル・状態・通知・エラーを聞く | 版と日付を記録する。支援技術ごとの差は、台帳に版つきの記録が少ない（S122・S127・S128）。「X は Y と読む」と断定しない |
| ブラウズモードと入力モード | タブ移動で読まれるラベルが、ブラウズモードで無視される組み合わせがある（S122）。両方で確かめる | NVDA は焦点の種類でモードを自動で切り替える（S124。2020 年の記事）。ブラウズモードは、文書を平らな表示として移動する（S123） |
| 音声操作 | 見えるラベルの語で操作できるか | 台帳に出典が無い。GOV.UK は試験の組み合わせに Dragon を含める（S116） |
| 拡大鏡 | 少なくとも 4 倍まで（S117） | 拡大した視野で、読んでいる位置を見失わないか（S180） |
| 利用者による理解 | 障害のある利用者が、実際の作業を完了できるか | 結果を一般化しない（S192）。自分の支援技術を持参してもらう（S193）。認知障害の参加者には、付き添いを許す（S197） |

## 4. 画面の型ごとの確かめ方

各型で、確かめる操作（実測）、出典のある指針、支援技術と人が要るもの、出典の薄さを分ける。部品のキー操作の型は `widget-patterns.md`。

### フォーム

- 確かめる操作（実測）: キーボードだけで全項目を入力して送信する。わざと誤入力して送信する。ツリーで、各欄の名前と必須・説明が出るか。文字だけ 200% と 320 px
- 出典のある指針
  - ラベルまたは説明を付ける（3.3.2。S027）。プレースホルダーはラベルの代わりにならない（S169）。デジタル庁は原則として使わない（S165）
  - 誤りは、自動で検出したら、項目を特定し、文で説明する（3.3.1。S027）。エラーの文は分かりやすく、直し方を示す（S170）
  - エラーの要約は、検証エラーのときに必ず出す。1 件でも出す（S148）。各欄のエラーには、読み上げ用の隠した「Error:」を先頭に付ける（S147）
  - 欄を離れた時点で検証しない（S149）。入力中のエラーを `aria-live` でリアルタイムに通知しない（S166）
  - 同じ手続きで、入力済みの情報を再入力させない（3.3.7。S028）
- 支援技術・人: 読み上げでのラベル・エラー・必須。タブ移動とブラウズモードの両方（S122）
- 本 skill の整理: 失敗した送信の後は、エラーの要約か最初の誤りへ焦点を移す。入力を消さない。日本語入力の途中（変換中）に文字数制限や検証が走らないか確かめる（出典なし）

### モーダル

- 確かめる操作（実測）: キーボードで開く → 焦点が中へ移るか（S058）→ Tab を一周（最後から最初へ戻る。S058）→ Esc で閉じる（S058）→ 焦点が呼び出し元へ戻るか（S059）。これらは APG の作法で、規範ではない（S055）。達成基準では 2.4.3（焦点の順序。S021）の確認に当たる。背景が操作できないか。名前があるか（S050）
- 出典のある指針
  - 開いたら、焦点はダイアログの中の要素へ移る。閉じたら、呼び出した要素へ戻る。例外は、呼び出した要素がもう無い場合など（S058・S059）
  - ダイアログには名前が必要（S050）。HTML の `dialog` を、メニュー・ツールチップなど別の部品に使うのは適合しない（S072）
  - HTML Standard は、文書がブロックされている間、主体の要素とその子孫を除く全てのノードを inert にすると定める（S073。ブロックはモーダルの `dialog` が起こす状態。本 skill の整理）。`dialog` はおおむね良い選択肢になった（2023 年時点の実務家の見立て。S077）
  - 焦点の閉じ込めは、通常は無効にしない（Material Web の文書。S162）。USWDS の試験記録は、閉じた後に焦点が期待する要素へ戻ることを項目に挙げる（S128。版 3.8.2）
  - モーダルは最後の手段（S152）。破壊的な操作の確認では、cancel に焦点（S158）、または最も破壊的でない操作（S059）。確認ダイアログだけでは安全対策にならない（S164）
  - 閉じるボタンを末尾に置くと、先に読まない画面読み上げがある（S153。版の記載なし。確かめること）
  - ダイアログは利用者の注視点の上に出る（S181。ロービジョンの要件の初期草案）
- 支援技術・人: 開いたときに名前と役割が読まれるか。閉じたときに元の位置の読み上げに戻るか
- 本 skill の整理: 呼び出し元が閉じた後に消える作り（一覧の行の削除など）では、次の操作の位置へ戻す

### メニュー

- 確かめる操作（実測）: キーボードで開閉する。ツリーに出る役割を見る。サイトのナビゲーションに menu の役割を付けていないか
- 出典のある指針: サイトのナビゲーションに ARIA の menu の意味を使わない（S066）。正しく組んだナビゲーションに ARIA は要らない（S067）。Bootstrap のドロップダウンは、ARIA の menu に必要な role・aria- を期待せず、自動でも付けない（S237）
- 食い違い: アプリのメニューに role=menu を使うデザインシステムがある（Carbon。台帳の補足の参照）。サイトの移動か、アプリの操作かで分ける
- 出典のある型（アプリのメニュー）: メニューボタンは役割 button、開くと `aria-expanded` が true。Enter か Space で開き、最初の項目へ焦点（S252）。メニューが開いたら焦点は最初の項目、Tab は項目の間を動かさない、Esc で閉じて開いた要素へ戻す（S253）
- 出典の薄さ: メニューの矢印キーの細部（項目間・サブメニュー）は、S253 の引用に含めていない。APG で確かめる

### タブ

- 確かめる操作（実測）: Tab でタブの列へ入り、矢印でタブ間を移り、Tab でパネルへ移る。ツリーに選択中が出るか。選択中のタブと隣の差（1.4.11。S016）
- 出典のある指針
  - タブは少なくとも 2 つのタブストップ（タブの列とパネル）を持つ（S161）
  - Tab は部品から部品へ、矢印は部品の中を動く（S071）。矢印で前後のタブが切り替わる実装がある（Bootstrap。S240）。MUI の文書は、手動切り替え（manual activation）でキーボード操作を実装すると述べる（S235）
  - パネルの内容が DOM にあれば、表示はほぼ即時。通信を伴うと、選択が焦点に自動で従うのは有害になりうる（S071）。選択が焦点に従わないとき、利用者は Enter か Space で選ぶ（S071）
  - 唯一の正解は無い（S068）
  - APG: tablist・tab・tabpanel の役割。Tab でタブの列に入ると選択中のタブへ焦点が置かれ、次の Tab でタブパネルへ出る。左右の矢印で前後のタブへ移り、端では反対側へ回る。パネルに焦点可能な要素が無いときは `tabindex="0"`（S251）
- 本 skill の整理: パネルの切り替えに通信が伴わないタブは自動、伴うなら手動（APG も、遅延なく表示できるなら自動を勧める。S251）

### コンボボックス（候補の一覧つきの入力）

- 確かめる操作（実測）: キーボードだけで、候補を開く・選ぶ・確定する・閉じる。ツリーの役割と状態。打った値が焦点移動で消えないか。候補の件数の通知
- 出典のある指針: コンボボックスは Tab の順路に入り、Esc でポップアップを閉じ、役割 combobox に `aria-controls`・`aria-expanded` を持つ。ポップアップが listbox・grid・tree のときは、項目へ移っても DOM の焦点は combobox に残り、`aria-activedescendant` が項目を指す。dialog のポップアップでの焦点の扱い（実際の焦点を中へ移すか）は引用に無く、APG で確かめる（S254）。ライブラリの既定値は `library-defaults.md` の 5。通知は状態メッセージの形で（4.1.3。S031）
- 本 skill の整理（推測）: 候補が開くことと、候補の件数が変わることは、焦点を奪わずに伝える（件数の通知は S254 の引用に無い）
- 支援技術・人: 候補を移動したときの読み上げ、確定したときの読み上げ

### データ表

- 確かめる操作（実測）: ツリーで、見出しセルとデータセルの関係。キャプションの有無。狭い幅・拡大で、横スクロールをキーボードで操作できるか。並べ替えの状態がツリーに出るか
- 出典のある指針
  - キャプションは、利用者が表を見つけ、移動し、理解する助けになる（S150）
  - 複雑な表は、小主題ごとの単純な表に分ける（S171）。セルとセル見出しの相互参照が多い構造は、画面読み上げの閲覧が難しい（S167）
  - 横スクロールする表は焦点を受けられるようにする（S154）。並べ替えを有効にするときは、ページに `aria-live` の領域を足す。並べ替えの状態が変わると知らせる領域で、読み込み前に HTML に置く必要がある（S154。USWDS の指針）
  - 並べ替えの可否は見た目に出ないので、設計者が注記する（S160）
- 支援技術・人（時点情報）: 横スクロールの表が、JAWS と NVDA で左右の矢印キーでスクロールしない記録がある（S127。USWDS 3.7.1 の試験記録）
- 表の情報設計は designer-admin（導入されていれば）

### 図（グラフ・ダイアグラム）

- 確かめる操作（実測）: マウスを使わずに要点が分かるか。色を抜いて区別できるか。代替の表・説明に届くか。部品の比（1.4.11。S184）
- 出典のある指針
  - 操作しなくても、図の要点が伝わる（S157）
  - 複雑な画像は、2 部の代替テキストが要る。1 つめは画像を特定し、必要なら長い説明の場所を示す短い説明、2 つめは画像が伝える本質的な情報の文字による表現（S172）
  - 色だけで区別しない（S010・S185）
  - 評価の観点集に Chartability がある（S176）
- 図の設計は designer-dataviz（導入されていれば）。代替の判定と読み上げは本 skill

### 動画

- 確かめる操作（実測）: 音を消して見る。画面を見ずに聞く。プレーヤーをキーボードだけで操作する。自動で 5 秒を超えて動くものを止められるか（2.2.2。S019）。点滅（2.3.1。S020）
- 出典のある指針
  - 字幕は、話し声と、理解に要る話し声以外の音の文字による版（S173）
  - 音声解説は、内容の理解に要る視覚情報を説明する（S174）
  - 書き起こし・音声解説版へのリンクの置き場所を、見た目の設計の段階で用意する（S175）
- 出典の薄さ: 時間依存メディアは、1.2.2・1.2.3・1.2.4・1.2.5 の見出しと本文の最初の部分が台帳にある（S008）。日本語の字幕の表記・表示時間の実務の出典は無い。プレーヤーの操作性の版つきの記録も無い

### 認証

- 確かめる操作（実測）: パスワード管理ツールで入力できるか。貼り付けできるか。コードを写さずに入れられるか。時間切れの前に警告が出るか
- 出典のある指針
  - 記憶する・転記する・パズルを解く、といった認知機能の検査を、認証の途中で求めない。ただし、代替の手段などがある場合は別（3.3.8。S029）
  - ユーザー名とパスワードの記憶は、一部の認知障害のある人に非常に重い、または不可能な負担になる（S178）。パスワード管理ツールと貼り付けを支える（S179）。パスワードを貼り付けられるようにする（S151）
  - 自動サインアウトは、20 秒前に予告する（S156）
- 出典の薄さ: パスキーの扱いは台帳に出典が無い

### トースト・通知

- 確かめる操作（実測）: 通知の領域と通知を同時に差し込んでいないか（S238）。焦点を奪わないか（S051）。消えるまでの時間と、閉じる手段（Esc など。S236）。通知に後で要る情報が載っていないか
- 出典のある指針: 状態メッセージは、焦点を受けずに提示できる形（S031）。通知は、更新された画面の他の場所でも見つけられる事柄だけ（S069）。トーストは、利用者と試してから慎重に使う（S070）。Carbon は操作を含めず、焦点を受けさせない（S159）。React Aria の文書は、最短 5 秒（ライブラリの目安で、WCAG の数値ではない。S233）
- 支援技術・人: 実際に読み上げられるか。消える前に読み終えられるか
- 判断: 自動で消すかは、内容で決める（`../SKILL.md` の「出典どうしで食い違う論点」）
