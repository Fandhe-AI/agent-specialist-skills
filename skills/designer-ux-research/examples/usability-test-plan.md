# 例: ユーザビリティテスト計画書

リリース前のアプリの初回体験を、初めて使う人で確かめる計画書の例。課題文・進行台本・指標・同意・中止の基準までを 1 本にまとめる。題材は架空の製品・会社・参加者で、実在のものの模倣は含まない。調査の計画を作るときに開く。

## 依頼

- 製品: 家計簿アプリ「つむぎ家計」（架空。運営は架空の会社「つむぎ堂」）。動くプロトタイプがある
- 依頼文: 「リリース前に、初めて使う人がつまずかないか確かめたい。5 人でテストすればいいよね」
- 想定する利用者: 家計簿アプリを使ったことがない 20〜40 代。スマートフォンで使う（本例の設定）
- 先に確認したこと: 調査の結果で決める判断は「登録と最初の記帳の画面を、リリース前にどこから直すか」。期限はリリースの 4 週間前。既存の利用データは無い（アプリが未公開のため）

## 目的の一文

家計簿アプリを使ったことがない人が、スマートフォンで登録から最初の 1 件の記帳までに止まる箇所を見つけ、リリース前に直す順番を決める。

研究設問は 2 つに絞る。

1. 使い始めてから最初の記帳が済むまでに、どの画面で止まり、何を誤解するか
2. 記帳を間違えたとき、自力で直せるか

「使いやすいか」という主張は、誰が・どの課題を・どんな条件でと相対に言う（S66）。本例の主張は「家計簿未経験の人が、初回に、スマートフォンで」に限る。

## 削るもの

| 削るもの | 理由 |
|---|---|
| 他の家計簿アプリを使っていた人（乗り換え層） | 利用者層が違うと行動が違うので、層を分けて見る必要がある（S16）。今回は未経験の層 1 つに絞る |
| 「この機能がほしいか」を聞く質問 | 態度の手法は、人が自覚して話せる範囲に限られる（S25）。求めるものと必要なものは違う（S35）。行動を見る |
| 価格・課金の画面 | 今回の判断（登録〜最初の記帳）と関係しない |
| 2 週間後の継続利用 | 1 回のテストでは見えない。日記調査などは別計画（詳細は未照合） |
| グラフ・月次レポートの画面 | 初回体験の範囲外。記帳が数件たまってから見る画面 |
| 満足度の平均点を結論にすること | 5 人の質問票は有意な数にならない（S27）。成績と併用し、主文にしない |
| 「全部の問題を見つけた」という結論 | 5 人で全問題は見つからない（S18、S19）。見ていないことを報告に書く |

## 構成

```text
ラウンド 1（5 人 + 予備 1 人）→ 修正 → ラウンド 2（5 人 + 予備 1 人）→ 修正の確認
  1 日目 3 セッション / 2 日目 3 セッション（予備を含む 6 枠）

1 セッション 45 分 + 片付け 15 分（1 時間の枠）
  0:00  導入・同意の確認・録画の開始       5 分
  0:05  ウォームアップ（日頃の家計の記録）  5 分
  0:10  課題 T1〜T4（思考発話）           25 分
  0:35  質問票（SUS）と振り返り            5 分
  0:40  謝辞・撤回の再確認・終了           5 分
```

- 進行役 1 人、記録役 1 人、観察者は別室で最大 3 人（本 skill の目安）。参加者の画面と声を中継する
- 1 ラウンドで終わらせず、直して再度確かめる回を計画に入れる。5 人の議論の中心は、1 回の大きな調査より小さな調査の反復である（S16）

## 仕様

出典のある値には S 番号を付ける。「目安」は本 skill の目安（出典なし）で、規格や法令の要件ではない。

| 項目 | 値 | 根拠 |
|---|---|---|
| 方法 | 進行役つきの個別テスト。思考発話 | S38、S21 |
| 人数 | 1 ラウンド 5 人。欠席に備えて予備 1 人。層は 1 つ | S16。予備は目安 |
| セッションの長さ | 45 分（30〜60 分の範囲） | S38 |
| 1 日の枠 | 3 セッション。上限は 1 日 6 セッション、間は 15 分以上 | S38 |
| 課題の数 | 4 本。1 本は 5 分で区切る | 目安 |
| 課題文の条件 | 明確な目標・現実的で信じられる・不具合が出る程度に難しい・答えやヒントを漏らさない | S38、S30 |
| 募集 | 経路を混ぜる。柔軟な働き方の人ばかりにしない | S42 |
| 除外される人 | 支援技術（画面読み上げ・拡大表示）の利用者を、5 人のうち 1 人以上含める。支援技術は本人の端末・設定を持参してもらう。課題文の見せ方も、募集のときに本人へ聞く（課題文の節の注） | S37、S43。人数は目安。1 人で利用者全体を代表しない。見せ方は本 skill の整理 |
| 謝礼 | セッションの最初に渡す。金額は組織の規程で決める（出典に金額なし）。参加を強いるほど過大にしない | S42、S56 |
| 観察者への説明 | 参加者のプライバシーを守る責任を、事前に全員へ説明する。参加者にも観察者がいることを伝える | S41、S40 |
| 記録 | 画面と音声の録画。同意があるときだけ | S40 |
| 保存期間 | 6 か月で削除（本例の設定。実際は社内規程で決める） | 目安 |
| 撤回 | セッション中に撤回されたら、中止して集めたデータを削除する | S40 |
| 成功の定義 | 完了 / 助けありで完了（進行役が経路を言った）/ 未完了 / 打ち切り | 本 skill の整理 |
| 修正の候補にする条件 | 同じ箇所で 2 人以上が止まったら候補。1 人でも、データを失う・誤った記録になるものは候補 | 目安 |
| SUS | 終了後に 1 回。5 人の平均点を主文にしない。比べる相手はラウンド 1 とラウンド 2 の同じ手順 | S27、S26 |

課題文の条件（S38）に照らして、課題文に画面のラベルと同じ語（「新規登録」「予算」など）を入れない。S30 は、特定の機能を触らせることに偏った課題文を問題とする。課題が答えの経路を言うと、結果は設計でなく課題文を反映する、という因果は本 skill の整理である。

## 文言

進行役の導入（実際に読み上げる）:

> 今日はお越しいただき、ありがとうございます。試されているのはこのアプリで、あなたではありません。うまくいかなくても、それがこのアプリの直すべき点の手がかりになります。
> 操作しながら、見えていること、考えていること、迷っていることを、そのまま声に出してください。私は途中で答えをお教えできませんが、それは意図的です。

同意の説明文（参加者に事前に渡し、当日に口頭で確認する。S40 の項目。〔 〕は、組織の規程で埋める記入欄）:

| 項目 | 文面 |
|---|---|
| 実施者 | この調査は、〔実施する会社名・部署の名称を記入〕が行います |
| 目的 | アプリの使い始めで分かりにくい箇所を見つけるためです |
| 集めるデータ | 画面の録画、音声、操作の記録、質問票の回答、年代と家計簿の利用経験 |
| 録画・観察 | 画面と音声を録画します。別室で社内の 3 人以内が見ています |
| 結果の使い方 | 社内の改善のために使い、報告では個人が分からない形にします |
| 保存期間 | 6 か月後に削除します |
| 任意・撤回 | 参加は任意です。途中でやめても、あとで取り下げても構いません。取り下げた場合は、録画などをすべて削除します |
| 連絡・苦情の窓口 | 参加をやめたいとき、データの扱いに苦情があるときは、〔窓口の名称と連絡先を記入〕へ連絡してください |

課題文（参加者には紙で 1 本ずつ見せ、声に出して読んでもらう。紙を使えない参加者への代替は表のあとの注）:

| # | 課題文 | ねらい | 完了の定義 |
|---|---|---|---|
| T1 | 友人に勧められた「つむぎ家計」を、今日から家計の記録に使い始めたいと思っています。使い始められる状態にしてください | 使い始めの流れ | ホーム画面に着く |
| T2 | 昼にコンビニで 580 円のお弁当を、現金で買ってきたところです。この買い物を記録してください | 最初の記帳 | 580 円の 1 件が一覧に保存される |
| T3 | さっき記録したお弁当は、レシートを見たら 680 円でした。直してください | 誤りの訂正 | 一覧の金額が 680 円になる |
| T4 | 今月は食べ物に 3 万円までしか使わないと決めました。使いすぎに、あとで気づけるようにしてください | 目標の設定 | 食費に 3 万円の上限が設定される |

注（本 skill の整理。出典なし）: 画面読み上げを使う参加者や、紙の文字を読みにくい参加者には、紙の代わりに、進行役が同じ文面を 1 本ずつ読み上げる。または、本人が使う支援技術で読める文書を、事前に本人の端末へ送る（拡大表示を使う人には大きな文字で印刷する）。どの方法が合うかは、募集のときに本人へ聞く。どの方法でも、課題文の文面は全員で同じにする。支援技術は本人に持参してもらう（S43）。

進行役のことば: 黙ったときは「いま、何が見えていますか」。避ける語は「そこを押してください」「ボタンは右下です」。未訓練の進行役の介入は参加者の行動を変える（S21）。進行役は、同僚相手の予行で台本どおりに黙れるかを確かめてから本番に入る（本 skill の整理）。

## コード断片

### 記録用の列（1 課題 1 行の CSV）

事実（見たこと）と解釈（なぜか）を別の列に分ける。参加者は ID（P01 など）だけで呼び、実名・連絡先は記録に入れない（S41）。

```csv
round,participant_id,task_id,outcome,seconds,stuck_screen,observed_fact,interpretation
1,P01,T2,assisted,214,category_picker,"分類の一覧を 2 度上下に動かし、「食費」を見つけられなかった","分類名が日常の言葉と離れている可能性（要確認）"
```

`outcome` は `completed` / `assisted` / `failed` / `aborted` の 4 値。`seconds` は参考の値で、思考発話の間に出るため速さの比較には使わない（本 skill の整理）。

### SUS の採点（質問文は転載しない）

質問文は著作権表示があるため、正規の文面を使い、順序・文言を変えない（S27）。採点は、奇数項が（回答 − 1）、偶数項が（5 − 回答）で、合計に 2.5 を掛ける（S08 は区分 B の要旨。2.5 を掛けることは S72）。

```python
def sus_score(answers):
    """質問の順（1 から 10）に並べた 1〜5 の回答 10 件から 0〜100 を返す。"""
    if len(answers) != 10 or any(a not in (1, 2, 3, 4, 5) for a in answers):
        raise ValueError("回答は 1〜5 を 10 件")
    odd = sum(a - 1 for a in answers[0::2])    # 奇数項: 回答 - 1
    even = sum(5 - a for a in answers[1::2])   # 偶数項: 5 - 回答
    return (odd + even) * 2.5

assert sus_score([3] * 10) == 50.0
assert sus_score([5, 1] * 5) == 100.0
assert sus_score([1, 5] * 5) == 0.0
# 例: sus_score([4, 2, 4, 2, 3, 2, 4, 1, 4, 3]) は 72.5（実行して確認した値）
```

NN/g は、平均 68（500 件の調査。Sauro の分析の紹介で、原論文未取得）という値を紹介するが、0〜100 は百分率ではなく、小標本では有意な結果にならず、成績なしでは意味が薄いと述べる（S27）。「68 以上なら良い」とは書かない。

## 初見検証

計画書と配布物を初めて読む人に、何を理解し・何をすればよいかを確かめる。

| 読む人 | 確かめること | 期待する答え | 外れたときの直し方 |
|---|---|---|---|
| 参加者（同意の説明文） | 何を集められるか。やめたいときどうするか | 「録画される」「いつでも取り下げられ、その場合は削除される」 | 同意の表の語を短くし、撤回を最後ではなく 2 行目に移す |
| 参加者（課題 T1〜T4） | 何をすればよいか | 画面の語を使わずに、自分の言葉で目的を言い直せる | 目的が場面つきで伝わっていない。状況の 1 文を足す |
| 観察者 | 何をしてはいけないか | 「発言しない」「参加者の個人情報を持ち出さない」 | 入室前の説明に、プライバシーの責任（S41）を口頭で足す |
| 依頼者（計画の要約） | この調査で何が決まり、何は決まらないか | 「登録と最初の記帳の直す順番は決まる。継続利用・乗り換え層は分からない」 | 「削るもの」の表を要約の先頭に移す |
| 同僚（進行の予行） | 黙っていられるか。課題文が経路を漏らしていないか | 課題文の語と画面のラベルが重ならない | 重なる語を言い換え、再度予行する |

## 点検

- 目的の一文に、誰の・どの判断を変えるかが入っている
- 層が 1 つで、人数の根拠に条件（同質の利用者・反復）と出所を添えた（S16）。5 人で全問題が見つかるとは書いていない（S18、S19）
- 課題文が、目的を場面つきで与え、答えの経路を言っていない（S38、S30）
- 同意の項目（目的・データ・結果の使い方と共有先・任意・撤回・保存期間・観察者・録画）が揃い、同意の証拠を保管する（S40）。日本の個人情報保護法・研究倫理の要件を満たすとは言えない。法令・社内規程・倫理審査の確認が要る
- 謝礼を最初に渡す。金額は規程に従う（S42）
- 支援技術の利用者を計画・募集に含め、本人の環境で行う（S37、S43）
- チームの各員が、利用者が使うところを直接見る機会を設け、報告書だけで終わらせない（Spool の経験則。S54、S55。査読を経ていない）
- 推測の明示: 本例の人数・課題数・保存期間・修正候補の条件は本 skill の目安で、実際の製品・利用者に合わせて決める。個別の利用データは分からない
