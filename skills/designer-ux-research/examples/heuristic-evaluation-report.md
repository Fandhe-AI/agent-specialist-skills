# 例: ヒューリスティック評価レポート

利用者調査の前に、専門家が申込の流れの問題を洗い出すレポートの例。独立した評価者・範囲の絞り方・所見の書き方・重大度の集計・「利用者で確かめること」までを 1 本にまとめる。題材は架空の自治体・サイト・評価者で、実在のものの評価ではない。ヒューリスティック評価を計画するとき、または結果を報告するときに開く。

## 依頼

- 対象: 架空の自治体「ひなた市」の粗大ごみ収集の申込サイト（架空。所見もすべて架空）
- 依頼文: 「利用者調査の前に、申込の流れの問題を早く洗い出したい。詳しい人に 1 人で見てもらえばいいよね」
- 想定する利用者: 初めて粗大ごみを出す市民。スマートフォンとパソコンの両方（本例の設定）
- 先に確認したこと: 調査の結果で決める判断は「利用者テストの前に直す箇所と、テストで確かめる箇所」。期限は利用者テストの 3 週間前。評価者は 3 人（E1〜E3。実名は載せない）

## 目的の一文

粗大ごみの申込（品目の選択から完了まで）で、利用者テストの前に直せる問題と、テストで確かめるべき問題を、専門家の目で分けて出す。

専門家の評価は仮説であり、利用者調査の代わりにならない（S22）。このレポートは、利用者調査の前段にあたる。

## 削るもの

| 削るもの | 理由 |
|---|---|
| 申込の流れ以外（分別の案内・お知らせ・管理画面） | 範囲を 1 つの流れに絞る。広げると所見が薄くなる（本 skill の整理） |
| 電話受付・コンビニでの手数料の支払い | サイトの外の体験。別の調査で見る |
| 画面読み上げ・拡大表示での動作確認 | 専門家の目視では足りない。支援技術の利用者で確かめる（S37、S43）。本例のコントラストの計算 1 件は、基準への適合の確認ではない |
| 色・写真の好み | 好みは所見でなく意見。使えるかどうかに関わるものだけ書く |
| 「問題の割合」「利用者の失敗率」 | 専門家の評価では分からない。利用者で確かめる（S22） |
| 評価者 1 人の所見だけでの確定 | 評価者ごとに見落とす（S22）。独立した 3 人の所見を突き合わせる |
| 「全部の問題を見つけた」という結論 | 専門チームによる評価の結果がほとんど一致しなかった報告がある（CUE。S19）。ヒューリスティック評価への当てはめは本 skill の推測。見ていないことを書く |

## 構成

```text
1. 要約（判断が変わる点・件数・限界）
2. 範囲と方法（評価した流れ・評価者・手順・見ていないこと）
3. 所見一覧（重大度の高い順。重大度は評価者間の最大値）
4. 評価者間の一致と食い違い
5. 利用者で確かめること
6. 次の手順
付録: 評価者ごとの提出（生データ）
```

手順: 範囲と項目の説明を共有する → E1〜E3 が互いの結果を見ずに各自で評価する → 提出する → 突き合わせて重複をまとめる → 重大度の食い違いを協議する → 報告する。

評価した流れ: 品目の選択 → 収集日の選択 → 申込者の情報の入力 → 確認 → 完了（5 画面）。

## 仕様

出典のある値には S 番号を付ける。「目安」「整理」は本 skill のもの（出典なし）。

| 項目 | 値 | 根拠 |
|---|---|---|
| 評価者 | 独立した 3 人（3〜5 人が目安） | S22 |
| 提出前 | 互いの評価を見せない。自分の評価が終わるまで見ない | S22 |
| 範囲 | 1 つの流れ（5 画面） | 整理 |
| 評価の進め方 | 流れ全体を通して見てから、画面ごとに項目に照らす（2 周） | 目安 |
| 項目 | NN/g の 10 項目。広い経験則で、具体的なガイドラインではない。指針であり、法則ではない | S12、S22 |
| 重大度 | 下の 3 段階。評価者ごとに付け、食い違いを残す。一覧と要約の重大度は、評価者間の最大値で集計し、最小〜最大を併記する。並べ方は、最大値の高い順、同じなら見つけた人数の多い順、それも同じなら ID の順 | 整理 |
| 食い違いの扱い | 重大度の差が 2 以上は協議する。消さずに報告に残す | 目安 |
| 位置づけ | 専門家の仮説。「利用者で確かめること」を別の節に書く | S22 |
| 色の確認 | 色のコントラストは、基準（通常のテキスト 4.5:1 以上）に照らして計算する | S59 |

項目は、NN/g のページの見出しの並びで H1〜H10 と呼ぶ（本例の便宜）。項目名は S12、右の要旨は本 skill の言葉で、定義文は転載しない。

| 記号 | 項目名（S12） | 要旨 |
|---|---|---|
| H1 | Visibility of System Status | 今の状態と結果が分かること |
| H2 | Match Between the System and the Real World | 利用者の言葉・概念で語ること |
| H3 | User Control and Freedom | 間違えたとき、すぐ抜けられること |
| H4 | Consistency and Standards | 同じものは同じに。外の慣習に合わせる（S13） |
| H5 | Error Prevention | 起きてから直すより、起きないようにする |
| H6 | Recognition Rather than Recall | 覚えさせず、見て選べるようにする |
| H7 | Flexibility and Efficiency of Use | 初心者にも熟練者にも合う近道を用意する |
| H8 | Aesthetic and Minimalist Design | 無関係・まれな情報を置かない |
| H9 | Help Users Recognize, Diagnose, and Recover from Errors | エラーは平易に、原因と直し方を示す |
| H10 | Help and Documentation | 説明が要らない設計が最良。要るなら探しやすく |

重大度（本 skill の整理。出典なし）:

| 値 | 意味 |
|---|---|
| 3 | 申込を完了できない、または誤った申込になる可能性が高い |
| 2 | 迷う・やり直しが要るが、完了はできる |
| 1 | 軽微。直せば良くなる |

## 文言

要約（レポートの冒頭。判断が変わる点を先頭に置く）:

> 申込の流れ（5 画面）を、独立した 3 人の評価者が評価し、重複をまとめて 10 件の所見を得た。重大度 3（評価者間の最大値）が 5 件（F01・F02・F03・F04・F09）。3 人とも見つけたのは 2 件、1 人だけが見つけたのは 3 件で、評価者ごとの見落としが大きい（S22）。このため、3 人でも全部の問題を見つけたとは言えない。所見は専門家の仮説であり、重大度 3 の 5 件と、評価者間で重大度が 1〜3 に割れた F09 は、利用者テストで確かめる。

所見の書き方（場所・何が・どの項目か・なぜ問題か）:

| 悪い書き方 | 良い書き方 |
|---|---|
| 分かりにくい | 品目の選択の画面で、品目名が分類名（「家具類（大）」）で並び、利用者が持つ物の呼び名（ベッド・たんす）で探せない（H2） |
| エラーが不親切 | 電話番号をハイフンつきで入れると「形式が正しくありません」とだけ出て、どう直すかが書かれていない（H9） |

所見一覧（重大度の高い順。見つけた人数・重大度の範囲は、コード断片の集計の出力と一致させた。重大度は評価者間の最大値）:

| ID | 場所 | 所見 | 項目 | 見つけた人数 | 重大度（最小〜最大） |
|---|---|---|---|---|---|
| F01 | 品目の選択 | 品目名が分類名で並び、利用者の呼び名で探せない | H2 | 3/3 | 2〜3 |
| F04 | 申込者の情報 | 電話番号のハイフンで、原因と直し方の無いエラーが出る | H9 | 3/3 | 2〜3 |
| F02 | 確認 | 確認画面から戻ると、選んだ品目がすべて消える | H3 | 2/3 | 3〜3 |
| F03 | 品目の選択〜確認 | 手数料の合計が最後の確認まで出ず、追加するか判断できない | H1、H5 | 2/3 | 2〜3 |
| F09 | 完了 | 完了画面に、申込の取消・変更の方法がない | H3、H10 | 2/3 | 1〜3（要協議） |
| F07 | 申込者の情報 | フォームの前に 7 段落の注意書きがある | H8 | 2/3 | 1〜2 |
| F08 | 品目の選択 | 品目を名前で検索できず、一覧から探すだけ | H6、H7 | 2/3 | 1〜2 |
| F05 | 収集日の選択 | 空きのない日が灰色の文字で示され、空きの有無が読み取りにくい（H1 の所見）。#8a8a8a の文字と #ffffff の背景のコントラスト比は 3.45:1 で、通常のテキストの基準 4.5:1（S59）に届かない。適合の判定ではなく、判定は別に確認する | H1 | 1/3 | 2〜2 |
| F06 | 全画面 | 画面ごとに「次へ」の位置と色が違う | H4 | 1/3 | 2〜2 |
| F10 | 全画面 | 「よくある質問」が PDF の一覧で、申込画面から遠い | H10 | 1/3 | 1〜1 |

利用者で確かめること（専門家の仮説を、利用者テストの課題にする。課題文の条件は S38）:

| 仮説 | 確かめ方 |
|---|---|
| F01・F08: 利用者は、持っている物の名前で探して、見つけられない | 「ベッドとたんすを出したいと思っています。出す手続きをしてください」という課題で、探す様子を見る |
| F03: 手数料が分からず、申込を途中でやめる人がいる | 「いくらかかるかを知ってから、申し込むか決めたい」という課題で、どの画面で金額を探すか見る |
| F09: 取り消したいときに、サイトで取り消せると分からない | 「申込のあとで日程が合わなくなりました」という課題で、行き先を見る |

## コード断片

評価者ごとの提出を 1 所見 1 行の CSV にする。評価者は E1〜E3 の記号だけで呼ぶ。

```python
import csv, io
from collections import defaultdict

RAW = """finding,evaluator,heuristic,severity
F01,E1,H2,3
F01,E2,H2,2
F01,E3,H2,3
F02,E1,H3,3
F02,E3,H3,3
F03,E1,H5,2
F03,E2,H1,3
F04,E1,H9,2
F04,E2,H9,2
F04,E3,H9,3
F05,E2,H1,2
F06,E3,H4,2
F07,E1,H8,1
F07,E3,H8,2
F08,E1,H7,1
F08,E2,H6,2
F09,E2,H3,3
F09,E3,H10,1
F10,E3,H10,1
"""
EVALUATORS = {"E1", "E2", "E3"}

groups = defaultdict(list)
for row in csv.DictReader(io.StringIO(RAW)):
    groups[row["finding"]].append(row)

report = []
for fid, rows in groups.items():
    sev = [int(r["severity"]) for r in rows]
    who = sorted({r["evaluator"] for r in rows})
    assert set(who) <= EVALUATORS and len(who) == len(rows), fid   # 1 人 1 所見 1 行
    report.append({
        "id": fid, "found_by": len(who), "who": "+".join(who),
        "heuristics": "/".join(sorted({r["heuristic"] for r in rows}, key=lambda h: int(h[1:]))),
        "min": min(sev), "max": max(sev), "disagree": max(sev) - min(sev) >= 2,
    })

report.sort(key=lambda r: (-r["max"], -r["found_by"], r["id"]))
print("id   found_by who        heuristics sev   評価者間の食い違い")
for r in report:
    print(f'{r["id"]}  {r["found_by"]}/{len(EVALUATORS)}      {r["who"]:<8}  {r["heuristics"]:<10} '
          f'{r["min"]}-{r["max"]}   {"要協議" if r["disagree"] else ""}')
print("3 人とも:", sum(r["found_by"] == 3 for r in report), "件 / 1 人だけ:",
      sum(r["found_by"] == 1 for r in report), "件 / 全", len(report), "件")
```

F02  2/3      E1+E3     H3         3-3   
F03  2/3      E1+E2     H1/H5      2-3

色のコントラスト比は、WCAG の相対輝度の式で計算する（基準値は S59。式そのものは本 skill の計算で、S59 の引用ではない）。

```python
def lin(c):
    c /= 255
    return c / 12.92 if c <= 0.03928 else ((c + 0.055) / 1.055) ** 2.4

def luminance(hex_color):
    r, g, b = (int(hex_color[i:i + 2], 16) for i in (1, 3, 5))
    return 0.2126 * lin(r) + 0.7152 * lin(g) + 0.0722 * lin(b)

def contrast(a, b):
    hi, lo = sorted((luminance(a), luminance(b)), reverse=True)
    return (hi + 0.05) / (lo + 0.05)

# contrast("#8a8a8a", "#ffffff") は 3.45、contrast("#767676", "#ffffff") は 4.54（実行した値）
```

## 初見検証

レポートを初めて読む人に、何を理解し・何をすればよいかを確かめる。

| 読む人 | 確かめること | 期待する答え | 外れたときの直し方 |
|---|---|---|---|
| 市の担当課（依頼者） | 何が最初に直す対象か。何は分からないか | 「重大度 3（評価者間の最大値）の 5 件」「利用者がどうなるかは分からず、テストで確かめる」 | 要約の先頭に、直す順と「分からないこと」の 2 行を置く |
| 委託先の開発者 | 所見の場所と直す対象を特定できるか | 画面名と場所から、該当の箇所を指せる | 所見に、画面名と操作の手順を足す（書き方の表の良い例の形） |
| 次の評価者 | 重大度を迷わずに付けられるか | 3・2・1 の意味から選べる | 意味の例を足す。それでも割れる所見は協議に回す |
| 利用者テストの担当 | どの所見をどの課題で確かめるか | 「利用者で確かめること」の表から課題を作れる | 仮説と課題文の対応の表に、観察する場所を足す |

## 点検

- 評価者が 3 人で、互いの結果を見る前に各自が評価した（S22）。1 人だけの所見で確定していない
- 範囲を 1 つの流れに絞り、見ていないこと（他の画面・支援技術・電話受付）を書いた
- 所見に、場所・何が・どの項目か・なぜ問題かがある。項目名は NN/g のページの見出しで、定義文は転載していない（S12）
- 重大度は本 skill の整理であることと、集計が評価者間の最大値であることを明記し、評価者間の食い違いを消さず、協議に回した
- 「全部見つけた」「必ず直る」といった断定を使っていない。3 人でも見落としが残る（S22。評価チームの不一致は S19 の CUE で、当てはめは推測）
- 専門家の仮説と、利用者で確かめることを分けた。利用者調査の代わりにしていない（S22）
- 色のコントラストは計算した値で書き、基準への適合の判定は別に確認する（S59）。支援技術の利用者での確認は別計画（S37、S43）
- 推測の明示: 本例の所見・評価者・重大度はすべて架空で、実在のサイトの評価ではない。評価者数・手順の周回数・食い違いの閾値は本 skill の目安
