# デザイン史: 規則を書く表現から、ブラウザの GPU まで

Web の生成的表現・WebGL・3D の慣習が、どんな制約から生まれ、何に直され、今の判断に何を示すかをまとめたファイル。年表の暗記用ではなく、「いま作ろうとしている表現は、どんな制約の変化で可能になったか」を確かめるための材料である。要点（見取り図・繰り返すパターン・媒体別の問い）と、時代別の詳細を 1 ファイルに置いた。中心の問いは次の 1 つ。

> その表現を可能にした制約の変化は、今回の利用者と端末でも成り立つか。

成り立つなら、その技法は今も根拠を持つ。成り立たないなら、技法だけが残っている可能性がある。

このファイルを開くのは、相談者が背景を求めたとき、制作の着手前（「媒体別の使い方」の節）、レビューで「慣習の由来」の項目が不明のとき、の 3 つである。

| 知りたいこと | 開く場所 |
|---|---|
| 全体像・横断の型 | 「見取り図」「繰り返すパターン」 |
| 媒体ごとに確かめる問い | 「媒体別の使い方」 |
| ある慣習の由来（Processing・Flash への批判・WebGL・WebGL 2・WebGPU・受賞作の工程など） | 「時代別の詳細」の 6 つの節 |
| 年が出典どうしで合わない項目 | 「年・日付が食い違う出典」 |
| 俗説・未検証の主張 | 「確認できなかったもの」 |

## 読み方と記法

- 時点: 記述は 2026-11-15 時点（出典の取得日）。出典の詳細（引用原文・日付・URL・検証区分）は `sources.md` を参照する。
- 各時代の 4 項目: 当時の制約 / 応答 / 副作用と反動 / 今の判断への示唆。4 項目めの「示唆」はすべて「本 skill の整理（推測）」で、出典が述べた因果ではない。因果（「A だから B になった」）は、出典が述べている場合だけ S 番号つきで書く。出典が述べていないつなぎは「整理（推測）」と書く。
- 区分は `sources.md` の凡例に従う（A 原典、B 第三者の転載・翻訳、C 論評、R 記者・歴史家・機関・Wikipedia の地の文、U 未検証）。B・C・R は区分を明記して要旨にし、英語の逐語で本人の発言としては示さない。R は年号の根拠にだけ使う。
- 英語の逐語は区分 A の出典だけで、1〜2 文に限る。日本語は要旨で、本人の発言ではない。Vera Molnár の文は英訳からの引用で、日本語にするときは英語からの重訳である。
- 年・日付: S 番号を添えた論旨上の年は、引用ブロックの原文に含まれるものに限る。引用ブロックに年を含むのは、S02（「68」。1968 年ごろの意味は本 skill の読み）・S06（1999-2003）・S18（2009）・S19（2011）・S20（2009-03-18）・S22（2010-04-24）・S29（2020 年末）・S31（2011-03-03）・S37（2026-09-15）・S114（2016-01-25）・S144（2001）・S145（2009-03-01）・S146（2017）・S152（2021-08-09）・S154（2014）・S167（2013-2020）である。ほかの年・日付（S23・S28・S32・S34 など）は、台帳の「媒体・日付」の項による書誌の年で、論旨を支える年としては使わない。
- この領域の歴史は、動きの原則（導入されていれば designer-interaction）や見た目の方向性（導入されていれば designer-web）の歴史と重なる。ここでは、WebGL・シェーダー・粒子・生成・3D を Web に出すときの判断に効く部分だけを扱う。
- 回答での使い方: 頼まれない限り、歴史を講釈しない。判断の根拠として 1 行で使う。

## 回答での使い方（例）

歴史は、判断の根拠として 1 行で添える。講釈にしない。

- 相談「WebGPU にすれば速くなる」: 4 つのブラウザが対応した（S34）。ただし Safari は macOS Tahoe 26・iOS 26 などで使える（S35）一方、Linux・Android・Intel Mac の対応は進行中だった（S36。いずれも 2025-11 の記事）。three.js の WebGPURenderer は実験段階で、場合によっては WebGLRenderer のほうが速いと述べる（S39）。一般則として「常に速い」とは書かない。
- 相談「Flash みたいな演出を今のブラウザで」: 批判の構図は戻りうる。Nielsen は、動かせるから動かす誘惑と、利用者の操作の自由を下げる提示を批判した（S24、S25）。技術が変わっても、設計の失敗は同じ形で起きる（本 skill の整理）。
- 相談「受賞作みたいにしたい」: 受賞作は素材の工程・期間・チームの産物である。2 人のチームがモデリングを手作業で数週間かけた事例（S81、S164）、1 年強かけた個人の作品（S85）、1 年がかりの社内企画（S109）がある。コードの技法だけでは再現できない。
- 相談「アクセシビリティは後で」: 動きの規則は WebGL のために作られたものではないが、シェーダーの動きにも適用される（S118、S121）。後付けは、canvas の外に意味を足す作業になる。最初に層 0（HTML の内容と操作）を作る（本 skill の整理）。
- 相談「機械が作る絵は冷たい」: Molnár は、冷たく非人間的と思われる機械が、人間のもっとも主観的で深いものの実現を助けうると述べた（S01、英訳・紹介文内の引用）。生成的表現の核は、規則の設計と結果の検証である（S03）。

## 見取り図

| 時代 | 何が可能になったか | 何が置き去りになったか |
|---|---|---|
| 1960 年代から 1970 年代 | 規則を書いて機械に絵を描かせる（Molnár・LeWitt） | 一般の制作者が使える道具はまだ無い |
| 1999 年から 2005 年ごろ | 設計者が自分でコードを書く（DBN・Processing） | Web での配布は別の仕組み（Flash 等）に頼る |
| Flash の時代（2000 年の批判から 2020 年末の配布終了予告まで） | ブラウザ上の豊かな表現 | 使い勝手・電力・タッチ・非公開の仕様への批判 |
| 2009 年から 2011 年 | プラグイン無しで JavaScript と GPU を使う（Chrome Experiments・three.js・WebGL 1.0） | 端末とブラウザの差 |
| 2017 年から 2022 年 | WebGL 2 が主要ブラウザで揃う。Flash の終了予告（2020 年末） | 動きの配慮（前庭障害）の議論が実装に追いつく途上 |
| 2022 年から 2026 年 | 制作会社の工程が公開され、WebGPU が主要ブラウザに入る | アクセシビリティの低さ・重さ・素材の工程の大きさ |

## 繰り返すパターン（本 skill の整理）

次の型は、出典を横断して読み取ったもので、出典が述べた法則ではない。例外は多い。

1. 驚きの技術は、まず実験場に出る。Chrome Experiments は、JavaScript と HTML5 の限界を押し広げる作品の展示場として始まった（S17、S18）。製品の本線に出すかは、実験と製品のどちらに置くかを先に決める。
2. 新しい技術の批判は、技術でなく設計の失敗に向く。Flash への批判（S23、S165）は、動かせるから動かす・操作の自由を奪う・注意をそらす、という設計の話である。WebGL の没入型サイトにも同じ構図が戻りうる。
3. 標準になっても、端末の差は残る。WebGL 1.0 の後も、ブラウザ・版・GPU の組み合わせの多さは悩みの種だった（S156）。WebGL 2 は 2017 年に出荷されたが（S146）、主要ブラウザが揃ったのは Safari 15 の対応による（S32。記事は 2022-02-09）。WebGPU も同じ段階にいる（S35、S36）。
4. 道具は、入口を低く、上限を高くする方向に進んだ。DBN の意図的な小ささ（S07）から、Processing（S08）、p5.js（S15、S16）へ。共有の規範（S10）が系譜を支えた。
5. 表現が先に進み、配慮が後から追いつく。動きを減らす設定の提案は 2014 年（S154）で、WebGL 1.0 の公開（2011 年。S31）より後である。評価の仕組みも遅れる（S136、S137）。
6. 受賞作の技法は、素材の工程と一対である。コードの断片だけを写しても、素材・期間・チームの前提は写らない（S81、S85、S109、S113）。
7. 性能は設計の制約として扱われる（S86）。古い端末で後処理を切る設計は、2016 年の記事にすでにある（S114）。

## 媒体別の使い方

制作の着手前に、該当する媒体の問いを歴史から引き、その表現を可能にした制約が今回も成り立つかを確かめる。問いは判断を助ける材料で、結論ではない。

### 告知ページの背景・ヒーロー（`../examples/shader-gradient-background.md`）

1. その動きは、ブラウザが GPU を持つ前なら、プラグインや動画に頼った表現だった（整理）。いまは素材なしで、式だけで作れる。素材の工程は要らない（S164、S85 と比べる）。
2. Flash への批判の構図（動かせるから動かす。S24）に当たらないか。背景の動きが、読むことを邪魔しないか。
3. 自動で動き続けるので、止める手段と、動きを減らす設定での静止があるか（S121、S127）。

### 製品サイトのファーストビュー（`../examples/particle-product-hero.md`）

1. 受賞作の製品の演出は、CAD の変換・3D スキャンの購入・圧縮の工程と一対である（S113、S108）。素材が無い段階で、式だけの形で足りるか。
2. 粒子の数は、専用設計の事例（S112）を初期値にしない。端末ごとに自動で品質を落とす設計は、2016 年の記事にもある（S114）。
3. ホバー前提の演出は、タッチで成り立たない（S27）。

### 読み物・年次報告（`../examples/scroll-procedural-3d.md`）

1. UI まで WebGL で描く構成は、受賞作に見られる（S77、S93）が、記事はその代償を述べていない。本文を DOM に置く構成と比べる。
2. 視差・拡大縮小などの動きは、前庭の症状の引き金になりうる（S120、S123）。
3. スクロールに完全に縛る提示は、Flash への批判（S25）と同じ構図になりうる（本 skill の整理）。

### 生成的なポスター・作品（`../examples/generative-poster.md`）

1. 従来の生成芸術には、多数の出力から少数を選ぶ段階があった（S30）。Web では、閲覧者ごとの出力を作者が選別できない。seed を固定するか、出力の幅を絞るかを決める。
2. 規則を書いて検証する姿勢（S03）は、見た目より先に規則を決める、という意味で今も使える。
3. 日時・会場など読ませる情報は、図の中に閉じ込めない（S129、S131 は区分 C）。

### 写真・作品のギャラリー（`../examples/distortion-gallery.md`）

1. 既にある素材に反応を足す表現は、素材の工程を新しく要らない。ただし、ホバー前提はタッチで壊れる（S27）。
2. 動きを減らす設定で、効果を作らない選択がある（S119、S122）。
3. 文脈の喪失は例外でなく通常の事象で、復帰の設計が要る（S64、S65、S158、S159）。

## 時代別の詳細

### 1960 年代から 1970 年代: 規則を書いて機械に回させる

**当時の制約**

- 計算機は研究機関や大学にあり、作家が自由に使えなかった。Molnár は 1968 年ごろに実機の計算機を使えるようになった（S02、区分 R の編集部の地の文）。それ以前は、machine imaginaire（想像上の機械）を手作業で回した（S04）。

**応答**

- 規則（アルゴリズム）を作者が書き、機械に実行させる。Molnár は、系を作り、変化と自分への作用を確かめる実験の方法と説明した（S03）。
- Sol LeWitt（1967 年の論文を Tate が引く。区分 B。S05）は、概念芸術では、計画と決定が事前に済み、実行は形式的な作業になる、と述べたと引かれる。

**副作用と反動**

- 機械は冷たく非人間的だという通念があった。Molnár は逆に、機械が人間のもっとも主観的で深いものの実現を助けうると述べた（S01、英訳・紹介文内の引用）。
- 生成芸術には、多数の出力から少数を選ぶ段階が、ほぼ常にあった（S30）。

**今の判断への示唆（整理・推測）**

- 生成的表現の核は、見た目でなく「規則の設計と、結果の検証」である。「それっぽい動き」を求められたときは、規則（何を入力に、何を保つか）を先に決める。
- Web では閲覧者ごとに出力が変わりうる。seed を固定するかを、設計で決める（S30 を前提にした整理）。

### 1999 年から 2005 年ごろ: 設計者がコードを書く道具

**当時の制約**

- コードを学ぶ場は計算機科学の学科で、テキストと数学だけを扱った。視覚の制作者は、数週間で離れるか、苦痛を抱えて残った（Reas の説明。S155）。

**応答**

- MIT Media Lab の Aesthetics and Computation Group で Design By Numbers（DBN）が作られた（S06。著作権表記は 1999-2003）。DBN は 8 つのコマンド・100 × 100 ピクセル・グレースケールだけの、意図的に小さな環境だった（S07）。
- Reas は、Processing を、DBN の最小性を保ちつつ、学習環境を超えて制作環境まで広げたものと説明する（S08）。開始は 2001 年（S144、区分 R）。最初の公開の 20 周年は 2021-08-09 に祝われた（S152）。Processing は、ソフトウェアのスケッチブックとして始まった（S11）。
- 同じ姿勢の仲間として、C++ の openFrameworks（S14）と、p5.js（S15、S16）がある。p5.js の公式ページは、p5.js を Processing の仲間の一つとして並べ（S166）、作者・リードの期間を 2013-2020 と記す（S167。公開日そのものではない）。Web に向く道具であることは、本 skill の整理（推測）。
- 共有の規範（ソースを見せ、学び合う）も系譜の一部だった（S10）。

**副作用と反動**

- 教師だった Maeda は、Processing の必要性を見誤ったと自ら書いたと引かれる（区分 B。S13）。道具の価値は、作る人の側から見えることがある。
- Maeda は Processing を Flash グラフィックスの数少ないオープンソースの挑戦者と位置づけた（区分 B。S12。Ben Fry のブログが引いた抜粋で、元の寄稿の日付は未確認）。Flash が当時の Web の表現を担っていたことの傍証になる（整理・推測）。

**今の判断への示唆（整理・推測）**

- 入口を低く、上限を高く。小さな環境で動かして試す姿勢は、プロトタイプの作り方（コードで速く描く）にそのまま使える。
- 設計者がコードを書くことは、この領域では古くからの前提である。デザイナーに合わせてコードを易しくするのでなく、動機づけて任せる（S09）。

### Flash の時代（2000 年の批判から 2020 年末の配布終了予告まで）

**当時の制約**

- ブラウザ単体では豊かな動きを出せず、プラグインに頼った（整理・推測）。Adobe 自身が、のちにプラグインが先行した機能の多くを標準が提供するようになり、標準が代替になったと述べた（S28）。
- Flash の登場年は、本台帳では確認していない。2000 年には Nielsen の批判の対象として存在していた（S23）。

**応答**

- 動きのあるインタラクティブな表現を、プラグインで Web に提供した（整理・推測）。

**副作用と反動**

- Jakob Nielsen は、Flash の存在は 99% の場合、使い勝手の病であると書いた（S23。記事の日付は 2000-10-29）。批判は 3 点で、悪いデザインを誘発すること、Web の基本の操作原則を破ること、サイトの核の価値から注意をそらすこと（S165）。具体的に、動かせるから動かす誘惑（S24）と、利用者の操作の自由度を下げ、テレビのような提示に戻る失敗（S25）を挙げた。
- Steve Jobs は公開書簡で、Flash は PC とマウスの時代のもので、モバイルは低電力・タッチ・オープンな標準の時代であり、Flash はそれらに弱いと述べた（S26、S27。2010 年は報道による）。Apple の利害を含む主張で、Adobe が反論したと報じられている（報道の要約による。反論の原文は未取得）。
- Adobe は、WebGL を含む標準が代替として成熟したと述べ（S28）、Flash Player の更新と配布を 2020 年末に止めると予告した（S29）。

**今の判断への示唆（整理・推測）**

- Flash への批判（動かせるから動かす・操作の自由を奪う・ホバー前提）は、WebGL の没入型サイトにも同じ形で戻りうる。批判は技術でなく設計の失敗に向けられている。
- 「標準で作る」ことは、特定の企業の都合から離れる利点があるが、標準の API だけで体験の質が保証されるわけではない。

### 2009 年から 2011 年: ブラウザが GPU を持つ

**当時の制約**

- Chrome Experiments は、JavaScript と HTML5 の限界を押し広げる作り手の作品を集める場として、2009 年に始まった。開始時は 19 作品だった（S17、S18）。初期の寄稿者に Casey Reas と Ricardo Cabello（Mr.doob）が含まれる（S21、区分 R）。

**応答**

- three.js の最初の公開版は 2010-04-24 のコミットである（S22）。
- WebGL 1.0 は、2011-03-03 に Khronos がプラグイン無しの HTML5 ブラウザ向けの仕様として公開した（S31。定義は S33）。Chrome Experiments の運営側は、WebGL が Chrome に入った 2011 年に、WebGL の実験が増えたと述べる（S19）。

**副作用と反動**

- Khronos は後年、オンライン配備の悩みはブラウザの種類・版・GPU の組み合わせが膨大なことだと述べる（S156）。端末差の問題は、WebGL の登場後も残った（整理・推測。three.js のマニュアルが、今も WebGL 2 を使えない端末や環境がありうると述べる。S62）。
- Chrome Experiments の開始日は、Google の告知記事が 2009-03-18（S20、区分 R）、Wikipedia が 2009-03-01（S145、区分 R）と食い違う。

**今の判断への示唆（整理・推測）**

- 「驚き」の技術を出す場所は、最初は実験場で、製品の本線ではなかった。今も、実験と製品のどちらに置くかを先に決める。

### 2017 年から 2022 年: WebGL 2 の普及と Flash の終了

**当時の制約**

- WebGL 2.0 は 2017 年に初めて出荷された（S146）。全主要ブラウザの対応は、Safari 15（macOS と iOS）が入って揃った（S32。記事は 2022-02-09）。iPhone が長く WebGL 2 を欠いたことが普及の壁だった（整理・推測。出典は、Safari 15 で揃ったと述べるのみ）。

**応答**

- インスタンス描画・複数のレンダーターゲット・一様バッファなど、より多くの機能が標準で使えるようになった（S157）。
- Adobe は Flash Player の更新・配布を 2020 年末に止めると予告した（S29。予告の確認で、実際の終了の確認は本台帳では取っていない）。

**副作用と反動**

- 点滅（WCAG 2.3.1・レベル A。S118）、自動で動き続ける内容の停止手段（2.2.2・レベル A。S121）、操作で起きる動きの無効化（2.3.3・レベル AAA。S119）の基準が、Web の動きに適用される。
- 動きへの配慮は、iOS 7 で視差とアプリ起動のアニメーションを無効にする設定が加わった（S153）。prefers-reduced-motion は、2014 年に CSS ワーキンググループへ提案された（S154）。Val Head の記事（S128）と、WebKit の対応告知（S126）が続く。順序は出典の日付による（因果の主張は含まない）。

**今の判断への示唆（整理・推測）**

- 動きの配慮は WebGL のために作られた規則ではないが、シェーダーの動きにも同様に適用される。本 skill は、いつ止めるか・何に置き換えるかの判断（代替表示）を担当し、動きの設計自体は designer-interaction（導入されていれば）に任せる。

### 2022 年から 2026 年: 制作の工程の公開と WebGPU

**当時の制約**

- 受賞級の作品は、3D 素材・音・撮影が必要で、コードだけでは作れない。Messenger は 2 人のチームで（S81）、モデリングを手作業で数週間かけ（S164）、Houdini と Blender で 3D を作った（S80）。Bruno は 1 年強かけた（S85）。Lusion の Oryzo は 1 年がかりの社内企画で（S109）、購入した 3D スキャンも使った（S108）。iyO の事例では、製品の CAD をそのまま出せず、リトポロジー・ベイク・Draco 圧縮を要した（S113）。
- メモリ制約は厳しい。iPhone の Safari は、メモリを使いすぎるとページを警告なしに終了する（S76）。

**応答**

- 制作の裏側が公開された。灰色のモックと previs で合意を作り（S96、S97）、ブラウザでコードと 3D を同時に作り、性能を測り続ける（S98、S99）。
- 性能は設計の制約として扱われる（S86）。自動で品質を落とす設計は、2016 年の記事にもある（S114）。
- WebGPU が Chrome・Edge・Firefox・Safari で対応した（S34）。仕様の文書状態は、2026-09-15 の Candidate Recommendation Draft（S37）。three.js は WebGPU 非対応端末で WebGL 2 に代替できる（S38）が、WebGPURenderer は実験段階との記述がある（S39）。

**副作用と反動**

- 評価と実装のずれ: Awwwards の Lacoste Polo Factory の審査表では、Animations / Transitions が 9.20、Accessibility が 6.00 だった（S136）。Zurb Radar は、動きと読み上げの可否のあいだの差を論じた（区分 C。S138）。
- 賞の評価基準への批判は、Roselli が書いている（区分 C。S133、S134）。Awwwards の評価ページの配点の項目名は、Design・Usability・Creativity・Content で、アクセシビリティの項目は無い（S137）。Lacoste の審査表の採点項目には、Accessibility がある（S136）。
- UI まで WebGL で描く選択が、受賞作で見られる（S77、S93、S94、S103）が、記事はその代償を述べていない。Awwwards は Developer Award の紹介で、デバイスやブラウザを問わず、すべての人に開かれていることを掲げる（S135）。canvas の中に文章を置くと読み上げが読めない、という開発者の指摘がある（区分 C。S131）。
- 重さへの批判（区分 C。S140）は、文章中心のサイトの肥大化に向けたもので、実験的な作品は射程の外と著者自身が断っている。WebGL 作品への批判として引かない。
- Messenger の Developer Site of the Year（S83）は、掲載ページに年の記載が無い。

**今の判断への示唆（整理・推測）**

- 受賞作は「素材の工程・時間・チーム」の産物で、コードの技法だけを真似ても再現できない。本 skill の到達点は、手続き的な形状とシェーダーまで（Bruno の草や Neve のノイズ背景の水準。S87、S116）である。
- 評価の高い作品が、アクセシビリティの低さを抱えたまま称賛されている構図がある（S136、S138。区分 C を含む。一般化しない）。本 skill は、代替表示と動きの配慮を最初から設計に含める。
- 対応状況（WebGPU・import map の integrity・Device Memory）は時点情報である。実装前に最新の互換表を確認する。
