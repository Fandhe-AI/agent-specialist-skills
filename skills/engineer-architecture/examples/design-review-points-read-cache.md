# 例: 他者の設計案をレビューして返す（読み取りのキャッシュ層）

架空の社内ポイント制度の設計書が、読み取りのキャッシュ層を足す案を出している。それを、レビュー観点チェックリストの項目で判定し、返答にまとめる例。返答の文面と、判定表を載せる。題材は架空の事業者・数値で、実在の製品・企業を写さない。他の人の設計書を見てほしいと頼まれたとき、または、自分の案を出す前に点検するときに開く。項目の全文は [レビュー観点チェックリスト](../references/review-checklist.md) にある。

## 依頼

- 事業者: 架空の「ひまわり商事」。社員 3,000 人向けの社内ポイント制度「ひまわりポイント」を運用している（架空の前提）
- 設計書の案: 残高と履歴の読み取りが多いので、読み取りの API の前に共有のキャッシュ層を置く。キャッシュの保持期間は 60 秒（架空の前提）。ポイントを付ける・使うときは、キャッシュを無効にする
- 設計書に書かれていること: 開発者は 4 人。期限は来期の開始まで。決めることの一文は「読み取りの経路にキャッシュ層を置くか」。動機は「残高の画面が遅い」。品質の目標は「速くする」で止まっていて、値が無い。構成図が 1 枚。代案・計測の結果は、書かれていない
- 依頼文: 「この設計書をレビューして、問題が無ければ進めたい」

## 目的の一文

設計書の案を、チェックリストの項目で判定し、足りない点と、確かめるべき計測を、誰がいつ測るかまで含めて返す。

## 削るもの

| 削るもの | 理由と削り方 |
|---|---|
| 案を作り直した別の設計 | 返すのは判定と、足りない点。作り直しは、設計書の筆者と決める |
| キャッシュ製品の比較と、性能の数字 | 実測が無い。製品の優劣は、ここでは判定しない（本 skill の整理） |
| キャッシュを一律に退ける助言 | 採る条件と採らない条件を書く。一律には求めも退けもしない（本 skill の整理） |
| 無効化の実装の細部 | 設計書に無い。必要なら、利用（ポイントを使う）の判定が古い残高で行われないかを、確認事項として返す（本 skill の整理） |
| 他社の事例 | 規模と処理の性質が違う。設計書も事例を根拠にしていない |

## 構成

```text
設計書を読む → チェックリストの全項目に、はい / いいえ / 不明 / 該当なし を付ける
→ いいえと不明を、改善案か確認事項に結びつける → 結論を先に書いて返す
→ 相談者が計測や記録を示したら、不明をはい・いいえに改める
```

- 順序: 特に落ちやすい群（決めることと制約・構成の選択・決定の記録）から返す
- 実測が要る項目は、証拠が無ければ「不明」とし、何を・誰が・いつ測るかを返す。計画があることを理由に、結果の項目を「はい」にしない

## 仕様

出典のある値には S 番号を付ける。それ以外は本 skill の整理で、規格の要件ではない。

| 項目 | 値 | 根拠 |
|---|---|---|
| 判定の種類 | はい / いいえ / 不明 / 該当なし | 本 skill の整理（チェックリストの「判定の付け方」） |
| 判定表の行 | チェックリストの項目に対応させ、項目を足さない | 本 skill の整理 |
| 品質の目標 | 場面と値で書く | S047 は、重要な品質を、具体的・測定可能に把握することを述べる。場面と値の形は本 skill の整理 |
| 図の更新 | 更新する人と時期を決める | S027 は、小さな文書には少なくとも更新される見込みがあると述べる（S027 は文書についての記述で、図についてではない）。担当と時期を決めるのは本 skill の整理 |
| キャッシュを採る条件 | 読み取りが遅さの主因だという計測がある。残高の古さの許容を、事業側が決めている。古さの上限を、競合・無効化の失敗を含めて確かめている | 本 skill の整理。効果と整合性の影響は、推測 |
| 実測の担当と時期 | 返答の中で、人と時期を挙げる。値は架空の前提 | 本 skill の整理 |

## 文言

### レビューの返答

> 結論: いまの設計書のままでは、進めることを勧めません。キャッシュ層を足すこと自体を退けるのではありません。採る条件（読み取りが遅さの主因だという計測と、残高の古さの許容を事業側が決めていること）の証拠が、設計書に無いためです。
>
> 判定の内訳: いいえ 12、不明 3、はい 2、該当なし 19（全 36 項目。表は下）。
>
> 先に直す点: (1) 目標が「速くする」で止まっています。場面と値（例: 月末のピークに、残高の画面を 95% 1 秒以内。架空の値）で書いてください。得るもの: 達成を判定できる。失うもの: 値を事業側と決める調整の手間。(2) 得るものだけが書かれています。残高の古さと、ポイントを使う判定が古い残高で行われないかを、書いてください。60 秒はキャッシュの保持期間で、古さの上限ではありません（更新と読み取りが競合したり、無効化に失敗したりすると、更新から見た古さは 60 秒を超えうる。推測）。得るもの: 事業側が古さの許容を決められる。失うもの: 設計書が長くなり、決める事項が増える。(3) 代案（問い合わせの見直し・索引など）と切り替える合図が無いので、並べて比べてください。得るもの: キャッシュが主因への最小の手段か分かる。失うもの: 比べる手間と、着手の遅れ。
>
> 確かめること（不明の項目）: 設計書の筆者が、直近 4 週間の読み取りの回数、時間帯別のピーク時の負荷の変化、経路別（画面・API・DB）のデータの受け渡し量、画面の遅さの内訳（DB・アプリ・画面）を、次のレビュー会までに出してください。使い方: 読み取りが特定の時間帯や経路に偏るかで、キャッシュが要るか、どこに置くかを判断します。残高の古さの上限は、設計書の筆者が、読み取りと更新の競合・無効化の失敗を想定した試験で、更新から画面に反映されるまでの最長を、導入の前に測ってください。許容する長さは事業側が決めます。開発リーダーが、目標を決めた後に、ピークの時間帯に 1 週間、応答時間を測ってください。運用の担当が、キャッシュ層の停止を想定した試験で、DB への読み取りが集中するかを、導入の前に確かめてください。
>
> 得るものと失うもの（採る場合）: 得るもの: 読み取りが主因なら、画面が速くなる見込み。失うもの: 残高が古く見える時間（上限は未確認）。運用の対象が 1 つ増える。効果は、ここでは測っていません（推測）。
>
> 確かめられないこと: 遅さの原因と、キャッシュの効果は、設計書にも、ここにも計測がありません。判定は、設計書の文面だけに基づきます。

## コード断片

判定表（抜粋でなく、全 36 項目。項目名は短くした。根拠は本 skill の整理）。

```text
項目 | 判定 | 理由・返すこと
決めることの一文 | はい | 「読み取りの経路にキャッシュ層を置くか」と書かれている
変えにくい部分の特定 | いいえ | 書かれていない。キャッシュ層が変えにくいかを書く
人数・期限・運用の体力 | いいえ | 人数と期限はある。キャッシュの運用の体力の記述が無い。運用の担当と、対応できる範囲を書く
捨てる前提か | いいえ | 書かれていない。長く使うか、数年で捨てるかを書く
境界を引く案の隠し方 | 該当なし | 境界を引く案ではない
業務の言葉の境界 | 該当なし | 同上
依存の向きの規則 | 該当なし | 規則を採っていない
翻訳の層 | 該当なし | 旧系・外部のモデルと接していない
チームの境界の表 | 該当なし | 境界を決める案ではない
得るものと失うもの | いいえ | 得るものだけ。残高の古さを失うものに書く

技術選定の理由 | はい | 理由は課題（画面が遅い）で、流行を挙げていない
```

## 初見検証

新しく入った開発者と設計書の筆者が、返答だけで、判定の理由と次にすることを言えるかを確かめる。

| 読む人 | 返答だけで言えること | 言えないときの直し方 |
|---|---|---|
| 設計書の筆者 | 進めない理由が、キャッシュの否定でなく、採る条件の証拠の不足だと言える | 結論に、採る条件を 1 文で置く |
| 設計書の筆者 | 先に直す 3 点と、不明の項目で誰がいつ何を測るかを言える | 返答に、人・時期・測る内容を対応させて書く |
| 事業側の担当 | 残高の古さの許容を、自分が決める事項だと言える | 失うものの文に、古さの許容の長さと、決める人を書く。保持期間と上限を分ける |
| 新しく入った開発者 | 「はい」でなく「不明」とした項目の理由を言える | 判定表の理由に、足りない証拠を書く |

## 点検

- 判定表が、チェックリストの項目に対応し、項目を足していない
- 実測が要る項目に、証拠が無いまま「はい」を付けていない。計画が無いことと、結果が無いことが分けられている
- 不明の項目ごとに、何を・誰が・いつ測るかが返されている
- 該当なしの項目に、理由が付いている。「いいえ」の項目に、改善案が付いている
- キャッシュを一律に退けず、採る条件と、得るものと失うものが書かれている
- 品質の目標が、場面と値で書かれている（S047 は、具体的・測定可能に把握することを述べる。場面と値の形は本 skill の整理）
- 効果と整合性への影響が、推測と書かれ、実測した値として扱われていない
- 数値（人数・期間・目標値）が、架空の前提と明記されている
- 推測の明示: 遅さの原因・キャッシュの効果・社内の体制は、設計書とここでは確かめられない。相談者のデータが要る
