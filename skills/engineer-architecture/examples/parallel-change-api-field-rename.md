# 例: 公開 API の項目名の変更を、拡張・移行・縮小で進める

架空の宿泊予約サービスの公開 API が、レスポンスの項目名を変える例。旧版の利用側を止められないので、新旧の項目を両方返す期間を置き、条件を満たしてから旧項目を外す。相談への返答の文面と、移行期間のレスポンス、告知の文面を載せる。題材は架空の事業者・数値で、実在の製品・企業を写さない。「公開 API の項目名を直したい。使っている側に影響が出ないか」という相談を受けたときに開く。

## 依頼

- 事業者: 架空の宿泊予約「やどりぎ予約」。開発者は 5 人（架空の前提）
- 対象: 予約の取得 API のレスポンスの項目 `price`。税込の合計金額なのに、税抜と読まれる問い合わせが多く、`total_price_with_tax` に改名したい（値の意味は変えない）
- 利用側（架空の前提）: 連携先の旅行比較サイトなど 12 社。各社の配備の時期は、こちらでは決められない。契約上、旧版の API は、拡張開始の告知から 6 か月以上は使えると案内している
- 契約の前提（架空）: API の契約が、利用側に「未知の項目は無視する」ことを求めている。連携先ごとの呼び出し経路（四半期のバッチなど頻度の低いものを含む）は契約の台帳に載っていて、台帳の全経路で、そのことを結合試験で確かめた記録がある。したがって、拡張の時点で新旧の両方を返しても壊れない前提である
- キャッシュの前提（架空）: この API の応答は、共有キャッシュに載せない（キャッシュしない設定で配信し、間に共有キャッシュを置かない）。この前提が崩れたときは、認証と応答の形でキャッシュを分ける
- 依頼文: 「項目名を直したいが、連携先が壊れるのは困る。いつ旧項目を消してよいか決めたい」

## 目的の一文

レスポンスの項目名を変えても、連携先が壊れないように、新旧を併存させる期間を置き、旧項目を外す条件を、判定できる形で決める。

## 削るもの

| 削るもの | 理由と削り方 |
|---|---|
| 項目の値や型の同時の変更 | 名前だけを変える。値の意味も変えると、移行の確認が 2 つの軸になる（本 skill の整理）。値の変更は別の変更にする |
| API の版を新しく切ること | この変更だけのために、版を増やさない。版を切るかは別の判断（本 skill の整理） |
| 連携先の分類・要求ごとの指定・利用の割合の計測 | 契約の前提（未知の項目を無視する）で、拡張時に壊れない。応答は 1 通りにする。前提が崩れた場合は、下の「前提が崩れた場合」 |
| 旧項目の即時の削除 | 旧版の利用側を止められないので、削除は縮小の相で、条件を満たしたときだけ行う |
| 他の項目の整理 | 1 回の変更に 1 つの改名だけを入れる（本 skill の整理） |

## 構成

```text
拡張: 新項目を足し、旧項目は残す（新旧は同じ値）→ 告知する
移行: 連携先が新項目へ移る
縮小: 条件を満たし、承認されたら、旧項目を外す。条件に届かなければ、縮小に進まず、再評価する
```

- 3 つの相は、順に進める。前の相の完了の条件に当たるまで、次の相へ進まない
- 拡張から移行へ進む完了の条件: 新旧が同値であることの試験が通り、告知が出ている
- 移行から縮小へ進む条件は、仕様の「縮小に進む条件」
- 旧版の利用側を止められず、新旧を併存させる必要がある前提のときの手順である

### 同時に切り替えられる場合

次の (a) または (b) が成り立ち、かつ (c) が成り立つときは、3 つの相に分けず、1 回の変更で切り替えてよい（本 skill の整理。本 skill 本文の「直接の移行で足りることもある」と、チェックリストの条件に揃えた）。

- (a) 利用側を止められる系である。止めている間に、すべての利用側を切り替え、再開の前に動作を確かめられる（本 skill 本文とチェックリストの「止められる系」を、この例はこの意味で読む。本 skill の整理）
- (b) 利用側が 1 つで、同時に配備できる
- (c) 変更を戻す方法（旧の版へ戻す手順）が、切り替えの前に確かめられている

どちらも成り立たない、または (c) が確かめられないときは、3 つの相に分ける。

### 前提が崩れた場合

未知の項目を拒む経路が見つかった場合は、この例の範囲の外とする。その経路には、明示の指定で応答の形式を選ばせる設計を別に考える（本 skill の整理）。

## 仕様

出典のある値には S 番号を付ける。それ以外は本 skill の整理で、規格の要件ではない。数値と日数はすべて架空の前提で、実際は相談者の事情で決める。

| 項目 | 値 | 根拠 |
|---|---|---|
| 3 つの相 | 拡張・移行・縮小に分ける | S083 は、後方互換のない変更を、拡張・移行・縮小の 3 つの段階に分けるパターンと述べる。この引用が言うのはそこまで。各相の中身は本 skill の整理 |
| 約束していない挙動への依存 | 利用者が十分に多いとき、観測できる挙動は誰かに当てにされる。値の形式・並び・欠落の扱いへの依存は、縮小前の試験で見る | S101 は、API の利用者が十分に多いと、契約で何を約束しても、観測できる挙動は誰かに当てにされると述べる。12 社が「十分に多い」に当たるかは、引用からは言えない（本 skill の整理） |

応答（この例の設定）:

| 時期 | 応答 |
|---|---|
| 拡張・移行の相 | 新旧の両方（`price` と `total_price_with_tax`。同じ値） |
| 縮小後 | 新項目だけ |
| 縮小後の切り戻し | 新旧の両方（全員が未知の項目を無視するので安全）。切り戻した後は、拡張・移行の相と同じ応答を確かめる |

### 縮小に進む条件（本 skill の整理）

3 つのすべてを満たす。1 つでも満たさなければ、縮小に進まず、まず再評価する（連携先への連絡・期間の延長・条件の見直し）。

| 条件 | 確かめ方 | 比べる基準 | 担当・時期 |
|---|---|---|---|
| 縮小後の応答の確認 | 台帳の全経路ごとに、試験環境で縮小後の応答（新項目だけ）を返し、実際のクライアントで処理できることを確かめる。値の形式・並び・欠落の扱いへの依存も、この試験と各社への聞き取りで見る | 台帳の全経路で、処理できると試験で確かめられている、または経路の廃止が確認されている。1 つでも済んでいない経路があれば、縮小しない | 連携の窓口と開発リーダー。縮小の判断の前 |
| 契約上の期間 | 契約が定める旧版の利用可能な期間を確かめる | 拡張開始の告知の日から 6 か月（架空）が過ぎている。実際の案件では、契約と告知の両方を満たす日が下限 | 連携の窓口。縮小の判断の前 |
| 承認 | 承認者が、上の 2 つの結果を見て承認する | 開発リーダーと連携の窓口の責任者が承認している。旧項目を外す決定は、再評価の後、承認されてから実行する | 6 か月目の後、1 か月以内（架空） |

### 移行で確かめる問い（本 skill の整理）

| 問い | この例での答え |
|---|---|
| 段階ごとに、書き込み（または要求）をどちらで受けるか | 該当なし。読み取りの項目名の変更で、要求の受け先は変わらない |
| 切り替えの前に、既存データの写しを旧系と照合できるか | 該当なし。データの写しは作らない。新旧の項目が同じ値かを、応答の試験で照合する |
| 書き込みの権限の引き継ぎ | 該当なし。書き込み先は変わらない |
| 認可が、どの経路でも同じく働くか | 認可は項目名と無関係。縮小後の応答でも、認可の結果が変わらないことを、試験で確かめる |
| 切り戻すとき、旧が残っているか | 応答の表のとおり。外した後も 1 か月（架空）、切り戻せる状態を残す |
| 旧を外す条件 | 縮小に進む条件の 3 つ |

## 文言

### 相談への返答

> 結論: 新項目 `total_price_with_tax` を足して旧項目 `price` を残す期間を置き、条件を満たしてから旧項目を外す、拡張・移行・縮小の 3 つの相を勧めます。
>
> 置いた仮定（架空の前提）: 連携先は 12 社で、各社の配備の時期は決められない。契約が「未知の項目は無視する」ことを求め、台帳の全経路で結合試験の記録がある。旧版は 6 か月以上使える契約になっている。値の意味は変えず、名前だけを変える。
>
> 選ぶ条件: 旧版の利用側を止められず、新旧を併存させる必要があるときに、この 3 つの相を選びます。止められる系、または利用側が 1 つで同時に配備できる場合は、戻す方法が確かめられていれば、1 回の変更で足ります。
>
> 失うもの: 移行の期間中、新旧の項目を両方返す手間がかかります。縮小の前に、台帳の全経路を試験する手間がかかります。
>
> 切り替える合図: 縮小に進む条件のどれかが満たされないときは、縮小に進まず、まず再評価します。旧項目を外す決定は、承認されてからです。未知の項目を拒む経路が見つかったときは、この計画の範囲の外で、その経路の設計を別に考えます。
>
> 確かめられないこと: 各連携先が実際にどの項目を読んでいるかは、こちらからは見えません。台帳の試験の結果は、ここでは出ていません。期間と連携先の数は、実際の契約で決めてください。

## コード断片

拡張・移行の相のレスポンス。新旧は同じ値を返す。

```json
{
  "booking_id": "B-20260001",
  "status": "confirmed",
  "price": 18700,
  "total_price_with_tax": 18700,
  "currency": "JPY"
}
```

縮小後のレスポンス。

```json
{
  "booking_id": "B-20260001",
  "status": "confirmed",
  "total_price_with_tax": 18700,
  "currency": "JPY"
}
```

告知の文面（架空。1 段。期日は、契約が定める期間に合わせて、拡張の開始日からの相対で決める）。

```text
件名: 予約取得 API の項目名の変更のお知らせ

予約取得 API のレスポンスの項目 price は、total_price_with_tax へ名前を変えます。
値の意味は変わりません（税込の合計金額）。

- 本日から: 両方の項目を同じ値で返します。契約のとおり、未知の項目は無視してください。
- 本日から 6 か月の間: 新しい項目への切り替えをお願いします。
- 本日から 6 か月後以降: 切り替えの状況を確認したうえで、price を外します。外す日は、
  事前に改めてお知らせします。

price の値の形式や項目の並びなど、仕様に書いていない動作に頼っている場合は、
当社の連携の窓口へご相談ください（宛先は、実際の告知に記載する）。
```

## 初見検証

新しく入った開発者や連携先の担当者が、記録だけで進め方の理由と条件を言えるかを確かめる。

| 読む人 | 記録だけで言えること | 言えないときの直し方 |
|---|---|---|
| 新しく入った開発者 | 旧項目をすぐに消さない理由を、「旧版の利用側を止められないから」と言える | 構成に、前提を 1 文で置く |
| 新しく入った開発者 | 旧項目を外す条件が、3 つ（台帳の全経路の試験・契約上の期間・承認）だと言える | 縮小に進む条件の表に、確かめ方・基準・担当・時期を書く |
| 連携先の担当者 | いつまでに何をすればよいかと、困ったときの連絡先を言える | 告知の文面に、期日と連絡の方法を足す |
| 連携の窓口 | 条件に届かないとき、まず何をするかを言える | 条件に届かないときは再評価、と書く |
| 前提が崩れた経路の担当 | この例の範囲の外で、別の設計が要ることを言える | 「前提が崩れた場合」を示す |

## 点検

- 名前だけの変更で、値の意味が変わっていない
- 契約の前提（未知の項目を無視する・台帳の全経路の結合試験の記録）が、依頼に書かれている
- 3 つの相が、順に並び、各相の完了の条件がある（S083 は、3 つの段階に分けることを述べる。各相の中身は本 skill の整理）
- 縮小に進む条件が 3 つで、確かめ方・基準・担当・時期が対応している。台帳の全経路が対象で、済んでいない経路が 1 つでもあれば縮小しない
- 条件に届かないとき、縮小に進まず、まず再評価する。外す決定は、承認の後
- 応答が表で定義され、拡張・縮小後・切り戻しの 3 通りだけで、告知・JSON 例・仕様が揃っている
- 約束していない挙動への依存の確認が、縮小前の試験と聞き取りに入っている。「利用者が十分に多いとき」という限定が、落ちていない（S101）
- 同時に切り替えられる場合の条件が、本 skill 本文とチェックリストに揃えて書かれ、3 つの相を一律に求めていない
- 前提が崩れた場合が、この例の範囲の外と書かれている
- 期間・連携先の数・基準の数値が、架空の前提と明記されている
- 推測の明示: 連携先の実際の動作と、契約上の期間、台帳の試験の結果は、相談者の確認が要る
