# 例: 公開 API の項目名の変更を、拡張・移行・縮小で進める

架空の宿泊予約サービスの公開 API が、レスポンスの項目名を変える例。旧版の利用側を止められないので、新旧の項目を両方返す期間を置き、利用の測定で旧項目を外す。相談への返答の文面と、移行期間のレスポンス、廃止の告知の文面を載せる。題材は架空の事業者・数値で、実在の製品・企業を写さない。「公開 API の項目名を直したい。使っている側に影響が出ないか」という相談を受けたときに開く。

## 依頼

- 事業者: 架空の宿泊予約「やどりぎ予約」。開発者は 5 人（架空の前提）
- 対象: 予約の取得 API のレスポンスの項目 `price`。税込の合計金額なのに、税抜と読まれる問い合わせが多く、`total_price_with_tax` に改名したい（値の意味は変えない）
- 利用側（架空の前提）: 連携先の旅行比較サイトなど 12 社。各社の配備の時期は、こちらでは決められない。契約上、旧版の API は、告知から 6 か月以上は使えると案内している（架空の前提）
- 依頼文: 「項目名を直したいが、連携先が壊れるのは困る。いつ旧項目を消してよいか決めたい」

## 目的の一文

レスポンスの項目名を変えても、連携先が壊れないように、新旧を併存させる期間を置き、旧項目を外す条件を、測れる値で決める。

## 削るもの

| 削るもの | 理由と削り方 |
|---|---|
| 項目の値や型の同時の変更 | 名前だけを変える。値の意味も変えると、移行の確認が 2 つの軸になる（本 skill の整理）。値の変更は別の変更にする |
| API の版を新しく切ること | この変更だけのために、版を増やさない。版を切るかは別の判断（本 skill の整理）。新旧の項目を同じ版に併存させる |
| 旧項目の即時の削除 | 旧版の利用側を止められないので、削除は縮小の相で、条件を満たしたときだけ行う |
| すべての連携先の個別対応 | 告知と測定で全体を進める。移行が遅い連携先にだけ、個別に連絡する |
| 他の項目の整理 | 1 回の変更に 1 つの改名だけを入れる。ほかの改名は、同じ手順で別に行う（本 skill の整理） |

## 構成

```text
拡張: 新項目を足し、旧項目は残す（新旧は同じ値）→ 告知する
移行: 連携先が新項目へ移る。利用の測定で、進み具合を見る
縮小: 条件を満たし、承認されたら、旧項目を外す。条件に届かなければ、縮小に進まず、再評価する
```

- 3 つの相は、順に進める。前の相の完了の条件に当たるまで、次の相へ進まない
- 拡張から移行へ進む完了の条件: 新旧が同値であることの試験が通り、告知が出ている。移行から縮小へ進む条件は、仕様の「縮小に進む条件」
- 旧版の利用側を止められず、新旧を併存させる必要がある前提のときの手順である。次の「同時に切り替えられる場合」は、3 つの相が要らない

### 同時に切り替えられる場合

次の (a) または (b) が成り立ち、かつ (c) が成り立つときは、3 つの相に分けず、1 回の変更で切り替えてよい（本 skill の整理。本 skill 本文の「直接の移行で足りることもある」と、チェックリストの条件に揃えた）。

- (a) 利用側を止められる系である
- (b) 利用側が 1 つで、同時に配備できる（例: 自社のアプリだけが使っていて、API と同時に出せる）
- (c) 変更を戻す方法（旧の版へ戻す手順）が、切り替えの前に確かめられている

どちらも成り立たない、または (c) が確かめられないときは、3 つの相に分ける。

## 仕様

出典のある値には S 番号を付ける。「目安」は本 skill の目安で、規格の要件ではない。数値と日数はすべて架空の前提で、実際は相談者の事情で決める。

| 項目 | 値 | 根拠 |
|---|---|---|
| 3 つの相 | 拡張・移行・縮小に分ける | S083 は、後方互換のない変更を、拡張・移行・縮小の 3 つの段階に分けるパターンと述べる。この引用が言うのはそこまで。各相の中身は本 skill の整理 |
| 拡張の相 | 新項目を足し、旧項目は同じ値で返す。告知を出す | 本 skill の整理 |
| 移行の相の期間 | 告知から 6 か月（架空の前提）。告知の期日は、契約が定める期間に合わせて決める | 目安 |
| 縮小に進む条件 | 下の 4 つを満たす | 本 skill の整理 |
| 約束していない挙動への依存 | 利用側が十分に多いとき、観測できる挙動は誰かに当てにされる | S101 は、API の利用者が十分に多いと、契約で何を約束しても、観測できる挙動は誰かに当てにされると述べる。12 社が「十分に多い」に当たるかは、引用からは言えない。聞き取りで確かめる（本 skill の整理） |
| 縮小の後 | 旧項目を外す。外した後も一定期間、旧項目を戻す設定を残す（架空の前提: 1 か月） | 本 skill の整理 |

### 縮小に進む条件（本 skill の整理）

レスポンスの項目を、利用側が読んだかは、サーバーからは見えない。サーバーで測れる信号と、利用側の申告を組み合わせる。

| 条件 | 確かめ方 | 比べる基準 | 担当・時期 |
|---|---|---|---|
| 旧項目を返さない指定での要求 | 要求に「旧項目を返さない」指定を足せるようにする。指定つきの要求の有無を、連携先ごとにログで数える | 12 社のすべてで、直近 4 週間の要求のうち 95% 以上が指定つきで、応答の成功率が通常の要求と同じ（架空の基準。試験の 1 回でなく、本番の移行を示す） | 連携の窓口が、移行の相の 4 か月目と 6 か月目に集計する |
| 利用側の申告 | 各社に、新項目への移行が済んだかを問い合わせ、返答を記録する | 12 社すべてが、書面（メールなど）で済んだと返す | 連携の窓口が、告知の 1 か月後から毎月 |
| 約束していない挙動への依存 | 旧項目の値の形式・並び・欠落の扱いに依存していないかを、各社に聞き取る。指定つきの要求で、各社の動作が変わらないかを見る | 依存が見つかった連携先は、個別に対応し、解消の確認が取れてから | 開発リーダーが、移行の相の 5 か月目まで |
| 契約上の期間 | 契約が定める旧版の利用可能な期間を確かめる | 期間（架空: 告知から 6 か月）が過ぎている | 連携の窓口が、縮小の判断の前に契約を確認する |

4 つのうち 1 つでも満たさなければ、縮小に進まない。まず原因を再評価する（連携先への個別の連絡・期間の延長・条件の見直し）。旧項目を外す決定は、再評価の後、承認されてから実行する。承認するのは開発リーダーと連携の窓口の責任者で、6 か月目の集計の後、1 か月以内に判断する（架空の前提）。

### 移行で確かめる問い（本 skill の整理）

| 問い | この例での答え |
|---|---|
| 段階ごとに、書き込み（または要求）をどちらで受けるか | 該当なし。読み取りの項目名の変更で、要求の受け先は変わらない |
| 切り替えの前に、既存データの写しを旧系と照合できるか | 該当なし。データの写しは作らない。新旧の項目が同じ値かを、応答の試験で照合する |
| 書き込みの権限の引き継ぎ | 該当なし。書き込み先は変わらない |
| 認可が、どの経路でも同じく働くか | 旧項目を返さない指定でも、認可の結果が変わらないことを、試験で確かめる |
| 切り戻すとき、旧が残っているか | 旧項目を返す設定を、外した後も 1 か月残す |
| 旧を外す条件 | 縮小に進む条件の 4 つ（利用の測定と契約上の期間を含む） |

## 文言

### 相談への返答

> 結論: 新項目 `total_price_with_tax` を足して旧項目 `price` を残す期間を置き、利用の測定で条件を満たしてから旧項目を外す、拡張・移行・縮小の 3 つの相を勧めます。
>
> 置いた仮定（架空の前提）: 連携先は 12 社で、各社の配備の時期は決められない。旧版は一定期間使える契約になっている。値の意味は変えず、名前だけを変える。
>
> 選ぶ条件: 旧版の利用側を止められず、新旧を併存させる必要があるときに、この 3 つの相を選びます。止められる系、または利用側が 1 つで同時に配備できる場合は、戻す方法が確かめられていれば、1 回の変更で足ります。
>
> 失うもの: 移行の期間中、新旧の項目を両方返し、両方を保つ手間がかかります。連携先への連絡と、利用の集計にも手間がかかります。
>
> 切り替える合図: 縮小に進む条件のどれかが満たされないときは、縮小に進まず、まず再評価します。連携先の個別の連絡・期間の延長・条件の見直しを比べます。旧項目を外す決定は、承認されてからです。
>
> 確かめられないこと: 各連携先が実際にどの項目を読んでいるかは、こちらからは見えません。約束していない挙動に依存した連携先があるかは、聞き取りと試験の結果が出るまで分かりません。期間と連携先の数は、実際の契約で決めてください。

## コード断片

移行期間（拡張と移行の相）のレスポンス。新旧は同じ値を返す。

```json
{
  "booking_id": "B-20260001",
  "status": "confirmed",
  "price": 18700,
  "total_price_with_tax": 18700,
  "currency": "JPY"
}
```

「旧項目を返さない」指定をつけた要求の応答（移行の相の測定用）。

```json
{
  "booking_id": "B-20260001",
  "status": "confirmed",
  "total_price_with_tax": 18700,
  "currency": "JPY"
}
```

廃止の告知の文面（架空。期日は告知の日からの相対で書く）。

```text
件名: 予約取得 API の項目名の変更のお知らせ

予約取得 API のレスポンスの項目 price は、total_price_with_tax へ名前を変えます。
値の意味は変わりません（税込の合計金額）。

- 本日から: 両方の項目を返します。
- 本日から 6 か月の間: 新しい項目への切り替えをお願いします。確認のため、
  要求に legacy_fields=off を付けると、price を返さない応答で確認できます（架空の指定）。切り替えが済んだら、当社の連携の窓口へご連絡ください（宛先は、実際の告知に記載する）。
- 6 か月後以降: 切り替えの状況を確認したうえで、price を外します。外す日は、
  事前に改めてお知らせします。

price の値の形式や項目の並びなど、仕様に書いていない動作に頼っている場合は、
ご相談ください。
```

## 初見検証

新しく入った開発者や連携先の担当者が、記録だけで進め方の理由と条件を言えるかを確かめる。

| 読む人 | 記録だけで言えること | 言えないときの直し方 |
|---|---|---|
| 新しく入った開発者 | 旧項目をすぐに消さない理由を、「旧版の利用側を止められないから」と言える | 構成に、前提を 1 文で置く |
| 新しく入った開発者 | 旧項目を外す条件が、4 つ（利用の測定 2 つ・聞き取り・契約上の期間）だと言える | 縮小に進む条件の表に、確かめ方・基準・担当・時期を書く |
| 連携先の担当者 | いつまでに何をすればよいかと、困ったときの連絡先を言える | 告知の文面に、期日と連絡の方法を足す |
| 連携の窓口 | 条件に届かないとき、まず何をするかを言える | 条件に届かないときは再評価、と書く |
| 自社アプリだけが使う別の API の担当 | 3 つの相が要らない条件を言える | 「同時に切り替えられる場合」の条件を示す |

## 点検

- 名前だけの変更で、値の意味が変わっていない
- 3 つの相が、順に並び、各相の完了の条件がある（拡張から移行へは、新旧が同値であることの試験が通り、告知が出ていること）（S083 は、3 つの段階に分けることを述べる。各相の中身は本 skill の整理）
- 縮小に進む条件に、サーバーで測れる信号が含まれ、確かめ方・基準・担当・時期が対応している
- 条件に届かないとき、縮小に進まず、まず再評価する。外す決定は、承認の後
- 約束していない挙動への依存の確認が、聞き取りと試験として計画に入っている。「利用者が十分に多いとき」という限定が、落ちていない（S101）
- 同時に切り替えられる場合の条件が、本 skill 本文とチェックリストに揃えて書かれ、3 つの相を一律に求めていない
- 縮小の条件に、契約上の期間と、承認する人・時期が含まれている
- 移行で確かめる問い（本 skill の整理）の 6 問に、答えか、該当なしの理由が付いている
- 切り戻す方法が、旧項目を外した後も一定期間残る設定として書かれている
- 期間・連携先の数・基準の数値が、架空の前提と明記されている
- 推測の明示: 連携先の実際の動作と、契約上の期間は、相談者の確認が要る。測定の結果は、ここでは出ていない
