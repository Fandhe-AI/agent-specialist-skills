# 例: モジュール間の依存の規則を、検査で守る

架空の会計 SaaS が、モジュール間の依存の規則を決め、CI で自動に検査する例。相談への返答の文面と、規則を表す設定、CI から検査の道具を呼ぶ契約（入出力・終了コード・道具を選ぶ条件）を載せる。import を読む自作の検査は載せない。題材は架空の事業者・数値で、実在の製品・企業を写さない。「境界を決めたが、守られているか分からない」「依存の向きが崩れていく」という相談を受けたときに開く。

## 依頼

- 事業者: 架空の会計 SaaS「つむぎ会計」。開発者は 7 人、1 つのコードベースのモジュラーモノリス（架空の前提）
- モジュール: 請求（billing）・在庫（inventory）・元帳（ledger）の 3 つ（架空の前提）
- 依頼文: 「請求の処理が在庫の内部の関数を直接呼んでいて、在庫の変更のたびに請求が壊れる。境界を決めたのに守られない。守らせる仕組みが欲しい」
- 先に確認したこと: コードは JavaScript。CI は PR ごとに動く。モジュールの公開の入口は、各ディレクトリの `index.js` にそろえられる（架空の前提）

## 目的の一文

「請求は在庫の内部を直接 import しない」を含む依存の規則を、人の注意でなく CI の検査で守り、規則を破る変更を、取り込まれる前に見つけられる状態にする。

## 削るもの

| 削るもの | 理由と削り方 |
|---|---|
| 規則の全面の整備 | 変更で実際に壊れた箇所（請求から在庫の内部）から始める。規則は 2 種類に絞る（本 skill の整理） |
| import を読む自作の検査 | 載せない。複数行・空白の有無・拡張子の省略・動的 import など、書き方の例外が多く、正規表現では抜けが残りやすい（本 skill の整理）。構文を解析する依存検査の道具を、チームが選ぶ |
| 道具の製品名 | 例に書かない。製品は変わり、選ぶのはチームである。選ぶ条件と終了コードの約束だけを書く |
| 循環・層の数式での評価 | 最初は入れない。違反の件数だけを見る。数式に見合う相談が出たら足す（本 skill の整理） |
| 性能・可用性の検査 | 別の目標で、別の検査になる。この例は構造の規則だけを扱う |
| すべての系への適用 | 依存の向きや境界の検査は、すべての系で必須とは限らない（本 skill の整理）。入れる条件と入れない条件を、下の構成に書く |

## 構成

```text
壊れた箇所を見る → 守りたい構造の目標を 1 文にする → 規則を 2 種類に絞って設定に書く
→ 構文を解析する依存検査の道具を選ぶ（確かめる条件は、コード断片）
→ 検査を CI に置く → 既存の違反の件数を数え、直してから、CI の必須の確認にする
→ 規則の見直しの担当と時期を決める
```

- 検査を入れる条件（本 skill の整理）: 境界を越える変更が実際に障害や手戻りを生んでいる。選ぶ道具が、使っている言語の import の書き方を構文として扱える。違反の数を、直せる範囲に収められる
- 入れない条件（本 skill の整理）: 数か月で捨てる系。境界がまだ仮説で、毎週引き直している間（規則の書き換えが検査より多くなる）。検査の保守の費用が、守る価値を上回る
- 検査は CI の必須の確認にする。違反があれば、非 0 の終了コードで失敗する

| 検査の頻度と担当 | PR ごとに CI。見直しは四半期ごと、開発リーダーが担当 | 本 skill の整理。この例の設定 |

見直しの対象と指標（本 skill の整理。基準は架空の前提）:

| 見直す対象 | 指標 | 基準 | 見直しの中身 |
|---|---|---|---|
| 規則・境界 | 四半期中の CI の実行（PR を含む）で `violations=` が 0 を超えた回数の推移 | 前の四半期より増えた | 規則を見直す議題に載せる |
| 規則（追加） | 規則の追加の要望の件数 | 四半期に 3 件以上 | 規則を見直す議題に載せる |
| 検査の道具 | 誤検出の報告の件数 | 四半期に 3 件以上 | 道具を比べ直す（再評価） |
| 境界（先に固める） | 規則ファイルの変更の回数 | 直近 4 週間で 3 回以上 | 検査より先に境界を固める |

## 文言

### 相談への返答

> 結論: 請求から在庫の内部への直接の依存を、設定で禁じ、CI で検査することを勧めます。まず規則は 2 種類（公開の入口だけを使う・在庫から請求へは依存しない）に絞ります。検査は、構文を解析する依存検査の道具に任せ、自作の検査は書きません。
>
> 置いた仮定（架空の前提）: 開発 7 人、モジュール 3 つ、JavaScript、各モジュールに `index.js` がある。境界を越える変更で請求が壊れた実績がある。
>
> 選ぶ条件: 変更の手戻りが実際に出ていて、選ぶ道具が、使っている言語の import の書き方を構文として扱える間は、この検査が合います。
>
> 失うもの: 規則の設定と、道具の選定・保守に手間がかかる。境界を引き直すたびに設定を直す。道具が解析できない依存は、失敗（2）になる。選ぶときに、対象コードの書き方を解析できるかを確かめる。
>
> 切り替える合図: 上の「見直しの対象と指標」の表のとおりです（基準は架空。開発リーダーが四半期の見直しで数える）。誤検出の報告が四半期に 3 件以上なら、道具を比べ直します（再評価）。違反の出た回数が増えた、または規則の追加の要望が 3 件以上なら、規則を見直します。規則ファイルが直近 4 週間で 3 回以上変わるなら、検査より先に境界を固めます。
>
> 確かめられないこと: 既存の違反の数と、検査の実行時間は、相談者のコードで測るまで分かりません。規則が実際の障害を減らすかは、ここでは検証していません。

### 検査が失敗したときに添える案内

> 違反の種類に応じて直す。内部への依存（相手のモジュールの `index.js` 以外を使っている）は、公開の入口（`index.js`）経由に直す。禁止された向きの依存（在庫から請求）は、`index.js` 経由でも禁止なので、依存の向きを変えるか、境界を見直す。直せない理由があるときは、規則か境界の見直しを、開発リーダーに相談する。

## コード断片

規則を表す設定（JSON。コメントは書けないので、意味は上の仕様に置く）。

- `deps-rules.json`

    ```json
    {
      "root": "src",
      "entry": "index.js",
      "modules": ["billing", "inventory", "ledger"],
      "forbidden": [
        { "from": "inventory", "to": "billing" }
      ]
    }
    ```

CI から呼ぶ検査の道具（チームが選ぶ）との契約。コードは載せない。環境変数 `DEP_CHECK` に、選んだ道具を契約に合わせる薄い包みを指定し、CI はその包みに規則ファイルとルートを渡して呼ぶ。

| 項目 | 契約 |
|---|---|
| 入力 | 規則ファイル（`deps-rules.json`）と、プロジェクトのルート（引数 2 つ） |
| 出力 | 標準出力に `violations=<数>` の行をちょうど 1 行。同じ出力を報告ファイル `deps-report.txt` に書く |
| 終了コード 0 | 違反なし（件数が 0） |
| 終了コード 1 | 違反あり（件数が 1 以上） |
| 終了コード 2 | 検査自体の失敗。設定の不正・対象 0 件・道具が無い・解析できない依存がある・報告ファイルの入出力のエラー・件数の行が無い、または 1 行でない・終了コードと件数の矛盾（0 なのに件数が 0 でない、1 なのに件数が 0）・0、1、2 以外の終了 |
| 失敗時の報告 | 1 や 2 で終わっても、報告ファイルがあれば成果物として残す（CI の、失敗時にも走る手順で。CI の製品名と構文は、ここでは書かない） |

道具を選ぶときに確かめる条件（本 skill の整理）:

- 複数行にまたがる import と、空白の少ない書き方を、構文として扱える
- 設定の参照先を検証する。`forbidden` の `from` と `to` が `modules` にあり、各モジュールが走査の対象になっていることを確かめ、不正なら失敗（2）にする
- シンボリックリンクの扱いが決まっていて、走査から外れるモジュールがあれば失敗にする
- 検査した対象が 0 件なら失敗にする
- 対象コードが実際に使う書き方（動的 import やパスの別名を使うなら、それも）を解析できる
- 解析できない依存が見つかったときは、失敗（2）を返す

## 初見検証

新しく入った開発者が、規則と検査の結果だけを見て、何を守ればよいかを言えるかを確かめる。

| 読む人 | 言えること | 言えないときの直し方 |
|---|---|---|
| 新しく入った開発者 | 他のモジュールの内部を直接 import せず、`index.js` を通す理由を言える | 目的の一文を規則ファイルの脇の文書に置く |
| 新しく入った開発者 | 検査が失敗したとき、何を直すか（公開の入口へ向ける）と、直せないときの相談先を言える | 失敗に添える案内の文に、直し方と相談先を書く |
| 請求の担当 | 在庫の内部が変わっても、請求が壊れない範囲を言える | 公開の入口に出す関数を、在庫の側で決めて書く |
| 開発リーダー | 規則を見直す時期と、見直しの基準（違反の件数・規則の追加の要望）を言える | 仕様の表の頻度と担当を、リーダーの作業の一覧に移す |
| 道具を選ぶ人 | 終了コード 0・1・2 の意味と、選ぶときに確かめる条件を言える | 契約と条件を、規則ファイルの脇の文書に置く |

## 点検

- 構造の目標が 1 文で書かれ、規則が目標に対応している（本 skill の整理）
- 規則の意味が明示され、検査が自動で動く（S051 は「適合」の意味を明示し、できる限り自動化すると述べる）
- 自作の import 解析を載せていない。構文を解析する道具に任せ、製品名を書いていない
- 検査が、違反を終了コード 1、検査自体の失敗（設定の不正・対象 0 件・道具が無い）を 2 に分け、失敗を「違反なし」として扱わない
- 道具を選ぶ条件（複数行と空白・設定の参照先の検証・リンクの扱い・対象 0 件で失敗・対象コードの書き方の解析・解析できない依存で失敗）が書かれている
- 違反の件数が `violations=<数>` として残り、四半期の見直しで推移を比べると書かれている
- 既存の違反が、CI を必須にする前に直されている。直せないものは、規則か境界の見直しに回っている
- 見直しの対象と指標が表 1 つにまとまり、仕様と返答が揃っている（基準は架空）。担当・時期がある
- 違反 0 が、規則 2 つについての代理であり、目的全体への適合ではないと書かれている
- 入れない条件が書かれ、検査を一律に求めていない
- 適応度関数の語の説明が S052 に、規則と検査の方法が本 skill の整理に分けて帰属されている
- 推測の明示: 人数・モジュール・期限は例の設定。道具の性能・障害の減少は実測していない
