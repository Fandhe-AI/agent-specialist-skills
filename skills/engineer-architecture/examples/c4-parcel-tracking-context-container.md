# 例: 荷物追跡サービスの C4 の図（コンテキストとコンテナ）

地域配送業者の荷物追跡サービスを、C4 のシステムコンテキストとコンテナの 2 枚で描き、描かないものを決める例。図のテキスト記法（Structurizr DSL）まで載せる。題材は架空の事業者・サービスで、実在のものを写さない。構成図が古い・何をどこまで描けばよいかわからないという相談を受けたときに開く。

## 依頼

- 事業者: 架空の地域配送業者「ほしの配送」。開発者は 4 人（架空の前提）
- 依頼文: 「構成図が 3 種類あり、どれも古い。新しく入る人に説明するための図を、何をどこまで描けばよいか決めたい」
- 対象: 荷物追跡サービス。受取人が Web で荷物の状態を見る。営業所の受付が、問い合わせの荷物の状態を見る
- 周りの系（架空の前提）: 荷物の登録と配送の記録を持つ「配送管理システム」（既存の社内システム）。再配達の申し込みを受ける「再配達の受付システム」（別のチームが持つ）。ドライバーのアプリは配送管理システムへ書き込み、追跡サービスとは直接やり取りしない
- 先に確認したこと: 図を読む人は、新しく入る開発者と、営業所の運用の担当。図の更新を担う人は、追跡サービスの開発リーダー

## 目的の一文

新しく入る開発者が、荷物追跡サービスが誰に使われ、何とつながり、どの実行単位でできているかを 2 枚の図で言えるようにし、あわせて、描かないものを決めて書く。

## 削るもの

描かない図と、図に入れない要素を分ける。どれも「いまは」描かない。描き足す条件を右に書く。

| 削るもの | 理由と、描き足す条件 |
|---|---|
| コンポーネントの図 | 内部の構造で新しい人が迷うという声が、まだ無い（架空の前提）。迷う声が出たら、迷われたコンテナ 1 つだけを描く（本 skill の整理） |
| コードの図 | 描かない。コードの構造は、コードそのものが一番新しい資料である（本 skill の整理）。読み手がコードを読めない場合は、そのための別の資料を決める |
| 配備の図 | 実行環境の担当の資料にある（架空の前提）。S039 は補助の図として deployment を挙げる。配備の相談を受けたときに、その相談のために描く |
| ドライバーのアプリ | 追跡サービスと直接やり取りしない（架空の前提）ので、描かない。直接やり取りが生まれたら、外部の箱として足す |
| 認証・ログ・監視 | 全部の箱に共通する関心は、箱ごとに矢印を引かない。矢印が全部の箱に出て、読めなくなる（本 skill の目安）。必要なら図の脇に注記を 1 行置く |
| ライブラリ名・フレームワーク名 | コンテナの技術の欄は、種類（Web アプリ・RDB など）までにする。名前は変わりやすく、図が古くなる原因になる（推測）。名前が読み手の判断に要るときは、そのコンテナの責務の一文に書く |
| 矢印ごとの項目名・プロトコルの細目 | 矢印は、目的を動詞句で 1 つだけ書く。細目は、設計の文書に書く（本 skill の整理）。細目が読み手の判断に要る矢印は、その矢印の説明に足す |
| 4 階層を全部そろえること | 全部の図は要らず、読み手に価値のある図だけ描く（本 skill の整理）。最初は 2 枚で足りるかを考える |

## 構成

```text
図 1: システムコンテキスト   範囲: 荷物追跡サービス 1 つ + 人 2 + 外部の系 2
      問い: 誰が使い、何とつながるか
図 2: コンテナ             範囲: 荷物追跡サービスの内側（実行単位 4 つ）+ 図 1 の人と外部の系
      問い: 何でできていて、データはどう流れるか
```

- 図 2 の外側の箱は、図 1 の「荷物追跡サービス」と同じものである。名前をそろえる
- 図は、リポジトリに、記法のテキストで置く。コードと同じ変更の中で更新する（本 skill の整理）
- 更新の契機: コンテナの追加・削除、外部の系との連携の追加・削除。更新する人は、追跡サービスの開発リーダー（架空の前提）

## 仕様

出典のある値には S 番号を付ける。「目安」は本 skill の目安で、様式の要件ではない。

| 項目 | 値 | 根拠 |
|---|---|---|
| 階層の種類 | 抽象はソフトウェアシステム・コンテナ・コンポーネント・コード。図はシステムコンテキスト・コンテナ・コンポーネント・コード。補助の図は system landscape・dynamic・deployment | S039 |
| 描く枚数 | システムコンテキストとコンテナの 2 枚から始める | 本 skill の整理。S039 の引用は、描く枚数を定めない |
| 記法 | Structurizr DSL。この例で使う記法 | S039 は、記法にも道具にも依存しないと述べる |
| コンテナの意味 | 本 skill では実行単位（Web アプリ・サーバーのアプリ・RDB など）の意で使う。実行用のコンテナの意ではない | 本 skill の整理。S039 の引用は、コンテナの定義を述べない |
| 箱の書き方 | 名前と、責務の一文。コンテナは、技術の種類も書く | 目安 |
| 矢印の書き方 | 使う側から使われる側へ。目的を動詞句で書く | 目安 |
| 更新 | 図は小さく保ち、更新の契機と担当を決める | S027 は、小さく分けた文書には少なくとも更新される見込みがあると述べる（S027 は文書についての記述）。契機と担当を決めるのは本 skill の整理 |

文法の確認（本 skill の整理。推測）: Structurizr DSL の文法は、出典台帳に出典が無い。読み手が使う道具で読み込んで確かめる。コメントの構文は確かめていないので、この断片では使わない。

## 文言

### 相談への返答

> 結論: 図は、システムコンテキストとコンテナの 2 枚だけを描くことを勧めます。コンポーネントとコードの図、配備の図は、いまは描きません。
>
> 置いた仮定（架空の前提）: 開発は 4 人。追跡サービスの実行単位は 4 つ。内部の構造で新しい人が迷うという声は、まだ無い。ドライバーのアプリは、追跡サービスと直接やり取りしない。
>
> 選ぶ条件: 読み手が知りたいのが「誰が使い、何とつながり、何でできているか」である間は、この 2 枚で足ります。
>
> 失うもの: 追跡 API の内部の構造は、図に出ません。新しい人は、その部分をコードから読むことになります。
>
> 切り替える合図: 次のどれかが起きたら、その図だけを足します。内部の構造で新しい人が迷うと言う: 迷われたコンテナ 1 つのコンポーネントの図。配備の相談を受ける: 配備の図。ドライバーのアプリが追跡サービスと直接やり取りするようになる: 図 1 に外部の系として足し、図 2 にも反映する。
>
> 確かめられないこと: 図が、実際のコードや運用と合っているかは、図だけでは分かりません。開発リーダーの確認が要ります。

### 図の脇に置く注記

> この図は、システムコンテキストとコンテナの 2 枚である。コンポーネントの図・コードの図・配備の図は描いていない。更新の契機は、コンテナまたは外部の系の連携の増減。

## コード断片

Structurizr DSL。システムコンテキストの図（`context`）とコンテナの図（`containers`）を、同じモデルから出す。

```text
workspace "荷物追跡サービス" "架空の地域配送業者「ほしの配送」の荷物追跡サービスの構成" {

    model {
        receiver = person "受取人" "荷物の現在の状態を調べる"
        desk = person "営業所の受付" "受取人からの問い合わせに答える"

        dispatch = softwareSystem "配送管理システム" "既存の社内システム。荷物の登録と配送の記録を持つ"
        redelivery = softwareSystem "再配達の受付システム" "既存の社内システム。再配達の申し込みを受け付ける"

        tracking = softwareSystem "荷物追跡サービス" "荷物の現在の状態を、受取人と受付に見せる" {
            web = container "追跡画面" "荷物の状態を表示する" "Web アプリ"
            api = container "追跡 API" "状態の問い合わせに答える" "サーバーのアプリ"
            intake = container "状態の取り込み" "配送管理システムの更新を受け取り、追跡用の形に直す" "サーバーのアプリ"
            store = container "追跡データベース" "荷物ごとの状態の履歴を持つ" "RDB"
        }

        receiver -> web "荷物の状態を調べる"
        desk -> web "問い合わせの荷物の状態を調べる"
        web -> api "状態を問い合わせる"
        api -> store "履歴を読む"
        dispatch -> intake "荷物の更新を知らせる"
        intake -> store "状態を書く"
        web -> redelivery "再配達の受付へ案内する"
    }

    views {
        systemContext tracking "context" "荷物追跡サービスの文脈" {
            include *
            autoLayout lr
            title "荷物追跡サービス（システムコンテキスト）"
        }

        container tracking "containers" "荷物追跡サービスのコンテナ" {
            include *
            autoLayout lr
            title "荷物追跡サービス（コンテナ）"
        }
    }
}
```

読み方（本 skill の整理）:

- `model` の中で、人・外部の系・追跡サービス（とその中のコンテナ）・関係を定義する。`views` の中で、同じモデルから 2 枚の図を取り出す
- 関係は、コンテナの階層（人 → 追跡画面など）にだけ書いた。システムコンテキストの図の矢印（人 → 追跡サービスなど）は、コンテナ間の関係から道具が補う想定（推測。道具で確かめる）
- 実際の相談では、この断片を、読み手が使う道具で図にして確かめてから渡す

## 初見検証

新しく入った開発者と、図を読む周りの人が、図だけで何を言えるかを確かめる。

| 読む人 | 図だけで言えること | 言えないときの直し方 |
|---|---|---|
| 新しく入った開発者 | 追跡サービスを使う人と、つながる外部の系を、図 1 から言える | 外部の系の箱に、責務の一文を足す。人の箱に、何をするかを足す |
| 新しく入った開発者 | 荷物の更新が、どの実行単位を通って、どこに保存されるかを、図 2 から言える | 矢印の動詞句を、目的が分かる語に直す。向きを、使う側から使われる側にそろえる |
| 営業所の運用の担当 | 問い合わせの荷物の状態を、どの画面で見るかと、再配達の申し込みがどこへつながるかを言える | 人の箱と、再配達の受付システムへの矢印の文言を直す |
| 再配達の受付を持つチームの人 | 追跡サービスが、自分たちの系とどうつながるかを言える | 図 1 と図 2 の矢印の名前を、同じ語にそろえる |
| 図を更新する人 | どの変更のときに、どの図を直すかを言える | 更新の契機を、図の脇の注記に書く |

## 点検

- 図 1 と図 2 で、追跡サービスの名前と、外部の系・人の名前が同じである
- 描いていない図が、図の脇の注記に書かれ、描き足す条件と対応している
- 各箱に責務の一文があり、各コンテナに技術の種類がある
- 各矢印が、使う側から使われる側へ向き、目的が動詞句で書かれている
- コンテナの語が、実行単位の意で使われ、その定義が本 skill の整理であると書かれている（S039 の引用は、定義を述べない）
- DSL の断片を読み手の道具で読み込み、エラーが無い。コメントの構文は使っていない
- 更新の契機と更新する人が決まっている（契機と担当は本 skill の整理。S027 は、小さな文書には更新される見込みがあると述べる）
- 記法が、この例で使うものであると書かれている（S039 は、記法に依存しないと述べる）
- 推測の明示: 開発者の人数・実行単位の数・周りの系は、本 skill の例の設定で、実際の事業者に合わせて決める。図が実態に合っているかは、図だけでは分からない
