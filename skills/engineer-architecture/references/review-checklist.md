# 設計レビューの観点チェックリスト

設計案（構成・境界・移行の計画・決定の記録・図）を、案を出す前に自己点検するとき、または他者の案を見るときに使う全項目の点検表。[SKILL.md](../SKILL.md) の「レビュー観点チェックリスト」から開く。各項目で「はい / いいえ / 不明 / 該当なし」を付け、いいえと不明を、改善案か相談者への確認事項に結びつける。

項目は 2 群に分ける。文書や図を読めば判断できる群と、相談者の計測・コード・運用の記録が要る群である。後者は、ここでは実測していない。判定に要る証拠が足りないときは「不明」とし、何を測るかを書く。相談者が計測や記録を示し、それで確かめられれば、「はい」または「いいえ」を付ける。実装前の設計案では、実測の項目は、検証の方法・担当・時期が決まっているかで判定する。結果は実装後に確かめる（本 skill の整理）。性能・可用性・費用の保証はしない。

根拠の欄は、出典の番号（[出典台帳](sources.md)）か「本 skill の整理」である。S 番号が支えるのは、引用ブロックに逐語であることだけで、残りは「本 skill の整理」「推測」と書く。区分は台帳の凡例に従い、A 以外は区分を添える。

## 文書だけで判断できる項目

### 決めることと制約

- [ ] 何を決める相談か（構造・実装・運用のどれか）を一文で言える（本 skill の整理。アーキテクチャを「変えにくいと人が感じるもの」と定義する見方がある: S006）
- [ ] 変えにくい部分はどこかを、先に絞った（本 skill の整理）
- [ ] 人数とチーム数、期限、運用の体力を、案の前提として書いた（本 skill の整理。下地の能力は S026 を見る）
- [ ] 数年後に捨てる前提か、長く使う前提かを書いた（本 skill の整理。S085 は、数年後に（うまくいけば）今作っているものを捨てる必要が出ると、いまのうちに受け入れる考え方を述べる）

### 境界と依存

- [ ] 他から隠す設計判断を受け持つモジュールに分け、インターフェースは中身を見せすぎていない（S008。B）
- [ ] 境界の内側でモデルが通用する範囲を、明示した（S013）
- [ ] 採用した依存の向きの規則が明示され、設計がそれに従う（本 skill の整理。S016 は、ソースコードの依存を内向きだけとする規則を述べ、内側の円は方針、外側の円は仕組みと述べる。内向きの規則は、採用したときに適用する）
- [ ] 旧系や外部のモデルの翻訳が要る境界かを確かめた。要るときだけ、翻訳の層の設計を点検した（S017 は、異なるサブシステムの間に置く層を述べる。旧系・外部との間に置くのは本 skill の整理）
- [ ] 境界を決める表に、チームの境界も並べた。境界を越える変更に、何チームの調整が要るかを書いた（本 skill の整理。Conway は組織の連絡の構造の写しになる設計への制約を述べる: S086。抄録は S092（B。抄録のみ）で、「組織を変えれば良くなる」の根拠ではない）

### 構成の選択

- [ ] 推す構成の、得るものと失うものを両面で書いた（本 skill の整理）
- [ ] マイクロサービスを推すなら、運用の下地（S026）を先に見て、独立した配備・拡大などで得る利益と、分割・移行・運用の費用（割増は S025）を比べた。チームが分かれたことだけを理由にしていない（本 skill の整理。SKILL.md の構成の表の条件）。参考として、S106（C。自称）は、サービスが別のチームに対応するとき、または、独立した配備の価値と独立した拡大の価値がオーケストレーションの費用を上回るとき、と「または」で並べる
- [ ] 反対の案と、切り替える合図を書いた（モノリス先行は S022、反対論は S023。C。後者が先に分割を選ぶ条件は引用の範囲外）
- [ ] 他社の事例を根拠にするとき、その会社の自称であることと、規模・処理の性質の違いを書いた（S104・S105・S106・S107。いずれも C）
- [ ] 技術を、課題から選んだ。流行や履歴書から選んでいない（本 skill の整理。S103（C）は、桁違いに大きい組織に合う型は自分に合う型と正反対のことが多いと述べる。S108 は、履歴書と応募の過程で、技術の流行を過度に重視する傾向への実証的な裏づけを述べる。設計判断への裏づけではない。本 skill の整理）

### 品質特性と決定の記録

- [ ] 品質の目標を、場面と値で書いた。「速く」「安全に」で止めていない（本 skill の整理。S047 は、重要な品質を具体的・測定可能に把握することを述べる）
- [ ] 案どうしのトレードオフを、品質特性の言葉で比べた（本 skill の整理。S048 は、アーキテクチャが複雑で、多くの設計上のトレードオフを伴うと書く）
- [ ] 可用性の目標（稼働時間・成功率）と、復旧の目標（復旧時間など）を、別々に確かめた（本 skill の整理。S061 は resilience の定義で、可用性の定義ではない。数値目標は相談者が決める）
- [ ] 決定は 1 件 1 記録で書いた（S030）。却下した案と見直す条件の欄を持つ（本 skill の整理）
- [ ] 受理した記録を書き換えず、置き換えている（S031）
- [ ] 図は、読み手に価値があるものだけを描き、更新する人と時期を決めた（本 skill の整理。小さな文書には少なくとも更新される見込みがある: S027）

### 分散・移行・役割

- [ ] 呼び出しがネットワーク越しになったとき、遅延・失敗・順序が手元と同じでないことを扱った（本 skill の整理。S067（B）は、分散アプリケーションを初めて作る人が置く 8 つの誤った前提の表を述べる。S066 は、「先に起きた」の関係は部分順序にすぎないと書く）
- [ ] CAP の言葉だけで系の性質を片付けず、分断時と平常時を分けて書いた（本 skill の整理。S070（B）は「2 of 3」の言い方が最初から誤解を招いたと述べ、S074（C）は単純化が過ぎると批判する）
- [ ] 古い系の置き換えは、全面置換でなく段階的な刷新を先に検討し、終わらせ方まで書いた（本 skill の整理。S079 は、同僚と自分は段階的な刷新を好むと述べる。内部の部品の入れ替えは S082 を見る）。該当する移行案では、SKILL.md の「移行で確かめる問い」の各問いに答えが出ているかを確かめる（本 skill の整理）
- [ ] インターフェースへの後方互換のない変更を、拡張・移行・縮小の 3 相に分けた（S083）
- [ ] 公開の API では、約束していない挙動も当てにされうることを、廃止の手順に入れた（本 skill の整理。S101 は、API の利用者が十分に多いと、契約で何を約束しても、観測できる挙動は誰かに当てにされると述べる）
- [ ] 決定を、アーキテクトが独占していない。チームへ能力を分ける道を書いた（本 skill の整理。S095 は、独占するとボトルネックになる危険を述べ、S096 は、アーキテクトの価値は下す決定の数に反比例するという見方を述べる。S058 は、能力をチームへ分けると述べ、S094 は、イネーブリングチームを、障害の克服を助け、足りない能力を検出するチームと書く）

## 実測や相談者のデータが要る項目

ここは、文書を読むだけでは「はい」にできない。相談者の計測・コード・運用の記録が足りないときは「不明」とし、何を測るかを書く。記録が示され、それで確かめられれば、「はい」または「いいえ」を付ける。

- [ ] 品質の目標値（応答時間・可用性・復旧時間など）が、実際の計測で満たされているか確かめた。値は相談者が決め、ここでは実測していない（本 skill の整理。S047 は、重要な品質を具体的・測定可能に把握することを述べる）
- [ ] 依存の向きと境界を、コードで検査している。検査が実際に通っているか確かめた（本 skill の整理。S016 は、ソースコードの依存を内向きだけとする規則を述べ、S051 は、「適合」の意味を明示し、できる限り自動化すると述べる）
- [ ] 構造の目標を、継続して測っている（S052 は、適応度関数を、アーキテクチャが目的にどれだけ近いかの記述と書く。テストとして測るかは本 skill の整理）。測っていないなら、何から測るかを書いた
- [ ] 境界を越える変更の件数と、調整に要るチーム数を、変更の履歴から数えた（本 skill の整理）
- [ ] 分割の費用（運用・配備・障害の連鎖）を、現在の記録で見積もった。他社の削減率を当てはめていない（本 skill の整理。S025 は割増の費用を、S107（C。自称）は 1 つのサービスの削減を述べる）
- [ ] 負荷の増え方と、データの受け渡しの量を計測し、構成の選択の前提にした（本 skill の整理。S107（C。自称）は、費用が最も高い操作に、分散コンポーネント間のデータの受け渡しを挙げる。1 サービスの話で、一般化しない）
- [ ] 旧系の実際の挙動を観測し、仕様書にない挙動を移行の前に洗い出した（本 skill の整理。S101 を見る）
- [ ] 障害が連鎖する経路を、図でなく実際の呼び出しの記録から確かめた（本 skill の整理。S067 も見る）
- [ ] 移行中に新旧が併存する期間の費用と、終わる条件を見積もった（本 skill の整理。相談者のデータが要る）

## 使い方

- 制作モードでは、案を出す前に全項目を見る。レビューでは、特に落ちやすい次の群から見る: 決めることと制約、構成の選択、決定の記録
- 「不明」が多いときは、案を断定せず、相談者へ確認する事項として返す
- 項目は、出典が定めた合格基準ではない。出典の主張と、本 skill の整理を、根拠の欄で分けている

## 判定の付け方

| 判定 | 意味 | 返し方 |
|---|---|---|
| はい | 文書や記録で確かめられた | 根拠を 1 行で添える |
| いいえ | 欠けている、または反している | 改善案を、得るものと失うものの両面で書く |
| 不明 | 判定に要る証拠が足りない。計測や記録が要る | 何を測るかと、誰が測るかを書く。証拠が示されたら、はい・いいえに改める |
| 該当なし | 対象の系に、その要素が無い（旧系・公開 API など） | 該当なしの理由を 1 行で添える |
