# ソフトウェア設計の歴史: モジュール・分散・文書・移行・揺り戻し

ソフトウェアの構造設計の考え方が、いつ、どんな議論として現れたかをまとめたファイル。年表の暗記用ではなく、「いま採ろうとしている型は、どんな前提のもとで語られたか」を確かめる材料である。開くのは、相談者が背景や由来を求めたとき、構成や移行の方針を決める前、「他社がそうした」「昔からの原則だ」と言われたときの 3 つである。中心の問いは次の 1 つで、本 skill の整理である。

> その型を語った議論の前提（規模・領域の理解・運用の体力・チームの形）は、今回の系でも成り立つか。

出典が薄い箇所は、薄いと書く。

| 知りたいこと | 開く場所 |
|---|---|
| 全体像・年の並び | 「見取り図」 |
| 議論が繰り返す型 | 「繰り返すパターン」 |
| 相談の種類ごとに確かめる問い | 「相談の種類別の使い方」 |
| 年が出典どうしで合わない項目 | 「年を書くときの注意」 |
| 空白・未検証 | 「確認できなかったもの」 |

## 読み方と記法

- 時点: 記述は出典ごとの取得日の時点。各項目は[出典台帳](sources.md)で見る
- 年は、各項目の「媒体・日付」に原稿で確かめたものだけを書く。月が確認できていないものは年だけにする
- S 番号が支えるのは、その項目の引用ブロックに逐語であることだけである。それ以外は「本 skill の整理」「推測」「本 skill の確認」と書く
- 区分は台帳の凡例に従う。B（第三者の複製や他媒体経由）と C（反論・自社の事例の記述）は、区分を添えて要旨にし、本人の発言としては示さない
- 見取り図の各行は、引用が言う範囲だけを書く。行どうしを結ぶのは「繰り返すパターン」で、すべて本 skill の整理（推測）である
- 各社の記事は、その会社の自称である。一般化しない
- 回答では、頼まれない限り歴史を講釈しない。判断の根拠として 1 行で使う

## 繰り返すパターン（本 skill の整理）

次の型は、出典を横断して読み取ったもので、出典が述べた法則ではない。すべて推測で、例外は多い。

1. 分けすぎと固めすぎの往復: 次の出典が並ぶ。分散オブジェクトの第一法則（S020）、SOA の語（S019）、マイクロサービス（S021）、モノリス先行論と反対論（S022・S023）、各社の自称（S104〜S107）である。往復という見立ては推測である
2. 名前が先に広まり、中身が拡散する: SOA は人によって指すものが違った（S019）。マイクロサービスにも同じことが起きたかは、出典が述べていない。語でなく中身で語る
3. 分散の費用は繰り返し現れる: 1978 年の順序の議論（S066）、分散オブジェクトの第一法則（S020）、8 つの誤った前提（S067。B）、2012 年の CAP の言い直し（S070。B）が並ぶ。ネットワーク越しの呼び出しを手元と同じに扱う誤りが時代を変えて現れるかは、推測である
4. 境界を、技術と組織の両面から見る: 他から隠す設計判断で切る（S008）、組織の連絡の構造の写しになる設計（S086）、組織と製品のモジュール性の関係を述べる抄録（S092。B）が並ぶ。境界を決めるときにチームの境界も並べる、は本 skill の整理である
5. きれいな設計が無いのではなく、圧力のもとで育つ: 泥団子の特徴づけ（S098）と、数年後に捨てる前提の受け入れ（S085）、段階的な刷新（S079）を並べて読む。応答として読めるかは推測である
6. 単独の技法に頼らない: 10 年で生産性・信頼性・単純さの 1 桁の改善を約束する単独の技法は無い（S002）、流行に合わせた選択への意見（S103）と、履歴書と応募の過程での流行の重視についての抄録（S108）が並ぶ。S108 の用途は履歴書と応募の場面に限る。技術選定や、新しい道具で全部解決するという話への留保として並べて使うのは、本 skill の整理である
7. 事例の自称は条件つき: 各社の事例（S104・S105・S106・S107）は、規模・処理の性質が違う。一般化しない

## 相談の種類別の使い方

問いはすべて本 skill の整理である。出典は、関係する項目の番号で、問いを支えるものではない。

| 相談の種類 | 確かめる問い | 関係する出典 |
|---|---|---|
| サービス分割・マイクロサービス | 議論の前提（組織の規模・運用の下地・分ける利点）は自分の系にあるか。事例は自称で、条件が同じか | S021・S022・S023・S103・S106・S107 |
| 境界・モジュール | 他から隠す設計判断ごとに切ったか。組織の形が案を先に絞っていないか | S008・S086・S092 |
| 古い系の作り直し | 全面置換でなく、段階的な刷新を先に検討したか。捨てる前提か | S079・S085 |
| 同期呼び出しと障害の連鎖 | ネットワーク越しを手元と同じに扱っていないか。順序と時刻に頼っていないか | S020・S066・S067・S070 |
| 技術選定 | 課題から選んだか、流行から選んだか | S103・S108（履歴書と応募の過程の話） |
| 決定の記録・文書 | 小さく更新される文書か。置き換えの履歴は残るか | S027・S029 |
| 構造の検査 | 目標は測れる形か。構造の規則を自動で検査できるか | S047・S051・S052 |
| アーキテクトの役割 | 決定を独占していないか。力をチームへ分けているか | S095・S096 |
