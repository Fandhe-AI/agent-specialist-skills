# デザイン史: 応答時間・動き・遷移・状態・キーボード・AI の応答

制作とレビューの判断に歴史を使うための参照。年表の暗記用ではなく、「いま作っている操作の感じは、どんな制約から生まれた慣習か」を確かめるための材料である。画面の「操作したときの感じ」（応答時間・動き・遷移・待ち・取り消し・キーボード・AI の応答）の慣習が、どんな制約から生まれ、何に直され、今の判断に何を示すかを、時代ごとに同じ 4 項目で書く。中心の問いは次の 1 つ。

> その慣習を生んだ制約は、今回の媒体・利用者でも成り立つか。

成り立つなら、慣習は今も根拠を持つ。成り立たないなら、様式だけが残っている可能性がある。

このファイルを開くのは、相談者が背景を求めたとき、制作の着手前（「媒体別の使い方」の節）、レビューで「慣習の由来」の項目が不明のとき、の 3 つである。

| 知りたいこと | 開く場所 |
|---|---|
| ある数値（0.1 秒・400 ms・300 ms 未満など）の由来 | 「時代別の詳細」の 1・6・9 |
| 動きを付ける・付けない判断の由来 | 「時代別の詳細」の 2・6・7 |
| スクロール演出・ページ遷移の由来 | 「時代別の詳細」の 3・5・8 |
| 動きを減らす設定の由来 | 「時代別の詳細」の 4 |
| AI の応答画面の由来 | 「時代別の詳細」の 10 |
| 全体像・横断の型・媒体別の問い・俗説 | 「見取り図」「繰り返すパターン」「媒体別の使い方」「確認できなかったもの・よく語られる俗説」 |

## 読み方と記法

- 時点: 本ファイルの記述は 2026-11-15 時点（出典の取得日）。出典の詳細（引用原文・日付・URL・検証区分）は `sources.md` を参照する。
- 各時代の 4 項目: 当時の制約 / 応答 / 副作用と反動 / 今の判断への示唆。4 項目めの「示唆」はすべて「本 skill の整理」（推測）で、出典が述べた因果ではない。因果（「A だから B になった」）は、出典が述べている場合だけ S 番号付きで書く。出典が述べていない制約は「整理（推測）」と書く。
- 区分は `sources.md` の凡例に従う（A 原典、B 第三者の転載、C 論評、R 記者・機関の地の文、U 未検証）。B・C・R は区分を明記して使い、本人の発言として書かない。書籍・未照合（N 番号）の内容は事実の主張に使わない。
- 自社の主張（Linear・Superhuman・Raycast・Vercel・Google）は「自称」として扱い、速さ・感触の良さを事実として書かない。個人の記事（Emil Kowalski・Rauno Freiberg・Jakub Krehel）は個人の経験則で、規格や公式の指針と同列に引かない。
- 年が出典どうしで食い違う、または年を確認できなかったものは、「年が食い違う・未確認の年」にまとめた。
- 回答での使い方: 頼まれない限り、歴史を講釈しない。判断の根拠として 1 行で使う。

## 回答での使い方（例）

歴史は、判断の根拠として 1 行で添える。講釈にしない。次の組み立てを使う。

- 相談「400 ms 以内にしたい（Doherty）」: 400 ms は、取得できた IBM の報告の本文に無い。第三者のブログ（S12。区分 B）か、サイトの要約（S13。区分 R）にある値である。ブログは図（the chart）を根拠とするが、図の出所は確認できていない。目標は INP のような測れる指標（S17）と、0.1 秒・1 秒・10 秒の限界（S01・S02・S03）で置く。
- 相談「ヌルヌル動かしたい」: 動きは、静的な表示では伝えにくい変化を伝えるための道具、という出発点が 1993 年の論文にある（S132）。何の変化を伝えるかを先に問う。
- 相談「スクロールで動く LP にしたい」: スクロールジャックは、制御・発見性・注意・効率を損なうと観察された（S138）。機能的な目的（段階的開示）があった例は成功した（S139）。目的があるかを先に問う。
- 相談「ページ遷移を滑らかにしたい」: 標準の機構（View Transition）が使えるようになった（S87・S89）。ただし新しいページは 1 秒以内に出すことが目標（S08）で、作れることは理由にならない（本 skill の整理）。
- 相談「削除の前に確認ダイアログを出したい」: 慣れた利用者は確認の警告に慣れて素通りする（habituation）、と 2007 年の論考が述べる（S116）。取り消せる設計（S115）に置き換えられないかを先に問う。

## 繰り返すパターン（本 skill の整理）

次の型は、時代を横断して読み取ったもので、出典が述べた法則ではない。例外は多い。

1. 新しい手段が出るほど、「作れるから使う」誘惑が増え、反動が来る。Flash への批判（S137。C）、スクロールジャックの観察（S138）、iOS 7 の動きの多用と Reduce Motion（S80・S81）は、手段が整ってから反動が出た例として並べられる。反動の因果は、出典がそう述べた範囲でしか書かない（iOS 7 の訴えを受けて設定を足した、という因果は出典に無い）。
2. 数値の限界は、用途ごとに別の資料から来る。0.1 秒・1 秒・10 秒は応答の限界（S01・S02・S03）、100〜500 ms は動きの長さの指針（S19）、200 ms 以下の INP は測定の推奨（S17）で、同じ表に混ぜると意味が崩れる。
3. 標準が揃うと、止める手段が数年遅れて対になる。CSS の transition は 2007 年（S84）、prefers-reduced-motion の提案は 2014 年（S82）、全ブラウザーの対応は 2020 年 1 月（S77）。
4. 自社の語りが規則として流通する。速さ・感触を自社の価値とする記事（S18・S60。自称）や、個人の経験則（S33）が、公式の指針より強い断定として引かれる。数値の出典としては弱く、問いの宝庫として使う。
5. 慣習の効果は、実験で測られていないことが多い。view transition の認知負荷の低減（S87）、楽観的更新の体感の向上、中断可能性の効果は、取得した範囲に実験の裏づけが無い。

## 時代別の詳細

### 1. 応答時間の研究: 端末の待ちと生産性（〜1993 年）

- 当時の制約: 端末とホストの応答は遅く、待ちが人の作業にどう影響するかが経済の問題だった。IBM の 1982 年の報告は、心理学者の Robert B Miller らが、人がコンピューターの応答を待つ上限は 2 秒だと論じたと述べる（S09。走査の OCR）
- 応答: 同報告は、ある事例でプログラマが 1 時間に約 180 件の処理をすると述べ（S10）、1 秒未満の応答の別の事例では生産量が 58 % 増えたと述べる（S11）。Nielsen は 1993 年の著書の抜粋に、0.1 秒・1 秒・10 秒の 3 つの限界を、Miller 1968 と Card ら 1991 から続く助言として書いた（S04・S01・S02・S03）。アニメーションは実時間の時計で計る、という助言も同じ記事にある（S05）
- 副作用と反動: 「400 ms」という数値が、IBM の報告の本文には無いまま広まった（S12・S13。区分 B・R の第三者の要約）。web.dev の RAIL は、100 ms 以内の応答を即時と感じると述べつつ、Core Web Vitals を推奨し閾値が異なると注記する（S14・S16）。INP は 200 ms 以下を良いとする（S17）。Superhuman は 100 ms の規則を自社の方針とする（S18。自称）
- 示唆（整理・推測）: 3 つの限界は、人が「自分の操作が結果を起こした」と感じる時間（0.1 秒）、思考が途切れない時間（1 秒）、注意が保てる時間（10 秒）の目安で、画面の動き 1 つ 1 つの長さを決める値ではない。動きの長さは別の資料（S19・S27）で決め、応答の限界は「操作から反応が始まるまで」に使う
- 注意: 1980 年代の端末でのプログラマの作業の結果を、現在の画面操作（ボタン・遷移）にそのまま当てはめない

### 2. アニメーションの原則を画面へ: Lasseter と Chang & Ungar（1987〜1993 年）

- 当時の制約: コンピューターアニメーションの多くは、作画アニメの原則を知らない技術者の手で作られていた。Lasseter（SIGGRAPH '87）は、伝統的な 2D の作画アニメの原則を 3D に当てはめる論文を書いた（S131）。UI では、静的な表示を前提とした画面が変化の伝達に向かず、利用者を驚かせ混乱させる、と Chang & Ungar（UIST '93）が問題を設定した（S132）
- 応答: Lasseter は、動きの速さが、その動きの意図が観客にどう読まれるかを決めると述べた（S130）。Chang & Ungar は、Thomas & Johnston の書籍の原則を元に（S133）、Self という研究用の UI に、予備動作や、遷移の中間を速く端を遅くする緩急を試した（S133・S134）
- 副作用と反動: 取得した範囲で、この試みが製品の標準になった経緯は確認できていない。「12 原則を UI に当てはめる」という通説は、数の根拠（N04）が取得できていない
- 示唆（整理・推測）: 「動きは変化を理解可能にするための道具」という出発点は 30 年以上前から述べられている。いま「動きを付けて」と頼まれたときも、「何の変化を伝えるのか」を先に問える

### 3. Flash の時代と反動（2000 年〜2020 年）

- 当時の制約（整理・推測）: 2000 年前後の Web には、動きや対話を作る標準が少なかった。Flash の普及の時期・割合の出典は取得していない（未検証・伝聞）
- 応答: Nielsen は 2000 年に、Flash の存在は 99 % の場合にユーザビリティの病に当たる、と批判した（S137。区分 C。99 % は統計ではなく強調）。批判の理由は、デザインの濫用・Web の基本的な操作原則からの逸脱・注意の分散だった（S144。C）。Apple は Flash を許さない理由を述べた文書で、先進的な図形・書体・動き・遷移は HTML5 でプラグインなしに作れる、と主張した（S136。ページ末に April, 2010 とある。保存コピーは 2011 年）。Adobe は 2017 年に、Flash Player の更新と配布を 2020 年末で止めると発表した（S135）
- 副作用と反動: 動きの手段が Web の標準（CSS・JavaScript・のちに Web Animations）へ移り、動きとページ・操作の関係が標準の機構（戻る・リンク・検索・読み上げ）と一緒に扱われるようになった（整理・推測）
- 示唆（整理・推測）: Nielsen の批判の論点（Web の基本的な操作原則からの逸脱・注意の分散。S144）は、後年のスクロールジャック（本章 5）の批判と構造が似ている。動きの演出が「標準の操作を壊す」かどうかが、繰り返し出る論点

### 4. CSS が動きを標準にした: transition・animation と iOS 7（2007 年〜2017 年）

- 当時の制約: 動きを Web で作るには、プラグインか、JavaScript でのタイマー操作が必要だった（整理・推測）。WebKit の記事は、CSS の transform・animation は WebKit の開発者が提案したもので（S83）、プラグインのセキュリティとバッテリーの負担なしに創造的な動きが作れるようになった、と述べる（S145。2017 年の記事）
- 応答: WebKit は 2007-10-31 の記事で、最も単純な動きとして CSS の transition を紹介した（S84）。W3C の CSS Transitions は、取得した版（Working Draft、2026-01-08）で、プロパティの値の変化を指定した長さで滑らかに起こす規格と述べる（S85）。MDN は、2 つの状態の間をブラウザーが補う動きを implicit transitions と呼ぶと説明する（S86）
- 副作用と反動: 2013 年の iOS 7 は視差・奥行き・ズームの動きを多用した（S81）。iOS 7 で Reduce Motion の設定が追加され、視差とアプリ起動の動きを切れるようになった（S80）。ALA（2015-09-08）は、iOS 7 の遷移で気分が悪くなった人がいた、と書く（S140）。prefers-reduced-motion は 2014 年に CSS WG へ提案され（S82）、MDN は全ブラウザーの対応を 2020 年 1 月からとする（S77）
- 示唆（整理・推測）: 動きの標準化と、動きを止める標準（設定・メディア特徴）が、数年のずれで揃った。いま動きを足すときは、止める側の設計（縮小版）を最初から対にする

### 5. スクロール演出の流行と反動（2010 年代〜）

- 当時の制約（整理・推測）: スクロールはページの基本操作で、位置に連動する演出（視差・スクロールジャック）が、製品や特集のサイトの演出として広まった。流行の時期・規模の出典は取得していない
- 応答: NN/g（2023-08-06）は、スクロールジャックを使うサイトの利用者テストで、制御・発見性・注意・効率・課題の成功への脅威を観察した（S138）。同記事は、機能的な目的（段階的開示）がある BBC の例は成功したとも述べる（S139）。NN/g の 2020 年の記事は、視差・カルーセルの自動送り・スクロールジャックが前庭障害の利用者にめまいや吐き気や片頭痛を起こしうると注意する（S26）。WCAG 2.3.3（AAA）は、操作で起きる動きを無効にできることを求め（S95）、スクロールで要素が動くと前庭障害を起こしうると説明する（S96）
- 副作用と反動: Chrome の解説は、従来のスクロール連動をメインスレッドのスクロールイベントで行う方法とし、ブラウザーがスクロールを別プロセスで行うためイベントが非同期に届く問題を挙げる（S146）。scroll-driven animations は、アニメーションをスクロールコンテナの位置に結びつける機構である（S90）。規格は取得した版の URL が 2023 年 6 月 6 日付の Working Draft の版だった（S143）
- 示唆（整理・推測）: 技術（速く滑らかに作れる）が整うほど、「作れるから使う」誘惑が増える。スクロール連動は、位置の理解や段階的開示（機能）に使い、スクロールの速さ・向きの置き換え（スクロールジャック）には使わない、と分けられる

### 6. デザインシステムとマイクロインタラクション（2014 年〜）

- 当時の制約（整理・推測）: 製品が増え、動きの長さ・イージングが画面ごとにばらつく。個々の小さな反応（トグル・ボタンの押下・通知）を設計の単位にする考えが広まった。NN/g は、2014 年に Saffer が書籍 *Microinteractions* でこの概念を定義し、設計モデルを示したと述べる（S119。R。書籍の本文は N01 で未照合）
- 応答: NN/g は、マイクロインタラクションをトリガーとフィードバックの組と定義する（S118）。Material Web のトークンは、duration を short（50〜200 ms）・medium（250〜400 ms）・long（450〜600 ms）・extra-long（700〜1000 ms）の段階で持ち（S27・S28・S147）、easing を cubic-bezier のトークンで持つ（S29）
- 副作用と反動: 値がトークンになると、画面ごとの違和感は減るが、頻度が高い操作の動きまで一律に揃える危険がある（整理・推測）。Emil は頻度の高い操作の動きを減らす（S31・S32。個人の経験則）、Apple の HIG は頻繁な操作に動きを足さない（S67）と述べる
- 示唆（整理・推測）: トークンは「選べる段階」の用意であって、「どこで動かすか」の判断の代わりにならない。使う場所の頻度の判断を、仕様書の別の欄にする

### 7. 流動的なインターフェース: 中断・方向転換・慣性（2017 年〜）

- 当時の制約: タッチとジェスチャーの画面では、遅延と、動きの途中で操作できない固定の動きが、道具として感じられない原因になる。WWDC18（Session 803）で Apple の Chan は、道具や楽器に遅延があったらどうか、と喩えた（S73）
- 応答: 同セッションは、操作の途中での方向転換と中断を許す、という原則を挙げ（S74）、流動性は人の側の性質で UI がそれに応じる、と述べる（S75）。個人の記事（Rauno・Jakub。個人の経験則）は、中断できる動きを重視する（S42・S43・S45）。Vercel の指針（自称）も、動きは利用者の入力で中断できるとする（S48）。HIG は、動きの完了を待たせない、特に繰り返し見る動きは、と述べる（S68）
- 副作用と反動: 中断できる動きは、実装の選択（CSS の transition は最新の状態へ補間して中断でき、keyframe は固定のタイムライン。S43）に依存する。取得した範囲に、中断可能性の効果を測った実験は無い
- 示唆（整理・推測）: 動きの長さの議論（何 ms）より前に、「途中で止められるか・戻せるか」を仕様の項目に入れる

### 8. Web プラットフォームが動きを担う（2020 年代）

- 当時の制約: 画面遷移・出現と退場・スクロール連動・オーバーレイは、JavaScript の補助が大きかった。自前の popover は、フォーカス・開閉の状態・キーボードを自前で実装する必要があった（S93）
- 応答: View Transition API は、状態間の遷移の演出の仕組みで、MDN は認知負荷・文脈の維持・体感の遅延の軽減に使われると述べる（S87）。Chrome の解説では、一覧のサムネイルから詳細の大きな画像への遷移が典型例（S88）、同一文書の view transition は Chrome 111 から対応する（S89）。`@starting-style` は初回表示の遷移の開始値を決め（S91）、MDN の表示は 2024 年 8 月から全ブラウザー。Popover API は標準の仕組みで（S92）、MDN の表示は 2025 年 1 月から。View Transitions の規格は、取得した版が Candidate Recommendation Draft だった（S142）
- 副作用と反動: 対応状況・規格の版は時点情報で、実装直前に確認する必要がある（N09）。効果（認知負荷が下がる）は MDN の記述で、実験の裏づけは取得していない
- 示唆（整理・推測）: 標準の機構が揃うほど、「作れる」ことは理由にならない。ページ遷移の演出を使うなら、速さ（新しいページは 1 秒以内。S08）・中断・縮小版・フォールバック（非対応でも機能する）を仕様に書く

### 9. 速さと感触を自社の価値にする文化とデザインエンジニア（2020 年代）

- 当時の制約（整理・推測）: 機能が似る製品の間で、速さ・操作の感触・キーボード中心の操作が、差別化の材料になった
- 応答: Superhuman は 100 ms の規則（S18）と、コマンドパレットによるショートカットの発見（S58・S59）を自社の方針とする（自称）。Raycast は、製品が好まれる理由は感触だと述べる（S60。自称）。Vercel は、デザインエンジニアという職能を、アニメーション・キーボード・タッチをコードで試す立場として説明し（S57。自称。2024-03-29）、Web Interface Guidelines で動き・状態・キーボードを細目にする（S47・S50・S53・S55。自称）
- 副作用と反動: 自社の価値の語りは検証できない（「速い」を測った結果は取得していない）。第三者の分析（S61。R）は筆者の推測である。個人の経験則（Emil の "never animate"。S33）が、公式の指針（HIG。S67）より強い断定として流通する危険がある
- 示唆（整理・推測）: この系譜の記事は、設計の「問い」（頻度・目的・中断・縮小）の宝庫で、数値の出典としては弱い。数値は経験則として分けて使う

### 10. AI の応答の画面（2019 年〜）

- 当時の制約（整理・推測）: AI の応答は時間がかかり、誤り、結果が長い。Microsoft Research らの 2019 年の指針は、能力の範囲を示す・精度を示す・誤ったときに編集・修正しやすくする・操作の影響を伝える、などを挙げた（S123・S124・S125・S126）
- 応答: Apple の HIG は、生成には時間がかかるので読み込み体験を設計するか背景で生成する（S69）、具体的なフィードバックで待ちを目的のあるものにする（S70）、破壊的・取り消しにくい操作を自動化しない（S71）と述べる。NN/g（2026-04-24）は、実在のチャットボットの調査で、長い応答の最後の自動スクロールが、読み始めた位置を見失わせると観察し（S120）、提案プロンプトで入力の負担を減らし（S121）、漠然とした導入文が過剰な期待を生むと述べる（S122）
- 副作用と反動: Google の自社研究は、生成の速さを無視すれば生成 UI が好まれたと述べる（S127。自称）。つまり速さという要素は、評価の外に置かれている。MeasuringU の調査は 153 人の小標本で（S128）、個別の操作の設計の根拠にはならない
- 示唆（整理・推測）: AI の応答は、「待ち」「途中経過」「誤り」「取り消し」を設計する領域で、既存の原則（システム状態の可視化・Undo。S117・S115）が当てはまる。新しい問いは、ストリーミングの途中で読む・止める・直す（S120）に集まる

## 媒体別の使い方

制作の着手前に、その媒体の問いを 1 つ確かめる。

| 媒体・題材 | 着手前の問い | 根拠の節 |
|---|---|---|
| 部品の押下・出現・退場 | この動きを何回見るか。頻度が高いなら動かさない・短くする。トークンの段階は、場所の頻度で選ぶ | 時代別の 6・7 |
| ページ遷移 | 標準の機構で足りるか。非対応でも機能するか。戻る操作・中断で壊れないか。1 秒以内か | 時代別の 4・8 |
| スクロール連動 | 位置の理解や段階的開示という機能的な目的があるか。スクロールの速さ・向きを奪わないか | 時代別の 3・5 |
| 待ち・読み込み | 待ちは何秒か。1 秒未満なら、骨組みもスピナーも不要。表示の点滅を避ける | 時代別の 1 |
| 楽観的更新・取り消し | 失敗したときの見せ方と取り消しは。確認ダイアログで済ませていないか | 時代別の 6・7 |
| キーボード・コマンドパレット | 全部の操作がキーボードでできるか。速さの語りを事実として書いていないか | 時代別の 9 |
| AI の応答画面 | 読み始めた位置を保つか。止める・直す・取り消すができるか。能力と精度を示すか | 時代別の 10 |
| 動きを減らす設定 | 位置・拡大縮小の動きを減らし、状態は動き以外でも伝わるか | 時代別の 4 |
