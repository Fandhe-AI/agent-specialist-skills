# 運用の文書のレビュー観点チェックリスト

SLO の決定記録、可観測性と警報の設計、公開の安全の方針、事後検証の文書を、出す前に自己点検するとき、または他者の文書を見るときに使う全項目の点検表。[SKILL.md](../SKILL.md) の「レビュー観点チェックリスト」から開く。各項目で「はい / いいえ / 不明 / 該当なし」を付け、いいえと不明を、改善案か相談者への確認事項に結びつける。

項目は 2 群に分ける。文書を読めば判断できる群と、相談者の計測・運用の記録が要る群である。後者は、ここでは実測していない。判定に要る証拠が足りないときは「不明」とし、何を測るかを書く。相談者が計測や記録を示し、それで確かめられれば、「はい」または「いいえ」を付ける。結果を問う項目は、証拠が得られるまで「不明」とする。可用性・性能・費用の保証はしない。数値の目標は相談者が決める。ここでは値の基準を置かない。

根拠の欄は、出典の番号（[出典台帳](sources.md)）か「本 skill の整理」である。S 番号が支えるのは、引用ブロックに逐語であることだけで、残りは「本 skill の整理」「推測」と書く。区分は台帳の凡例に従い、批判・留保の側（C）は区分を添える。各社の運用は、その会社の自称である。

## 文書だけで判断できる項目

### SLO の決定記録

- [ ] 利用者の困りごと（どの利用者が、何で困るか）が書かれ、SLI がその利用者の側から測る形で決まっている（本 skill の整理。S022 は、SLI を利用者の側から測るのがよいと述べる）
- [ ] SLI が、計測の方式（事象ベースか時間ベースか）・分子と分母の単位・何を良い事象（良い状態）と数えるか・どこで測るかが決まっている（S005 は、良い事象の数 ÷ 全事象の数の比を勧める。方式・単位・数え方・測る場所は本 skill の整理）
- [ ] 目標の値と期間が書かれ、通常のサービスで 100% や「9 の数」だけで止めず、時間ベースでは許容する停止時間の合計、事象ベースでは許容する失敗件数で言い直されている（S003 は、100% はおそらく正しい目標ではないと述べる。S008 は、停止の合計・頻度・長さに言い換えられると述べる。頻度や 1 回あたりの長さは、個別の要件があるときだけ確かめる。安全上の要求がある系は個別の要件を確かめる。本 skill の整理（計算））
- [ ] SLO の数が、優先順位の議論で引ける少数に絞られている（S002 は、優先順位の議論で引けない SLO は、おそらく持つ価値が低いと述べる）
- [ ] 外向けの約束があるなら、内部の SLO と分けて書かれている（本 skill の整理）。SLA の法的な効力・契約の判断は、ここでは扱わない。外向けより厳しい内部の SLO は、外から見える前に慢性の問題へ手を打つ余裕を与える（S002）。SLA の定義は S001
- [ ] 対象の SLI を満たすのに欠かせない依存先と、足りないときの緩和策が書かれている（S007。記録による判定は「実測や相談者のデータが要る項目」で行う）
- [ ] 計測できる記録の期間と粒度が書かれている。記録が短いときは、暫定の目標と見直す日付が付いている（本 skill の整理）
- [ ] error budget の方針に、数える期間・何を消費に数えるか・消費の段階・止める範囲と例外・決める人・見直す日が書かれている（S004 が支えるのは、1 四半期の中という期間の枠だけ。四半期は Google の例。残りは本 skill の整理。S006 は架空の例の文書で、構成の参考。値は相談者が決める）
- [ ] 消費したときに誰が何を決めるかが書かれ、数式だけで止まる形になっていない。罰としてでなく、信頼性に集中してよい許可として書かれている（S006。例の文書の記述）
- [ ] 止める決めごとへの経営の合意の有無と記録が書かれ、合意が無いときは代わりの扱いが書かれている（S115。決めごとは経営が命じない限り受け入れられないかもしれない、という推進側の留保）
- [ ] 却下した案・失うもの・見直す条件と日付が書かれている（本 skill の整理）

### 可観測性と警報の設計

- [ ] 人を呼ぶ通知が、利用者の困りごと（症状）に結びつき、対処でき、判断を要るものに限られている（S009・S010・S011・S012）
- [ ] 通知の種類（呼び出し・チケット・画面）が分けられ、急がないが放置できないものの扱い先が決まっている（S010 は、機械的な応答で済むものをページにしないと述べる範囲。扱う先の設計は本 skill の整理）
- [ ] 最初に測る信号が、要求側（遅延・トラフィック・エラー・飽和。S018）と資源側（利用率・飽和・エラー。S019）のどちらの考えで選ばれたか書かれている（使い分けは本 skill の整理）
- [ ] 信号ごとに、何の問いに答えるために取るかが書かれ、3 種類をそろえたこと自体を可観測性の達成としていない（S031。C。本 skill の整理）
- [ ] 警報の評価が、precision（検知したもののうち意味のある事象に当たる割合。S013 の引用が言う）と、recall（意味のある事象のうち検知できた割合。引用に定義は無く、本 skill の整理）に分けて書かれている
- [ ] SLO に結ぶ警報では、予算を評価する期間・長い窓・その窓で予算の何割を消費したら呼ぶか、を相談者が先に決め、そこから倍率と閾値が求められ、長い窓と短い窓の両方で超えたときに発報する形になっている（本 skill の整理）。前提（窓の中の対象リクエスト数が時間の比率どおり）が確かめられ、偏るときは窓の中の失敗件数を期間の予算件数に照らしている（本 skill の整理。S014 が言うのは、短い窓を長い窓の 1/12 にする目安だけで、ワークブックの章の指針）
- [ ] 計測の名前の規約が決まっている（S023 は、共通の命名にそろえる利点を、コード・ライブラリ・基盤をまたいで標準化できることと述べる。規約を決めること自体は本 skill の整理）
- [ ] 標本化の方針と、ラベルの値の組み合わせが増える費用の扱いが書かれている（S024・S025）
- [ ] 遅延を平均だけで語らず、分位点が推定値であることが書かれている（S026 は、Prometheus の histogram と summary の文脈で、分位点は推定値と述べる。平均だけで語らないは本 skill の整理）
- [ ] 通知の数の上限と、超えたら何をするかが決まっている（本 skill の整理。S015 は 1 回の当番あたりの事故の件数の目標で、通知の数ではない。Google の運用の自称で、基準ではない）。上限を超えて警報を消す・通知にしないときは、外す前に、警報とは別の記録で、その警報が実害を検知していたかを確かめる（本 skill の整理）
- [ ] 当番が上げる条件と、上げる先が決まっている（S016。PagerDuty の運用の自称）
- [ ] 警報ごとに、受ける人・対処の手がかり・見直す時期が書かれている（本 skill の整理）

### 公開の安全の方針

- [ ] 変更の種類（コード・設定・データ・形式）ごとに、公開の段階が書かれている。設定とデータも段階的に広げる扱いになっている（本 skill の整理。S053 は、Google の更新の大半を少しずつ進める運用を述べる（自称）。設定・データは S121・S123 の自称の報告を参考にする）。速さが要る経路（止血の切り替えなど）も、一斉公開の条件（影響が許容範囲に収まる・切り戻せる・重要な業務を止めない）を満たすときに限って一度に出してよい。満たさない緊急の変更は、一斉公開の例外にするかを含めて相談者が決める。そのときも、切り戻せる変更なら切り戻す条件を、切り戻せない変更なら前へ直す条件と担当を、先に置く。影響範囲の上限も先に置く（本 skill の整理）
- [ ] 切り戻す条件（判定の指標・比べる対象・時間・決める人）が、公開の前に書かれている（本 skill の整理）
- [ ] カナリアを使う場合、評価して広げるかを決める手順と、同時に走らせる数が書かれている（S057。対照群と比べる様式は引用の範囲外で、本 skill の整理）
- [ ] 戻せない変更（形式・データ）が分けて書かれ、新旧の両方に対応する版を先に出す段取りが決まっている（S059 はデータベースのスキーマの場合、S061 は互換性の無い変更を 3 段に分ける方法、S063 は Amazon の自称）。戻せない段には、前へ直す条件と担当が書かれている（本 skill の整理）
- [ ] feature flag を使う場合、数が少なく保たれ、寿命と消す日が決まっている（S060 は、在庫として少なく保つと述べる。寿命・消す日は本 skill の整理。全員に一括でオンにするだけなら、段階公開として扱わない。本 skill の整理）
- [ ] 自動化には、速さの制限・エラーの閾値・承認といった歯止めが付いている（S103。AWS の指針は、歯止めを付けられると述べる）
- [ ] 段階の数と間隔の理由が、公開の頻度と失敗の影響に照らして書かれている。一斉の公開を選ぶ場合は、失敗の影響が許容範囲に収まる理由が書かれ、切り戻せない変更や重要な業務の停止がある変更でないことが確かめられている（本 skill の整理）

### 事後検証の文書

小さな事象で、概要と対応項目だけの様式を使う場合は、省いた項目を該当なしにしてよい（SKILL.md の事後検証の型と同じ）。

- [ ] 書く条件が事前に決まり、この事象がどの条件に当たるかが書かれている（S041 は、事後検証を書く基準を事前に決めておくことだけを支える。事象への当てはめは本 skill の整理）
- [ ] 概要の影響が、測れた数字と、測れていない部分に分けて書かれている（本 skill の整理）
- [ ] 時系列に、時刻の基準と、各行の根拠（記録・口頭・推測）が書かれている（本 skill の整理）
- [ ] 寄与要因が、複数あれば分けて書かれ、1 つなら、そう判断した理由が書かれている（本 skill の整理）。原因の一行と「誰か」に収束していない（S045 は、大きな失敗（破局）に限って、小さな失敗の重なりが要ると述べる。S046・S051 は批判の側で C。S117 は言い換える案を述べる C）
- [ ] 当事者の判断が、その時の手元の情報でなぜ妥当に見えたかが書かれ、結果を知った後の見え方で評価していない。聞き取りが済んでいなければ、未確認と書かれている（S047 が支えるのは、後知恵が事後の評価に偏りを生むことだけ。妥当に見えた理由と聞き取りの扱いは本 skill の整理）
- [ ] 個人やチームを咎める記述が無く、責めないことが責任を問わないことと混ざっていない（S041 は、人やチームを責めない範囲だけを支える。責めないことは、責任を問わないことと同じではない、は本 skill の整理。S048 は、安全と説明責任の釣り合いを述べる）
- [ ] 対応項目に、内容・担当・期限・追跡の方法が書かれている（S044 は、期限と、催促・報告による追跡だけを述べる。Atlassian の運用の自称。内容・担当は本 skill の整理。期限の値は相談者が決める）
- [ ] 事象の後の会議の日時が決まっている（S043。PagerDuty の運用の自称。日数は相談者が決める）
- [ ] 平均の指標（MTTR など）を、文脈なしの単独の結論にしていない（S116・S118。ともに C。S116 は 1 人の著者の分析）
- [ ] 未確認・推測が、分かっていることと分けて書かれている（本 skill の整理）

## 実測や相談者のデータが要る項目

ここは、文書を読むだけでは「はい」にできない。相談者の計測・運用の記録が足りないときは「不明」とし、何を測るかを書く。記録が示され、それで確かめられれば、「はい」または「いいえ」を付ける。計画があるだけで、結果の項目を「はい」にしない。

- [ ] SLI の実測が記録の期間にわたって出ていて、SLO の目標に対する達成が確かめられている。未達は「いいえ」。値は相談者が決め、ここでは実測していない（本 skill の整理）
- [ ] error budget の消費が計測され、方針の段階に照らされている（本 skill の整理。S004 が支えるのは、1 四半期の中という予算の枠だけ。計測は相談者の記録）
- [ ] 選んだ SLI が、利用者の困りごとの記録（問い合わせ・離脱など）と突き合わされ、合っている（本 skill の整理）
- [ ] 対象の SLI と同じ単位と分母（時間ベースなら時間、事象ベースなら要求）で、欠かせない依存先か代わりの経路が使えた割合を見る。相談者の実測の記録で確かめ、記録が無ければ不明。公開の SLA や目標値は約束で、実測の代わりにならない。公開の観測の結果（稼働の履歴など）は、対象の経路・期間・粒度が合えば使える（S007。本 skill の整理）
- [ ] 警報の precision（鳴った警報のうち、意味のある事象に当たった割合。S013）と recall（意味のある事象のうち、検知できた割合。本 skill の整理）が数えられている。意味のある事象は、警報とは別の記録（障害・問い合わせ）と突き合わせて決める。対処した件数では数えない（本 skill の整理）
- [ ] 通知の件数が、決めた上限に収まっている（本 skill の整理。S015 は事故の件数の自称の例で、通知の数ではない）。上限を超えて警報を消す・通知にしないときは、外す前に、警報とは別の記録で、その警報が実害を検知していたかを確かめる（本 skill の整理）
- [ ] 警報の閾値が、過去の記録に当てて、鳴るべき時に鳴り、鳴らない時に鳴らないと確かめられている（本 skill の整理）
- [ ] 計測の費用（時系列の数・保存量）が、相談者の予算に収まっている（本 skill の整理。S025 を見る）
- [ ] 切り戻しが、決めた条件で実際に戻せると試されている。試していなければ「不明」とする。経路やデータを戻す方式では、戻した後も、新しい版で受けた書き込みが失われず、旧版で読め、処理中の取引を扱えることを確かめている（本 skill の整理。SKILL.md の段 2 と同じ条件）
- [ ] 段階公開の各段で、判定の指標が実際に取れている（本 skill の整理）
- [ ] 事後検証の時系列が、ログ・チャット・変更の記録と突き合わされている（本 skill の整理）
- [ ] 対応項目が、決めた期限内に完了している。追跡の記録で確かめる（S044。自称の運用）
- [ ] 上の層が、犯人を求めず、事後検証の結果を受け止めている。相談者の組織の様子が要る（S117。C。現場が責めない振り返りをしても、上の層が犯人を求めれば、それが文化を決める、という指摘）

## 使い方

- 制作モードでは、案を出す前に全項目を見る。レビューでは、先に見る価値が高い（本 skill の整理）次の群から見る: SLO の決定記録の「依存先」と「error budget の方針」、警報の「通知の種類」、事後検証の「寄与要因」と「対応項目」
- 「不明」が多いときは、文書を断定せず、相談者へ確認する事項として返す
- 項目は、出典が定めた合格基準ではない。出典の主張と、本 skill の整理を、根拠の欄で分けている
- 障害の最中の相談には使わない。平時の設計と障害の後の文書の点検である

## 判定の付け方

| 判定 | 意味 | 返し方 |
|---|---|---|
| はい | 文書や記録で確かめられた | 根拠を 1 行で添える |
| いいえ | 使う要素の記載が欠けている、反している、目標が未達 | 改善案を、得るものと失うものの両面で書く |
| 不明 | 判定に要る証拠が足りない。その要素を使うかどうかを確かめられない場合を含む。計測や記録が要る | 何を測るかと、誰が測るかを書く。証拠が示されたら、はい・いいえに改める |
| 該当なし | その要素を使っていないと確かめられた場合に限る（フラグを使わない・外向けの約束が無いなど）。小さな事象で簡略版の様式を使い、その様式が省く項目も含む | 該当なしの理由を 1 行で添える |
