# 運用の歴史: 作った人が運用する・SRE・社内の基盤

運用の考え方が、いつ、どんな規模・組織・道具の前提のもとで語られたかをまとめたファイル。年表の暗記用ではなく、「いま採ろうとしている運用の型は、どんな前提で生まれたか」を確かめる材料である。開くのは、相談者が背景や由来を求めたとき、運用の型（当番・SLO・基盤チーム）を決める前、「Google がそうしている」「DevOps の定石だ」と言われたときの 3 つである。中心の問いは次の 1 つで、本 skill の整理である。

> その運用の型は、どんな規模・組織・ツールの制約の中で生まれたか。今回の系・チームでも成り立つか。

出典が薄い箇所は、薄いと書く。

## 読み方と記法

- 時点: 記述は出典ごとの取得日の時点。各項目は[出典台帳](sources.md)で見る
- 年は「始まり」と「公表」を分ける。始まりは、出典が実務の開始として書いている時期。公表は、資料の媒体・日付の年。実務は公表より前に始まっていることが多い。一次で確かめていない年は、未確認と書く
- S 番号が支えるのは、その項目の引用ブロックに逐語であることだけである。要旨にだけ書かれた年（2003 年の記述、DORA の各年）は、「要旨の記述」「頁によれば」と断る。それ以外は「本 skill の整理」「推測」と書く
- 区分は台帳の凡例に従う。B（第三者の頁経由）と、批判・留保の側の C は、区分を添えて要旨にし、本人の発言としては示さない
- 各社の記事は、その会社の自称である。区分は A のまま、「自称」と書いて一般化しない
- 見取り図の各行は、引用が言う範囲だけを書く。行どうしを結ぶのは「繰り返すパターン」で、すべて本 skill の整理（推測）である
- 回答では、頼まれない限り歴史を講釈しない。判断の根拠として 1 行で使う

### 時代ごとの前提（規模・組織・ツール）

時代は一直線に交代しない。「作った人が運用する」は、2006 年の Amazon の対談（S108。自称）で語られた。Google の SRE（Treynor が 2003 年に Google で運用チームを率いた、という S111 の要旨の記述。始まりの年とは書いていない）は、運用チームの設計をソフトウェア技術者に任せた型で、別の型である。Amazon の対談（2006 年）は「DevOps」の語（2008 年後半）より前である。SRE との前後は、始まりの年を確かめていないので言えない。SRE の書籍は、実務の回想であって始まりではない（本 skill の整理）。以下の前提は、引用の語の範囲を除き、本 skill の整理（推測）である。

- 作った人が運用する・DevOps（2000 年代後半〜）
  - 組織: 開発が運用へ壁越しに投げる型をやめ、作ったチームが運用までを受け持つ（S108。自称）。開発と運用は、決まった責任の範囲に閉じ、責め合う文化に苦しんできた（S109。講演概要）
  - ツール: サーバーを数秒で立ち上げられる時代になった、と Fowler は書く（S079。2016 年の記述）。記録されない場当たりの変更が、構成のずれの原因の一例である（S083）。変更可能なサーバーに構成管理の道具で定義を当て続ける方式では（この前提の文脈は引用に無く、本 skill の整理）、実際には構成を完全には管理できない（S084）
  - 問う点: 運用まで受け持つ人数と当番の体力があるか。Amazon・Flickr の規模と、自チームの規模は同じか
- SRE（Treynor が 2003 年に運用チームを率いた、と要旨にある。始まりの年とは書いていない。序章が 2016 年初めの時点で書かれている）
  - 組織: SRE は、ソフトウェアの技術者に運用チームを設計させた結果だと書く（S111。自称）。DevOps の、いくつか独自の拡張を持つ特定の実装とも見られると書く（S111）。error budget で止める決めごとは、経営が命じない限り開発側に受け入れられないかもしれないとも書く（S115。Google の例で、期間は四半期。止める線は相談者の方針で決める。本 skill の整理）
  - 規模: S111 が書くのは成り立ちである。Google の規模と採用が前提で、そのまま他社に移せる型ではない、は本 skill の整理
  - 問う点: 移すのは型か、道具か。自チームに SRE を名乗る人員も、止める決めに合意する経営もあるか
- 社内の基盤をプラットフォームとして出す（年は未確認）
  - 組織: 基盤を、流れに沿ったチームの配信を速める社内向けの製品として出すチーム（S113）。DevOps が約束した部門横断の協力を、明示的な形にしたものとして出てきたという CNCF の見方がある（S114。因果の事実としては確かめていない）。利用者の声を聞かない、または上からの命令に頼って採用させる基盤は、ほぼ確実に反発を受け、約束された価値の多くを逃すと書く（S114）
  - 問う点: 基盤の利用者は何チームか。製品として扱う人員と、利用者の声を聞く経路があるか

## 繰り返すパターン（本 skill の整理）

次の型は、出典を横断して読み取ったもので、出典が述べた法則ではない。すべて推測で、例外は多い。

1. 分けた責任を、再び結ぶ動き: 開発と運用の壁（S108）、責め合う文化（S109）、運用チームの設計をソフトウェア技術者へ（S111）、基盤を社内の製品として出す（S113）が並ぶ。同じ動きの繰り返しと見るのは推測である
2. 大きな組織の型の移植: Amazon の自称（S108）、Google の成り立ち（S111。規模と採用が前提という見方は本 skill の整理）は、前提となる規模・組織が違う。型でなく、前提を先に確かめる
3. 道具の変化と、手作業のずれ: サーバーを数秒で立ち上げられる（S079）と、変更可能なサーバーに定義を当て続ける方式では（この前提の文脈は引用に無く、本 skill の整理）、実際には構成を完全には管理できない（S084）が並ぶ。道具が安くなっても、運用の判断は残る
4. 指標が先に広まり、読み方が後から直る: MTTR への批判と留保が 2021 年（S116・S118。いずれも C。S116 は 1 人の著者の分析）と 2022 年（S117。C）にあり、DORA の MTTR の改称・再定義は 2023 年である（S096）。両者の関係は確かめていない。3 本柱の語にも批判がある（S031・S032。C）。読み方が直る前の資料を、当時の名称として読む
5. 原因を 1 つに絞る語りと、その批判: 孤立した原因は無いという論考（S046。C）、寄与要因への言い換え案（S117。C）、SRE の書籍の寄与した原因（S041）が並ぶ。語の使い方は分野・著者で揃っていない
6. 速さと安定の綱引き: 速さと安定はトレードオフではないという DORA の研究の主張（S094。DORA の自称）と、error budget が尽きたら四半期の残りのリリースを止める決めごと（S115。Google の例で、期間は四半期。経営が命じない限り受け入れられないかもしれない、という留保つき。止める線は相談者の方針で決める。本 skill の整理）が並ぶ。判断の対象が違う（本 skill の整理）
7. 事例の自称は条件つき: 各社の事例は、規模・組織・負荷が違う。一般化しない

## 相談の種類別の使い方

問いはすべて本 skill の整理である。出典は、関係する項目の番号で、問いを支えるものではない。

| 相談の種類 | 確かめる問い | 関係する出典 |
|---|---|---|
| SRE の型を導入したい | Google の型が前提にした規模・採用は、自チームにあるか。型でなく道具だけを移していないか | S111・S115 |
| 運用の責任の置き方 | 作ったチームが運用まで受け持てる人数・当番の体力か。壁を壊す効果は、自称の事例以外で確かめたか | S108・S109 |
| 基盤チームを作りたい | 利用者は誰で、声を聞く経路はあるか。命令で使わせていないか | S113・S114 |
| SLO・error budget の合意 | 止める決めごとに、経営の後ろ盾があるか。通常のサービスで 100% を目標にしていないか | S003・S115 |
| 配信の指標の導入 | どの年の指標か。指標を目標にしていないか。性質の違うアプリを比べていないか | S094・S095・S096 |
| 事後検証の文化 | 現場だけが責めない振り返りをして、上の層が犯人を求めていないか | S041・S048・S117 |
| 平均の指標・MTTR | 文脈なしに平均を示していないか。改称前の定義か | S096・S116・S118 |
| IaC・手作業の変更 | 構成のずれの検出範囲は決まっているか。道具の時代の前提を移していないか | S079・S083・S084 |
| 「他社がそうした」「定石だ」 | 事例は自称で、規模・組織が違わないか。語でなく中身で語る | S108・S111・S114 |
