# 例: 可観測性の設計案をレビューして返す（社内の予約 API）

架空の社内予約 API の設計書が、「全部の経路を全部のレベルで取る」案を出している。それを、レビュー観点チェックリストの可観測性と警報の群を先に選び、その群の項目だけで判定し、返答にまとめる例。返答の文面と、判定表を載せる。題材は架空の事業者・数値で、実在の製品・企業を写さない。他の人の可観測性の設計書を見てほしいと頼まれたとき、または、自分の案を出す前に点検するときに開く。項目の全文は [レビュー観点チェックリスト](../references/review-checklist.md) にある。

## 依頼

- 事業者: 架空の「かもめ工業」。社員向けの設備予約 API「かもめ予約 API」を運用する。開発は 6 人、当番は平日の日中のみ（架空の前提）
- 設計書の案: 約 40 本ある API の全経路で、ログは最も細かいレベルまで、メトリクスは全経路、トレースは全要求を、標本化せずに取り、1 つの保存先に 90 日残す（架空の前提）。警報は、現行のまま
- SLO: まだ置いていない。警報を SLO に結ぶ設計も無い（相談者に確かめた。架空の前提）
- 設計書に書かれていないこと: 何の問いに答えるために取るのか。ログの形式（現状は自由な文字列で、構造化されたログは無い）。名前の規約。費用の見積もり。警報の見直し
- 相談者の申告: 警報が 1 日 40 件鳴り、当番が通知を見なくなっている。40 件の内訳の記録は無く、実測は無い
- 依頼文: 「全部取っておけば、何が起きても調べられるはず。この案で進めたいので、見てほしい」

## 目的の一文

設計案を、チェックリストの項目で判定し、足りない点と、確かめるべき記録を、誰がいつ確かめるかまで含めて返す。

## 削るもの

| 削るもの | 理由と削り方 |
|---|---|
| 選ばなかった群の項目（SLO・公開・事後検証） | 依頼の対象は可観測性と警報の設計なので、この群を先に選ぶ。判定は、文書だけで判断できる 13 項目と、実測が要る項目のうち警報・通知・計測の費用に関わる 5 項目の、全 18 項目（13 + 5 = 18。本 skill の整理（計算））に限る。選ばなかった群は判定しない。項目は足さない |
| 計測の実装手順・ダッシュボードの作り方 | 返すのは判定と、足りない点。実装は設計書の筆者と決める。図の描き方は designer-dataviz（導入されていれば） |
| 計測製品の選定・比較 | 特定の製品の助言はしない（範囲）。可観測性の製品の会社の主張は、利害があるものとして扱う |
| 警報の閾値の全件の計算 | 実測が無い。例には 1 つの警報の断片だけ載せ、値は例の設定とする |
| 本番の診断 | 40 件の中身は見ていない。ここでは判定の根拠にしない |
| ログに入れてよい個人情報の判断 | 脅威と認可の領域。導入されていれば engineer-security へ案内する |

## 構成

```text
依頼の対象の群（可観測性と警報）を先に選ぶ → 設計書を読む → その群の 18 項目に、はい / いいえ / 不明 / 該当なし を付ける
→ いいえと不明を、改善案か確認事項に結びつける → 結論を先に書いて返す
→ 相談者が記録を示したら、不明をはい・いいえに改める
```

- 順序: 先に見る価値が高い項目（警報の「通知の種類」）から返す
- 実測が要る項目は、記録が無ければ「不明」とし、何を・誰が・いつ確かめるかを 1 行で返す。計画があることを理由に、結果の項目を「はい」にしない

## 仕様

出典のある値には S 番号を付ける。それ以外は本 skill の整理か例の設定で、基準ではない。

| 最初に測る信号 | 要求側は遅延・トラフィック・エラー・飽和。資源側は利用率・飽和・エラー | S018 は、利用者に面した系で 4 つしか測れないなら、この 4 つに集中すると述べる。S019 は、資源ごとにこの 3 つを確かめる方法で、調査の早い段階で使うと述べる。使い分けは本 skill の整理 |

| 警報の評価 | 検知したもののうち意味のある事象に当たる割合（precision）と、意味のある事象のうち検知できた割合（recall）に分けて書く | S013 の引用が言うのは precision の定義まで。recall の定義は引用に無く、本 skill の整理 |

| 通知の数の上限 | 上限と、超えたら何をするかを先に決める。上限と同じ単位・期間で数える | 本 skill の整理。S015 は 1 回の当番あたりの事故の件数の目標で、通知の数ではない（Google の運用の自称） |

| 名前の規約 | 共通の命名にそろえる | S023 は、その利点を、コード・ライブラリ・基盤をまたいで標準化できることと述べる。規約を決めること自体は本 skill の整理 |
| 標本化・ラベル | 全件を取らず、方針を決める。値の組み合わせが多いラベルは、費用を見て入れるかを決める（本 skill の整理） | S024 は、標本化を費用を下げる有効な方法の 1 つと述べる（文書の主張）。S025 は、ラベルの値の組み合わせごとに新しい時系列になると述べる |

| 日付 | レビュー 2026-11-20（金）、次のレビュー会 2026-12-04（金）、上限の確認 2026-12-18（金） | 例の設定 |

## 文言

### レビューの返答

> 結論: 「全部の経路を全部のレベルで取る」案は、このままでは勧めません。取る量を増やしても、当番が通知を見なくなっている問題は解けません（推測。通知の数は警報の設計の問題で、案は触れていない）。先に警報を、利用者の困りごと（予約が確定しない・遅い）に結びつくものに絞る方向で見直し、取る信号は、答えたい問いから選んでください。
>
> 判定の内訳: いいえ 7、不明 10、該当なし 1、はい 0（全 18 項目。表は下）。
>
> 置いた仮定: 当番は平日の日中のみ。1 日 40 件は申告で、内訳は見ていない。夜間の利用と、許容できる復旧時間は分からないので、夜間・休日に待てない障害をどう知らせるかは未決で、代わりの連絡先を用意するか、当番の体制と利用者への約束（SLO）を見直すかは、相談者が決めます。翌営業日の確認に回してよいのは、翌営業日まで待てると確かめた警報だけです。
>
> 先に直す点: (1) 人を呼ぶ通知を、症状に結びつき、対処でき、判断を要るものに絞り、残りはチケットか画面に移す。ただし、移す候補の警報が、過去 4 週間に実際の障害を拾っていたかを確かめ（4 週間で拾っていなくても、まれな障害は見えない）、拾っていたなら代わりの検知を用意してから移し、見逃しが出たら戻す。得るもの: 当番が通知を読める。失うもの: 検知が遅れる場合がある。警報とは別の記録（問い合わせや障害の記録）から、検知できた割合を、減らす前後で比べる。(2) 信号は、遅延・トラフィック・エラー・飽和から始め、信号ごとに答える問いを書く。3 種類をそろえることは目的ではない。得るもの: 取る理由が言える。失うもの: 書く手間。(3) ログを構造化し、名前を決める。現状は自由な文字列で、案にも形式が無い。得るもの: 集計と絞り込みができる。失うもの: 既存のログ出力の書き換え。(4) 全件・全レベルをやめ、標本化と保存期間を決める。得るもの: 費用が見積もれる。失うもの: 後から調べたい情報が残らない場合がある。
>
> 選ぶ条件: まず予約確定の経路だけを詳しく取って試します。経路を広げるたびに費用を測り直し、予算に収まるときだけ次の経路へ進みます。切り替える合図: 症状の警報で拾えない障害が続いたら、その経路の原因側の信号を足します。既知の壊れ方は監視、未知の壊れ方は調べる力、と分けて持ちます（本 skill の整理）。
>
> 確かめること（不明の 10 項目）は、判定表の理由の欄に、担当と日付つきで書きました。
>
> 確かめられないこと: 40 件の内訳、費用、警報の効果は、ここでも設計書にも計測がありません。判定は、設計書の文面だけに基づきます。

## コード断片

警報規則の最小の断片（記法は例。特定の製品の書式ではない。値は例の設定）。

```text
alert: booking-confirm-slow
symptom: 予約確定の応答のうち、2 秒以内に返った割合
condition: 直近 10 分で、要求が 20 件以上あり、2 秒以内の割合が 95% を下回る
notify: 呼び出し（平日の日中の当番）
else: 待てると確かめた遅れ → チケット（確かめていないものは未決）
hint: 直近の公開・依存先の状態
review: 四半期ごと
# 限界: 遅延だけを見る規則。エラーの規則は別に置く
# 要求が 20 件未満・0 件のときの扱いは未決
# 夜間の受け手は未決（当番は平日の日中のみ）
# チケットに回すのは、待てると確かめた遅れだけ
```

構造化されたログの 1 行（記法は例。名前は例の設定）。

```text
time=2026-11-20T10:21:03+09:00 level=info route=/bookings/confirm status=200 duration_ms=840 request_id=r-0042
```

## 初見検証

設計書の筆者と、当番のリードが、返答だけで、次にすることを言えるかを確かめる。

| 読む人 | 返答だけで言えること | 言えないときの直し方 |
|---|---|---|
| 設計書の筆者 | 案を退けるのでなく、先に警報を絞り、一部の経路から試すことだと言える | 結論に、先にすることを 1 文で置く |
| 当番のリード | 自分が数える項目と日付（2026-12-04 までの警報の記録）を言える | 表の理由に、人・対象・日付を書く |
| 新しい当番 | 不明とした理由が、記録が無いことだと言える | 理由に、足りない記録を書く |
| 運用の担当 | 閾値は、過去の記録に当てて確かめるまで確定でないと言える | 実測の行に、確かめ方を書く |

## 点検

- 依頼の対象の群（可観測性と警報）だけを判定し、選ばなかった群は判定していない。判定表が、チェックリストの項目に対応し、18 行で、内訳（いいえ 7・不明 10・該当なし 1・はい 0）の合計と一致する
- 実測が要る項目に、記録が無いまま「はい」を付けていない。不明の項目ごとに、誰が・何を・いつまでに確かめるかが書かれている
- 案を一律に退けず、一部から試す条件と、切り替える合図が書かれている。得るものと失うものが両面で書かれている
- 「1 日 40 件」を申告として扱い、実測した値にしていない。効果は推測と書いている
- 数値（人数・上限・閾値・日付）が、例の設定と明記されている
