# 例: 可観測性の設計案をレビューして返す（社内の予約 API）

架空の社内予約 API の設計書が、「全部の経路を全部のレベルで取る」案を出している。それを、レビュー観点チェックリストの可観測性と警報の群を先に選び、その群の項目だけで判定し、返答にまとめる例。返答の文面と、判定表を載せる。題材は架空の事業者・数値で、実在の製品・企業を写さない。他の人の可観測性の設計書を見てほしいと頼まれたとき、または、自分の案を出す前に点検するときに開く。項目の全文は [レビュー観点チェックリスト](../references/review-checklist.md) にある。

## 依頼

- 事業者: 架空の「かもめ工業」。社員向けの設備予約 API「かもめ予約 API」を運用する。開発は 6 人、当番は平日の日中のみ（架空の前提）
- 設計書の案: 約 40 本ある API の全経路で、ログは最も細かいレベルまで、メトリクスは全経路、トレースは全要求を、標本化せずに取り、1 つの保存先に 90 日残す（架空の前提）。警報は、現行のまま続ける
- SLO: まだ置いていない。警報を SLO に結ぶ設計も無い（相談者に確かめた。架空の前提）
- 設計書に書かれていないこと: 何の問いに答えるために取るのか。ログの形式（現状は自由な文字列で、構造化されたログは無い）。名前の規約。遅延の見方（平均以外に何を見るか）。ラベルの値の組み合わせの扱い。警報の評価（precision・recall）。費用の見積もり。警報の見直し
- 現行の警報の運用（通知の種類・上限・受け手・上げる条件）: 設計書の外にあり、示す資料はまだ見ていない（資料不足。架空の前提）
- 相談者の申告: 警報が 1 日 40 件鳴り、当番が通知を見なくなっている。40 件の内訳の記録は無く、実測は無い
- 依頼文: 「全部取っておけば、何が起きても調べられるはず。この案で進めたいので、見てほしい」

## 目的の一文

設計案を、チェックリストの項目で判定し、足りない点と、確かめるべき記録を、誰がいつ確かめるかまで含めて返す。

## 削るもの

| 削るもの | 理由と削り方 |
|---|---|
| 選ばなかった群の項目（SLO・公開・事後検証） | 依頼の対象は可観測性と警報の設計なので、この群を先に選ぶ。判定は、この群の文書だけで判断できる 13 項目と、実測が要る 6 項目の、全 19 項目（13 + 6 = 19。本 skill の整理（計算））に限る。選ばなかった群は判定しない。項目は足さない |
| 計測の実装手順・ダッシュボードの作り方 | 返すのは判定と、足りない点。実装は設計書の筆者と決める。図の描き方は designer-dataviz（導入されていれば） |
| 計測製品の選定・比較 | 特定の製品の助言はしない（範囲）。可観測性の製品の会社の主張は、利害があるものとして扱う |
| 費用・警報の閾値・recall の数え方の計算 | 実測が無く、単価も相談者の記録にある。値と数え方は、相談者が先に決めて書く。例には 1 つの警報の断片だけ載せ、値は例の設定とする |
| 本番の診断 | 40 件の中身は見ていない。ここでは判定の根拠にしない |
| ログに入れてよい個人情報の判断 | 脅威と認可の領域。導入されていれば engineer-security へ案内する |

## 構成

```text
依頼の対象の群（可観測性と警報）を先に選ぶ → 設計書を読む → その群の 19 項目に、はい / いいえ / 不明 / 該当なし を付ける
→ いいえと不明を、改善案か確認事項に結びつける → 結論を先に書いて返す
→ 相談者が記録を示したら、不明をはい・いいえに改める
```

- 順序: 点検表の順に返す。先に見る価値が高いのは通知の種類
- 実測が要る項目は、記録が無ければ「不明」とし、何を・誰が・いつ確かめるかを 1 行で返す。計画があることを理由に、結果の項目を「はい」にしない
- 設計書に書くべきことが無いと確かめたものは「いいえ」（欠落）、設計書の外の資料が足りず判定できないものは「不明」（資料不足）と、理由の欄で分ける

## 文言

### レビューの返答

> 結論: 「全部の経路を全部のレベルで取る」案は、このままでは勧めません。取る量を増やしても、当番が通知を見なくなっている問題は解けません（推測。通知の数は警報の設計の問題で、案は触れていない）。現行の警報は、方針と規則を確かめるまで評価できないので、先に確かめ、取る信号は、答えたい問いから選んでください。
>
> 判定の内訳: いいえ 6、不明 10、該当なし 3、はい 0（全 19 項目。表は下）。
>
> 置いた仮定: 当番は平日の日中のみ。1 日 40 件は申告で、内訳は見ていない。現行の警報の運用（通知の種類・上限・受け手）は、設計書の外にあり、資料を見ていない。夜間の利用と、許容できる復旧時間は分からないので、夜間・休日に待てない障害をどう知らせるかは未決で、代わりの連絡先を用意するか、当番の体制と利用者への約束を見直すかは、相談者が決めます。翌営業日の確認に回してよいのは、翌営業日まで待てると確かめた警報だけです。
>
> 先に直す点: (1) 現行の警報の方針と規則を確かめる。確かめるまで、現行の警報が症状に結びつくかは「不明」で、現行のままです。確かめた結果、症状に結びつかない・対処できない通知があれば、人を呼ぶ通知を、症状に結びつき、対処でき、判断を要るものに絞り、残りはチケットか画面に移す案を採ります（この案の条件: 移す候補の警報が過去に検知した実害のある事象を、警報とは別の記録で確かめる。実害を検知していた警報は、代わりの検知を用意してから移す。チケットに移してよいのは、遅れて対処しても利用者への影響が許容内のときだけ）。得るもの: 当番が通知を読める。失うもの: 検知が遅れる場合がある。(2) 信号は、遅延・トラフィック・エラー・飽和から始め、信号ごとに答える問いを書く。3 種類をそろえることは目的ではない。得るもの: 取る理由が言える。失うもの: 書く手間。(3) ログを構造化し、名前を決める。現状は自由な文字列で、案にも形式が無い。得るもの: 集計と絞り込みができる。失うもの: 既存のログ出力の書き換え。(4) 全件・全レベルをやめ、標本化と保存期間を決める。ラベルの値の組み合わせの数の上限と、超えたときの扱いは、先に決めて書いてください。得るもの: 費用が見積もれる。失うもの: 後から調べたい情報が残らない場合がある。(5) 遅延は、設計書に平均以外の見方が書かれていません（欠落）。平均だけで語らず、何で見るかを書いてください。
>
> 選ぶ条件: まず予約確定の経路だけを詳しく取って試します（1 経路・1 週間は例の設定）。経路を広げる前に、対象の経路全体・保存期間・単価での費用の見積もりを、相談者が確かめてください（単価と見積もりの値は未決）。経路を足すたびに、実績と見積もりを照らし、予算に収まるときだけ次の経路へ進みます。切り替える合図: 症状の警報で拾えない障害が続いたら、その経路の原因側の信号を足します。既知の壊れ方は監視、未知の壊れ方は調べる力、と分けて持ちます（本 skill の整理）。
>
> 先に決めて書くこと: 通知の上限（単位・期間）と超えたときの対応、recall を数える記録、ラベルの値の組み合わせの上限、夜間・休日の待てない障害の連絡先、警報の対象と夜間の受け手は、試行の開始（2026-11-27）までに、相談者が決めて書いてください。決まらなければ試行を始めません。
>
> 確かめること（不明の 10 項目）は、判定表の理由の欄に、担当と日付つきで書きました。
>
> 確かめられないこと: 40 件の内訳、費用、警報の効果は、ここでも設計書にも計測がありません。判定は、設計書の文面だけに基づきます。

## 初見検証

設計書の筆者と、当番のリードが、返答だけで、次にすることを言えるかを確かめる。

| 読む人 | 返答だけで言えること | 言えないときの直し方 |
|---|---|---|
| 設計書の筆者 | 案を退けるのでなく、先に現行の警報の方針を確かめ、一部の経路から試すことだと言える | 結論に、先にすることを 1 文で置く |
| 当番のリード | 自分が示す項目と日付（2026-11-27 までの警報の方針・規則と運用、2026-12-04 までの警報の記録）を言える | 表の理由に、人・対象・日付を書く |
| 新しい当番 | 不明とした理由が、資料が無いことだと言える | 理由に、足りない資料を書く |
| 運用の担当 | 閾値は、過去の記録に当てて確かめるまで確定でないと言える | 実測の行に、確かめ方を書く |
| 相談者 | 自分が先に決めて書くこと（通知の上限、recall を数える記録、ラベルの上限、夜間・休日の待てない障害の連絡先、警報の対象と夜間の受け手）と、その期限（試行の開始 2026-11-27）を言える | 「先に決めて書くこと」の段に、決める項目を並べる |

## 点検

- 依頼の対象の群（可観測性と警報）だけを判定し、選ばなかった群は判定していない。判定表が、チェックリストの項目に対応し、19 行で、内訳（いいえ 6・不明 10・該当なし 3・はい 0）の合計と一致する
- 実測が要る項目に、記録が無いまま「はい」を付けていない。不明の項目ごとに、誰が・何を・いつまでに確かめるかが書かれている
- 設計書の欠落（いいえ）と、資料不足（不明）を分けて書いている。現行の警報を続ける案は、警報を消す・移す項目で「該当なし」とし、移す提案は改善案の条件に書いている
- 案を一律に退けず、一部から試す条件と、切り替える合図が書かれている。得るものと失うものが両面で書かれている。広げる前の費用の見積もりと、経路ごとの実績との照合が書かれている
- recall の数え方・通知の上限・ラベルの上限は、相談者が先に決めて書く形にとどめ、定義や式を足していない
- 「1 日 40 件」を申告として扱い、実測した値にしていない。効果は推測と書いている
- 数値（人数・上限・閾値・日付）が、例の設定と明記されている
