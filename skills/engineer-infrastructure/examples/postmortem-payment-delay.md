# 例: 決済の遅延（90 分）の事後検証（聞き取りの前の初版）

架空の決済サービスで、承認の遅延が 90 分続いた後に、責めない振り返りの文書を書く例。一次情報は時系列のログと、担当 3 人の口頭の説明だけで、聞き取りはまだ。分かっていること・推測・未確認を分けて書く。相談への返答の文面と、事後検証の本体を 1 組にまとめる。題材は架空の事業者・数値・日付で、実在の障害を写さない。障害の後に、文書の型と対応項目の置き方を決めたいときに開く。型は [SKILL.md](../SKILL.md) の「事後検証の型（責めない振り返り）」にある。

## 依頼

- 事業者: 架空の「さざなみ決済」。決済の承認を外部の決済代行に中継する（架空の前提）。通常は、承認の 95% が 2 秒以内に返る（例の設定）
- 事象（架空）: 2026-10-13（火）、承認の遅延が 10:20 から 11:50 まで続いた。時刻は日本時間（ログの時刻の基準）
- 一次情報: 時系列のログ（変更履歴・応答時間・要求数）と、当時の警報の規則（設定の記録）と、担当 3 人（設定変更の担当・問い合わせ連絡の担当・運用の担当）の口頭の説明。聞き取りは未実施
- 組織の取り決め（架空の前提）: 利用者の決済に 30 分以上の影響が出た事象は、事後検証を書く。会議は事象の後 5 営業日以内に開く
- 依頼文: 「事後検証を書きたい。設定変更の担当が設定を変えた直後で、本人が責められそうだ。聞き取りの前に、何を書いてよいか知りたい」

## 目的の一文

事象を、責めずに、記録と推測を分けて書き、複数の寄与要因と、担当・期限つきの対応項目を残す。

## 削るもの

| 削るもの | 理由と削り方 |
|---|---|
| 警報・計測の実装と製品の選定・閾値の全件の計算 | 対応項目に方針と閾値を 1 つ書くだけ。実装手順・ダッシュボードの作り方・製品の選定はしない。閾値は、他の警報まで決めない |
| 再発防止の網羅的な一覧 | 優先を絞った少数の対応項目だけ書く。全件を数え上げる表にしない（本 skill の整理） |
| 個人の評価・責任の判断 | 書かない。役割で書く。責めないことは、責任を問わないことではない（本 skill の整理）。S048 が述べるのは、安全と説明責任の釣り合いを取る努力である。責任の判断は事後検証の外 |
| 外向けの報告文 | 内部の記録だけ。外向けの文章は editorial-writer へ案内する（導入されていれば） |
| 本番の診断・原因の断定 | ここは記録の文書で、診断はしない。推測は推測と書く |
| 利用者数・二重の承認の有無 | 記録が無い。未確認と書き、確かめる担当を置く |
| 平均の復旧時間の算出 | 1 件の事象から平均を作らない。この文書は文脈つきで書く（S118 は、文脈の無い件数と平均では、安定性や回復の力はあまり分からないと述べる。C） |

## 構成

```text
概要（測れた影響・測れていない影響）→ 時系列（根拠の区分つき）→ 寄与要因（複数）
→ なぜ当時その判断が妥当に見えたか（未確認を明記）→ うまくいったこと／いかなかったこと
→ 対応項目（内容・担当・期限・追跡）→ 未確認・推測
```

節の並びは [SKILL.md](../SKILL.md) の事後検証の型に従う。

## 仕様

出典のある値には S 番号を付ける。それ以外は本 skill の整理か例の設定である。

| 項目 | 値 | 根拠 |
|---|---|---|
| 書く条件 | 事前に決めた条件に当たるかを、冒頭に書く。本例は 30 分以上の影響（例の設定） | S041 は、事前に事後検証の基準を決めることを述べる。事象が条件に当たるかの当てはめは本 skill の整理。値は例の設定 |
| 姿勢 | 個人・チームを咎めず、寄与した原因を探す。書くことは罰でなく学びの機会 | S041 |
| 寄与要因 | 複数あれば分けて書き、1 つなら、そう判断した理由を書く。「人為ミス」や 1 つの原因で締めない。本件は 4 つ挙げ、重なりかどうかは聞き取りの後に確かめる | 大きな失敗（破局）には、小さな失敗の重なりが要る（S045。Cook の論考。医療など複雑な系一般の話。本件が大きな失敗に当たるかは、ここでは断定しない）。事故を「根本原因」に帰属させるのは根本的に誤りという主張（S046。C）。様式の形は本 skill の整理 |
| 「なぜ」の使い方 | 「誰が」に行き着く問いを避け、当時の手元の情報を聞く | S051 は、「なぜ」が「誰が」に行き着きやすいと述べる（C）。問いの置き方は本 skill の整理 |
| 後知恵 | 結果を知った後の見え方で人を評価しない | S047 は、後知恵が事後の人の働きの評価に偏りを生むと述べる。妥当に見えた理由の書き方は本 skill の整理 |
| 時系列 | 時刻の基準と、各行の根拠（記録・口頭・推測・未確認）を書く | 本 skill の整理 |
| 時間の計算 | 10:20 から 11:50 は 90 分。検知まで 10:20 から 10:38 の 18 分。戻してから回復まで 11:20 から 11:50 の 30 分 | 本 skill の整理（計算） |
| 会議 | 2026-10-20（火）。事象（10-13）の後、5 営業日目（10-14・15・16・19・20） | S043 は、5 営業日以内の会議を述べる（PagerDuty の運用の自称）。日付の算術は本 skill の整理（計算）。日数と日付は例の設定 |
| 対応項目の期限 | 優先の項目は 4 週（2026-11-10）、それ以外は 8 週（2026-12-08）。会議の前に要る項目（影響の調査・聞き取り）は、会議の前を期限にする。催促と報告で追跡する | 優先とそれ以外を分けることと、どの項目を 4 週・8 週にするかの割り当ては、この例の組織の設定。S044 が述べるのは、優先の対応項目の期限がサービスに応じて 4 週か 8 週になることまで（Atlassian の運用の自称）。催促と報告での追跡は例の設定。4 週後・8 週後の日付の算術は本 skill の整理（計算）|
| 対応項目の判定 | 完了した項目は、完了の日と期限を記録で比べる。期限を過ぎて未完了だと追跡の記録で確かめられれば「いいえ」、記録が足りなければ「不明」。期限前で未完了の項目は「不明」とし、判定する予定の日を書く | 本 skill の整理 |
| 段階公開 | 設定の変更も段階的に広げる（段 1 の段階公開の行に当たる）。合格の条件と切り戻しの 3 つの条件は、方式によらない | 本 skill の整理。S053 は、Google の更新の大半を少しずつ進める運用を述べる（自称） |

## 文言

### 相談への返答

> 結論: 聞き取りの前でも、初版を書けます。書くのは、ログで確かめられたこと（記録）、担当の口頭の説明（口頭）、推測、未確認の 4 つの区分に分けた時系列と、複数の寄与要因です。「なぜその判断が妥当に見えたか」は、聞き取りが済むまで空欄にせず「未確認」と書き、聞く問いを残します。
>
> 設定変更の担当の設定変更は、時系列の 1 行として書きます（記録）。再試行の間隔の短縮が遅れを増やしたかは、検証前の仮説（推測）として、代行側の遅れ・警報の設計・再試行の仕方と並べて書きます。原因の欄には置きません。担当は役割で書き、名前は付けません。
>
> 失うもの: 初版では動機や手元の情報が「未確認」になる。未確認と書いても、読み手が推測で補うおそれがあるので、聞き取りの後に埋める（推測）。聞き取りの後に、改訂版を出し、版を残してください。
>
> 確かめられないこと: 原因は診断していません。回復が設定の戻しによるのか代行側の回復によるのかは未確認です。

## コード断片

事後検証の本体（Markdown）。`docs/postmortem/` に置く想定で、字下げして載せる。記法は例。

- `docs/postmortem/2026-10-13-payment-approval-delay.md`

    ```markdown
    # 事後検証 2026-10-13 決済の承認の遅延（初版・聞き取り前）

    - 会議: 2026-10-20（火）10:00（日本時間。例の設定）。会議の進行役・記録の役は会議で決める。事故対応の指揮の役は、置かれていたかを未確認
    - 書く条件: 30 分以上の決済への影響（取り決め）。本件は 90 分
    - この文書の時間・閾値・回数・件数・期限は例の設定

    ## 概要
    10:20 から 11:50（日本時間）、承認の応答が遅れた。測れた影響: この間の決済の要求 18,000 件のうち、承認が 10 秒を超えたのは 7,200 件（記録。例の設定）。測れていない影響: 影響を受けた利用者の数、再試行による二重の承認の有無（未確認）

    ## 時系列（日本時間。区分: 記録・口頭・推測・未確認）
    - 10:05 決済の再試行の間隔を 2 秒から 0.5 秒に短縮する設定を、全台へ反映（記録: 変更履歴。設定変更の担当）。段階を踏んだか、変更の理由は未確認
    - 10:20 外部の決済代行への呼び出しの応答が遅くなり始め、承認の応答が伸びた（記録: 応答時間のログ）
    - 10:20 以降 代行への要求数が増えた（記録: 要求数のログ）。再試行が遅れを増やした可能性（推測）
    - 10:38 問い合わせ窓口から「決済が進まない」と連絡（口頭: 問い合わせ連絡の担当の説明）。検知まで 18 分。遅延の警報は無かった（記録: 警報の規則）
    - 10:45 問い合わせ連絡の担当と運用の担当が、代行の遅れとみて調べ始めた（口頭）
    - 11:20 設定変更の担当が設定を元に戻した（記録: 変更履歴）
    - 11:50 承認の応答が通常に戻った（記録）。回復の理由は未確認（設定の戻しか、代行側の回復か、滞留した要求の消化か）

    ## 寄与要因の候補（確かめた事実と、寄与が未確認の仮説を分けて書く。重なりかは聞き取りの後に確かめる）
    1. 代行の応答が遅くなった（記録）。代行側の理由は未確認
    2. 再試行の間隔が短縮され、全台へ反映された。遅れを増やした可能性（推測）。段階を踏んだかは未確認
    3. 遅延で人を呼ぶ警報が無かった（記録: 警報の規則）。問い合わせで知った（口頭: 問い合わせ連絡の担当の説明。問い合わせの記録を照合したら更新する）
    4. 再試行に、間隔の延長と回数の上限が無かった可能性（推測。設定を確認する）

    ## なぜその判断が妥当に見えたか
    - 設定変更の担当（設定の変更）: 口頭の説明は変更の事実のみ。当時の手元の情報と時間の圧力は未確認。聞く問い: 何を見て、何を確かめた上で出したか
    - 問い合わせ連絡の担当・運用の担当（調査と判断）: 代行の遅れとみた根拠は口頭の説明。手元の情報は未確認

    ## うまくいったこと / いかなかったこと
    - うまくいった: 変更履歴が残っていた（記録）
    - いかなかった: 検知が問い合わせ経由で 18 分かかった

    ## 対応項目
    - 優先 1: 決済の経路の設定変更を段階に分け、変更した台と変更していない台を比べ、変更していない台に比べて、変更した台の承認の応答が許容の幅を超えて悪くなったら戻す（幅は相談者が決める）。台の間で差が出ないことは、共有の依存先（外部の決済代行）への影響が無いことを示さない（本 skill の整理）。見る指標には、代行への要求数と失敗率を含める。各段の観測は、症状が出るまでの時間（本件は変更から 15 分。原因は未確認）より長くする（例: 各段 30 分。仮）。比べる要求は各段 100 件以上（例の設定）。戻すかを決める人: 公開の担当者。切り戻しにかかる停止の上限を先に決め（値は相談者が決める）、その時間内に戻せるかを公開の前に確かめる。担当: 開発リーダー。期限: 2026-11-10。追跡: 週次の確認。使う条件は決済の経路の設定。設定とデータの通常の変更は、この段階公開の対象にする。各段で広げる合格の条件（判定に使う指標と許容範囲・観測する時間・要るデータの量・比べる対象）を先に決め、満たさないとき、または観測の時間・データの量に届かないときは、その段で止める。変更した台が変更していない台に比べて悪くならなくても、決済代行への要求数か失敗率が公開前の基準を超えて悪くなったら、広げるのを止め、変更した段を戻す（基準・幅・観測の窓は相談者が決める（未決））。ただし戻せるのは、切り戻しの 3 条件を満たす段に限る。切り戻すのは、戻しても書き込みが失われず、形式が互換で（新版で受けた書き込みを旧版で読める）、処理中の取引を扱えるときに限る。満たさない段では、広げるのを止めて、先に決めた前へ直す担当へ知らせる。切り戻せない変更（データや通信の取り決めの形式を変えるもの）は、戻す代わりに前へ直す条件と担当を、別に決める（本 skill の整理。未確認の項目に載せて追跡する）
    - 優先 2: 当番を呼ぶ警報を足す。条件は相談者が決める（未決）。決めた条件を過去の記録に当て、鳴るべき時（本件を含む）に鳴り、鳴らない時に鳴らないと確かめてから入れる。決済の当番の体制（夜間・休日に呼べるか）は未確認。体制の確認は、未確認の項目に載せ、運用の担当が 2026-10-19 までに行う。確認までは、呼び出しの先と時間帯を決めず、問い合わせ経由の検知が続く。呼べない時間帯の待てない障害は、代わりの連絡先を決めるか、当番の体制と利用者への約束を見直す（本 skill の整理）。担当: 運用の担当。期限: 2026-11-10。追跡: 週次の確認。警報の対象の要求が 0 件や少ない間の扱いは未決（判定しない）
    - 3: 再試行の現行の仕様を確かめ、無作為化した指数バックオフ（S065）・ゆらぎ（S066）・要求ごとの回数の上限（3 回。例の設定）が無ければ入れる。サーバー全体の再試行の予算（決済代行への再試行の全体の量）と、使い切ったときの扱いも決める。一般に、副作用のある API は、冪等でなければ再試行が安全でない、というのが Amazon の見方である（S066）。結果が分からない要求は、再試行せず、代行へ照会して状態を確かめ、承認済みなら取り消すか確定するかを決める（本 skill の整理）。再試行するのは、冪等であると確かめた要求か、元の要求が副作用なく終わったと確定した要求に限る（未承認の応答だけでは確定としない）。使う条件: 外部への呼び出しの再試行。担当: 設定変更の担当。期限: 2026-12-08。追跡: 週次の確認
    - 4: 二重の承認の有無と、影響を受けた利用者の数を、決済の記録と代行の記録を照合して確かめる。会議を待たずに先に行う。担当: 運用の担当。期限: 2026-10-15。追跡: 結果を概要に追記
    - 5: 聞き取り（担当 3 人）。担当: 開発リーダー。期限: 会議の前日（2026-10-19）。追跡: 会議で報告

    ## 未確認・推測
    代行側の理由。回復の理由。利用者の数。二重の承認。設定変更の動機と手元の情報。再試行の現行の仕様。設定変更の公開の手順（段階の有無）。決済の当番の体制（担当: 運用の担当。期限: 2026-10-19）。切り戻せない変更の扱い（担当: 開発リーダー。期限: 2026-11-10）。
    ```

## 初見検証

事後検証を初めて読む開発者と、設定変更の担当が、文書だけで言えるかを確かめる。

| 読む人 | 文書だけで言えること | 言えないときの直し方 |
|---|---|---|
| 新しい開発者 | 時系列の各行が、記録・口頭・推測・未確認のどれかを言える | 各行に区分を付ける |
| 設定変更の担当 | 自分の変更が原因の一行として扱われず、時系列の事実と、検証前の仮説（推測）に分けて書かれている | 寄与要因を複数にし、変更は事実と仮説に分け、「誰か」で締めない |
| 運用のリーダー | 優先 1・2 の担当・期限と、追跡の方法 | 項目に 4 つの欄を付ける |
| 経営の担当 | 測れていない影響が何か | 概要に未確認を分けて書く |

## 点検

- 時系列に時刻の基準があり、各行に区分がある。10:20 から 11:50 が 90 分、検知までが 18 分、戻してから回復までが 30 分と合っている
- 寄与要因が、複数あれば分けて書かれ（1 つならその理由が書かれ）、「人為ミス」や個人の名前で締めていない
- 「なぜ妥当に見えたか」が、聞き取りの前なので口頭の範囲と未確認だけで書かれている
- 対応項目に、内容・担当・期限・追跡が付き、優先を絞っている。網羅表にしていない。判定の付け方（完了は日付の比較、期限前で未完了は「不明」、期限を過ぎて未完了は「いいえ」）が分かる
- 推測と未確認が分けて書かれ、診断や断定をしていない。数値と日付が例の設定と明記されている
