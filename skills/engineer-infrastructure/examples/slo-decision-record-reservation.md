# 例: 予約サービスの SLO の決定記録（事象ベースの SLI と error budget の方針）

架空の予約サービスが、記録の短い状態で暫定の SLO を決め、error budget を使い切ったときに誰が何を決めるかまでを、1 件の決定記録に残す例。相談への返答の文面と、記録の本体を 1 組にまとめる。題材は架空の事業者・数値で、実在の製品・企業を写さない。SLO を初めて置くとき、または目標を置いたが消費したときの扱いが決まっていないときに開く。記録の型は [SKILL.md](../SKILL.md) の「SLI・SLO・error budget」にある。

## 依頼

- 事業者: 架空の「つばめ予約」。開発は 12 人。当番は平日の日中のみで、夜間と休日に人を呼ぶ体制は無い（架空の前提）
- 利用者の不満: 「予約が確定したのに完了しない」（架空の前提）
- 計測できる記録: 直近 4 週間（28 日）の「予約確定の成功率」だけ。この率が数えるのは、確定の要求のうち、サーバーが成功の応答を返したものの割合である（計測の方式は事象ベース。分子・分母の単位は確定の要求の件数。時間ベースではない）。確定の後の工程（確認の通知・一覧への反映）は見ていない（架空の前提）。利用者の再試行で件数が増えうる。予約の単位との差は未確認
- 直近 28 日の記録（例の設定）: 確定の要求 280,000 件、うち失敗 1,120 件（成功率 99.6%。本 skill の整理（計算））。計画停止中の確定要求も数える。除外は置かない（除く上限と承認者を決められないため）
- 欠かせない依存先（架空の前提）: 在庫の保存先と決済代行。相談者の記録による可用性は、それぞれ 99.95% と 99.9%（依存先ごとの値で、依存先の呼び出しが成功した割合。確定の要求と同じ分母で数えた記録ではない。例の設定）。確定 1 件で、両方の依存先を 1 回ずつ呼ぶ（架空の前提）
- 外向けの約束（SLA）は無い。経営は、error budget で公開を止める決めごとには合意していない（架空の前提）
- 依頼文: 「SLO を決めたい。目標の値は自分たちで決めた（99.0%）。でも記録は 4 週間分しかなく、使い切ったときの扱いも決まっていない」

## 目的の一文

予約確定の SLO を暫定で 1 つ置き、予算を件数で示し、消費したときに誰が何を決めるかと、見直す条件・日付を、新しく入った人が読んで言える形に残す。

## 削るもの

| 削るもの | 理由と削り方 |
|---|---|
| 本番の診断 | 件数は例の設定で、本番の記録を見ていない。失敗の原因は診断しない |
| SLI の計測の実装手順・ダッシュボードの作り方 | 返すのは決定と記録。計測の実装は別の作業で、ここでは SLI の定義だけを書く |
| 警報の閾値の計算・消費の速さ（burn rate）による警報 | 別の記録で決める。当番が平日の日中のみなので、夜間に人を呼ぶ警報は、この記録に入れない。別の記録で置くときは、長い窓と短い窓の両方で閾値を超えたときに発報する形にし、窓の中の確定要求が時間の比率どおりに分かれる前提を確かめる。偏るときは、窓の中の失敗件数を、期間の予算件数に照らす（本 skill の整理） |
| 計測製品の選定・比較 | 特定の製品の助言はしない（範囲） |
| 時間への換算（許容停止時間） | この SLI は事象ベースで、予算は件数で示す。許容停止時間の分数は、時間ベースの SLO で全面停止として数えたときの計算で、ここには当てはまらない（本 skill の整理（計算））。トラフィックが偏ると、短い停止でも多くの件数を消費する |
| SLA の法的な効力・契約の判断 | 外向けの約束が無い。あっても範囲外 |
| 目標値の決定 | 99.0% は相談者が決めた値で、本 skill は決めない（例の設定） |

## 構成

```text
利用者の困りごと → 目指す SLI と、いま測れる SLI を分けて書く → 暫定の目標（例の設定）
→ 依存先の上限を確かめる → 予算を件数にする → 段階と、消費したときに決める人
→ 却下した案 → 結果（失うものを含む）→ 見直す条件・日付
```

記録の節は [SKILL.md](../SKILL.md) の雛形に従う。1 つの決定を 1 つの記録にする（architecture の ADR と同じ考え方）。

## 文言

### 相談への返答

> 結論: 予約確定の成功応答の割合を、28 日の移動窓で 99.0%（暫定）とする SLO を 1 つだけ置くことを勧めます。値はあなたが決めたものです。計測の方式は事象ベースで、予算は件数（確定の要求の件数）で示します（2,800 件）。止める決めごとは入れず、予算の 80% で 2 人が 2 営業日以内に次の公開の予定を見直し、超えたら止める範囲を決める、という形にします。止める線を「超えたとき」とするか「0 になったとき」とするかは、合意した方針で決めます。ここでは超えたときとしました（例の設定）。
>
> 置いた仮定（架空の前提）: 直近 28 日の確定の要求は 280,000 件、失敗は 1,120 件。外向けの約束は無い。経営は、公開を止める決めごとに合意していない。当番は平日の日中のみ。
>
> 選ぶ条件: 成功応答の記録しか無い間はこの形です。記録が 28 日分しか無いので、目標は暫定として置き、見直す日付を付けます。
>
> 先に言っておくこと: 不満は「確定したのに完了しない」で、いま測れる成功率は確定の後の失敗を数えません。この SLO を満たしても不満が残る可能性があります（推測）。完了までを数える SLI を、記録の取り始めから用意し、置き直すか 2 本目を足すかは、記録がたまった時点で決めます。
>
> 失うもの: 不満の中心が、当面この SLO に現れません。公開を止める強制力が無く、守られるかは 2 人の会議に頼ります。会議の時間も要ります。
>
> 切り替える合図: 完了の記録が 4 週間以上たまったら、SLI と目標を置き直すか 2 本目を足すかを決めます。経営が止める決めを命じたら、方針に止める範囲を書きます。
>
> 確かめられないこと: 99.0% が利用者の体験に合うかは、実測していません。不満の問い合わせの記録と突き合わせて確かめてください。

## コード断片

SLO の定義の最小の断片（記法は例。特定の製品の書式ではない。値は例の設定）。

```text
slo: booking-confirm-success
good:   確定要求のうち、成功応答を返したもの
total:  確定要求
method: event-based   # 事象ベース。単位は確定要求の件数
objective: 99.0%   # 暫定
window: 28 日の移動窓
budget_events: total × 1%
stages: 50%, 80%, 100%   # 予算の割合。今の件数なら 1400, 2240, 2800 件
```

決定記録の本体（記法は例）。`docs/slo/` に置く想定で、字下げして載せる。

- `docs/slo/SLO-0001-booking-confirm.md`

    ```markdown
    # SLO-0001 つばめ予約 予約確定の成功の割合の目標（暫定）

    - 状態: 提案（経営との合意の場の後に、承認の日を記す）
    - この記録の件数・割合・期限・日付は例の設定
    - 日付・決める人・相談した人: 2026-11-20（架空）・サービスの責任者・開発リーダー、当番のリード、プロダクトの責任者

    ## 利用者の困りごと
    予約を確定したのに完了しない、という不満（架空の前提）。

    ## SLI
    - 計測の方式: 事象ベース。分子・分母の単位は確定の要求の件数
    - 目指す形: 確定の要求のうち、成功応答が返り、かつ確定から 10 分（例の設定）以内に予約が「完了」状態になったものの割合。完了の記録は、いま取れていない
    - 当面: 確定の要求のうち、成功応答を返したものの割合（サーバーの応答の記録で測る）。確定の後の失敗は数えない。利用者の再試行で件数が増えうる。予約の単位との差は未確認

    ## SLO
    28 日の移動窓で 99.0%（暫定・例の設定）。外向けの約束は無い。直近 28 日は 280,000 件中、失敗 1,120 件（99.6%）。

    ## 依存先の上限
    予約確定の SLI を満たすのに欠かせない依存先。在庫の保存先 99.95%、決済代行 99.9%（依存先ごとの値。相談者の記録。依存先の呼び出しが成功した割合。例の設定）。上限は、SLI と同じ分母で、欠かせない依存先がすべて使えたか、代わりの経路で同じ要件を満たせたかを数えた割合で確かめる。その記録はまだ無く、取り始めるまで上限は不明（本 skill の整理）。参考として、独立と仮定した積は約 99.85%（推測）。目標 99.0% は、この参考値を下回る。

    ## error budget の方針
    - 予算: SLI と同じ単位（件）で書く。窓の確定要求の総数 × 1%。今の件数なら 2,800 件。毎週、窓の件数で計算し直す。段階は予算の割合で置く
    - 計画停止中の確定要求も数える。除外は置かない（除く上限と承認者を決めるまでは、除かない）
    - 消費に数える: 成功応答を返さなかった確定要求。依存先が原因のものも数える（利用者には失敗に見える）。会議では内訳を分け、止める効果があるかの材料にする
    - 利用者側の原因（入力の誤り・在庫なしによる拒否）: 数える・数えないを決めて書く。例の設定では数えない
    - 検知: 毎週月曜に、当番のリードが窓の失敗数を数える。検知は最大 7 日遅れ、週の中で予算を超えうる（失うもの）。期限の起点は、この確認で段階に達したと分かった日（検知日）。窓の確定要求が 0 件の週は、達成・未達を付けず 0 件だったと書く（欠測とは分ける）。数えるときは SLI と同じ分母と評価期間を使い、記録が欠けて達成・未達が変わりうるときは「不明」とする（本 skill の整理）
    - 予算の 50%（今は 1,400 件）: 週次の確認で共有し、直近の変更を見る。決める人は当番のリード
    - 予算の 80%（今は 2,240 件）: 開発リーダーとプロダクトの責任者が 2 営業日以内に会い、次の公開の予定を見直すか決める
    - 予算の 100% 超（今は 2,800 件超。止める線は、合意した方針で決める。ここでは超えたときとした）: 同じ 2 人が 2 営業日以内に、公開を止める範囲を決めて、この記録に追記する。止めない場合は理由を書く
    - 値の理由: 99.0% は、現状（99.6%）と依存先の参考値（約 99.85%）より低く、相談者が決めた暫定。50% は週次の確認で気づいてから動ける余裕、80% は会議のあとに公開の予定を変えられる余裕、2 営業日は会議の手配の時間（いずれも例の設定。実測の根拠は無い）
    - 例外: 障害の修正と、利用者のデータを守る修正は止めない。例外の公開も、影響範囲の上限と戻す手段を先に置く（本 skill の整理）
    - この方針は罰ではない。信頼性に集中してよい許可である。公開を止める決めごとは、経営との合意が無いので入れない
    - 事象ベースなので、停止の分数には換算しない

    ## 却下した案と理由
    - 99.9%（例の設定）: 予算は 280 件（280,000 × 0.1%。本 skill の整理（計算））で、直近の窓では 1,120 件の失敗が超える。議論で引かれなくなる（推測）
    - 目標を置かず記録を待つ: 優先順位の議論で引く値が無い
    - 今の SLI を「完了」までにする: 記録が取れていない

    ## 結果
    良い点: 優先順位の議論で引ける値が 1 つできる。失うもの: 完了の不満が当面現れない。止める強制力が無い。会議の時間

    ## 見直す条件・日付
    - 2026-12-04（金）までに、完了状態の記録を取り始める（担当: 開発リーダー）
    - 2027-01-08（金）: 完了の記録が 4 週間以上たまったら、SLI と目標を置き直すか 2 本目を足すかを決める
    - 窓の予算を使い切る事象が起きたとき: 次の会議で、目標と体制を見直すか決める
    - 経営が公開を止める決めを命じたとき: 方針に止める範囲を書く
    ```

## 初見検証

新しく入った当番と、プロダクトの責任者が、記録だけで、次にすることを言えるかを確かめる。

| 読む人 | 記録だけで言えること | 言えないときの直し方 |
|---|---|---|
| 新しい当番 | 失敗が予算の 50%（今の件数なら 1,400 件）に達したら、誰が何を見るか | 段階の行に、決める人と、見ることを 1 文で書く |
| プロダクトの責任者 | 予算の 80%（今の件数なら 2,240 件）に達したら、検知日から 2 営業日以内に自分が会議に出る。なぜ 50%・80%・2 営業日かも言える（例の設定で、実測の根拠が無いことも） | 段階の行に、人・起点・値の理由を書く |
| 開発者 | 今の SLO が「完了」を数えていないこと。なぜ 99.0% か（現状と依存先の参考値より低く、相談者が決めた暫定） | SLI の「当面」の行と、値の理由の行に書く |
| 経営の担当 | 止める決めごとが入っていない理由と、入れる条件 | 方針の末尾と、見直す条件の最終行を対応させる |

## 点検

- SLI が、計測の方式（事象ベース）・分子と分母の単位・良い事象と全事象の比で書かれ、目指す形と、いま測れる形が分かれている
- 予算が件数で示され、時間への換算をしていない。段階が予算の割合で置かれ、件数は今の件数から計算し直せる（1,400 = 2,800 × 50%、2,240 = 2,800 × 80%）
- 消費したときに、誰が何を決めるかが、人・期限つきで書かれている。数式だけで止まる形になっていない
- 依存先の上限が、SLI と同じ分母で数えた割合として確かめる形で書かれ、積は参考値にとどまっている。記録が無いので「不明」としている
- 経営の合意が無いことが書かれ、止める決めごととして置いていない。止める線は合意した方針で決めるとされている
- 見直す条件が、日付または出来事で書かれている。却下した案と失うものが書かれている
- 数値（人数・件数・目標・窓）が、例の設定と明記されている。実測していない値を断定していない
