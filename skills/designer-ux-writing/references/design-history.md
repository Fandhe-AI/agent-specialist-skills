# デザイン史: 平易な言葉の運動から、GUI の文言・Web の文章・スタイルガイド・コンテンツデザイン・UX ライティングの職能・生成 AI まで

画面の文言（ボタン・エラー・案内・用語・ボイスとトーン・国内の表記）の慣習が、どんな制約のもとで、どう変わってきたかをまとめたファイル。年表の暗記用ではなく、「いま採ろうとしている慣習や規則は、どんな制約から生まれたか」を確かめるための材料である。要点（見取り図・繰り返すパターン・媒体別の問い）と、時代別の詳細を 1 ファイルに置いた。中心の問いは次の 1 つ。

> その慣習を生んだ制約は、今回の画面・利用者・言語でも成り立つか。

成り立つなら、慣習は今も根拠を持つ。成り立たないなら、形だけが残っている可能性がある。出典が薄い時代は、薄いと書く。

このファイルを開くのは、相談者が背景を求めたとき、制作の着手前（「媒体別の使い方」の節）、慣習や規則の由来が不明のとき、の 3 つである。

| 知りたいこと | 開く場所 |
|---|---|
| 全体像・横断の型 | 「見取り図」「繰り返すパターン」 |
| 画面の種類ごとに確かめる問い | 「媒体別の使い方」 |
| 平易な言葉の運動・国内の公用文・GUI の文言・Web の文章・スタイルガイド・コンテンツデザイン・国際化・国内の表記と敬語・騙しの文言と生成 AI | 「時代別の詳細」の 1〜9 |
| 年が出典どうしで合わない項目 | 「年が食い違う・注意する出典」 |
| 空白・未検証 | 「確認できなかったもの」 |

## 読み方と記法

- 時点: 記述は出典ごとの取得日の時点（`sources.md` の各項目を見る）
- 各時代の 4 項目: 当時の制約 / 応答 / 副作用と反動 / 今の判断への示唆。4 項目めの「示唆」はすべて「本 skill の整理（推測）」で、出典が述べた因果ではない。因果（「A だから B になった」）は、出典が述べている場合だけ S 番号つきで書く。「当時の制約」を出典が述べていない時代は、「整理（推測）」または「出典なし」と書く
- 区分は `sources.md` の凡例に従う（A 原典、B 第三者の転載、C 論評・批判、R 記者・機関・運営者の地の文、U 未検証）。B・C・R は区分を明記して要旨にし、英語の逐語で本人の発言としては示さない。R を研究結果の根拠にしない
- 年・日付: S 番号を添えた論旨上の年は、その引用ブロックに含まれるものに限る。ほかの年は記事・文書の公開日で、「媒体・日付」の項による
- 1 社の当事者の回想（Microsoft・Facebook・Uber）は、その会社の記録として扱い、業界全体の起点にしない
- 英語の逐語は区分 A の出典だけで、1〜2 文に限る。日本語は要旨で、本人の発言ではない
- 回答での使い方: 頼まれない限り、歴史を講釈しない。判断の根拠として 1 行で使う

## 回答での使い方（例）

- 相談「エラー文の冒頭で毎回謝りたい」: 入力検証で謝る必要は無く、深刻な障害のときだけ謝る、と GOV.UK の指針は述べる（S042・S041）。Atlassian は謝罪自体を避ける（S221。要旨）。Google は、謝罪の受け取り方は文化で違うと述べる（S095）。出典はどれも英語の画面の議論で、日本語の画面は本 skill の整理
- 相談「確認ダイアログを全部の削除に出したい」: Win32 の指針は、不要な確認は読まれずに閉じられると述べる（S058）。確認の代わりに、取り消しを置く案が先にある（S049）
- 相談「親しみやすい文言にしたい」: ボイスは一定で、トーンは場面で変える（S001・S027）。トーンは面白さ・堅さ・敬意・熱量の 4 軸で記述できる（S028）。冗談は、利用者が本当に面白いと思う場合に限る（S029）
- 相談「お役所っぽくなくしたい」: 公用文の基準の側が、解説・広報等では親しみやすい表記を用いてもよいと述べている（S104）。規則を捨てる話ではなく、文書の種類の選び方の話である

## 繰り返すパターン（本 skill の整理）

次の型は、出典を横断して読み取ったもので、出典が述べた法則ではない。例外は多い。

1. 網羅すると読まれない: 政府には「念のため全部書く」傾向があった（S185）。読まれる語は多くて 28%、おそらく 20% という推定がある（S161。他の研究者の調査のデータを NN/g が分析した）。書き足す前に、誰の何のニーズかを問う（S025・S187）
2. 平易さは易しくすることではない: 専門家も平易な文を好む（S152）。平易さは、読み手の理解のための条件として制度化された（S192・S193・S153）
3. 流し読みの前提は全員に当てはまらない: 読むのが苦手な人は、1 語ずつ追い、視野が狭い（S151）
4. 測れる数値に寄る: 読みやすさの公式（S168・S169・S170）や A/B テスト（S164）は、理由や意味を測らない。質的な確かめ方（S156・S158・S163）で補う。多くの案は指標を改善しない（S165・S174）
5. 親しみは転用される: 親しみのある文言の推奨（S029）が、断る選択肢を貶める文言（S200・S202）へ転用されうる。整理（推測）
6. 職名は変わるが仕事の核は同じ: technical writer から UI text writer、UX writer、content designer へ（S190・S191）。名称の変化を理由に仕事の範囲を決めない
7. 理念は変わらず、細則が実態に追いつく: 公用文の基本の考え方は変わらず、実態との食い違いが大きくなった細則を見直した（S179）
8. 規範は自らの適用範囲を限定し、その外側に別の慣習が育つ: 内閣告示は専門分野や個人の表記に及ぼさない（S115・S117）。公用文の建議は、語末 -y にも長音符号を用いる（S110）が、SmartHR は語末 -y に長音符号を付けない（S234。要旨）。決め方は分かれる

## 媒体別の使い方

制作の着手前に、文言の種類ごとに次の問いを確かめる。

| 文言の種類 | 確かめる問い | 開く時代 |
|---|---|---|
| エラー・入力検証 | 設計で防げなかったか。責めていないか。直し方があるか。謝る場面か | 3・5・6 |
| 確認ダイアログ | 読まれるか。取り消しで代えられないか | 3・7 |
| ボタン・ラベル・見出し | 同じものを同じ語で呼んでいるか。流し読みで拾えるか | 3・4 |
| 通知・メール | 1 件 1 要件か。誰に見えるか。同意はあるか | 4・6 |
| ボイスとトーン・スタイルガイド | 声と調子を分けたか。ユーモアは翻訳・文化で成り立つか | 5・7 |
| 多言語・翻訳 | 連結していないか。複数形・長さは。併記は支援技術で問題にならないか | 7・8 |
| 手続き・行政・やさしい日本語 | 読み手の下限を決めたか。しなくてよいことも書いたか。読み手本人に確かめたか | 1・2・8 |
| 解約・同意・断る選択肢 | 断る側の文言に敬意があるか。二重否定は無いか | 5・9 |
| AI の機能の文言 | 人格を演じていないか。画一化していないか | 9 |

## 時代別の詳細

### 1. 行政文書の平易化（〜 2010 年、米国）

- 当時の制約: 整理（推測）: 規則や給付の文書は、専門家が専門家に向けて書く形式で、読む市民の理解を前提にしていなかった。plainlanguage.gov の年表は、Nixon が連邦官報を「layman’s terms」で書くよう定めたことを、初期の弾みとして挙げる（S194。R。機関の地の文）
- 応答: 1998 年の覚書は、連邦政府の文書は平易な言葉で書かなければならないと述べた（S192）。2010 年に Plain Writing Act が成立し、「plain writing」を、明確・簡潔・よく整理され、主題と読み手に合った慣行に従う文章と定義した（S193・S194）
- 副作用と反動: 台帳の範囲では、民間の画面への義務を確認していない。整理（推測）: 制度の対象の外では、慣習が残った
- 今の判断への示唆: 平易さは好みではなく、読み手が内容を理解するための条件として制度化された。手続き・料金・解約・同意の文は、行政文書と同じ重さで平易さを求めてよい（本 skill の整理）。ただし、米国の法律は日本の民間の画面の根拠にならない

### 2. 国内の公用文: 戦後の要領から「公用文作成の考え方」へ

- 当時の制約: 戦後の公用文の口語化を述べた引用は、台帳に無い（出典なし）。昭和 27 年の内閣官房長官依命通知「公用文改善の趣旨徹底について」は、令和 4 年の通知で廃止された（S178）
- 応答: 令和 3 年の報告は、「感じのよく意味のとおりやすいものとする」という基本の考え方は変わらないものの、実態や社会状況との食い違いが大きくなっているところが見られる、と述べた（S179）。報告は、読点に「、」が用いられることが多いという実態にも触れる（S113）。令和 4 年の建議「公用文作成の考え方」は、読み手に理解され、信頼され、行動の指針とされる文書を作成する、を掲げ（S103）、文書を種類で分けて、解説・広報等では親しみやすい表記を認めた（S104・S109）
- 副作用と反動: 建議は語末 -y にも長音符号を用いるとしたが（S110）、令和 6 年度の世論調査では「セキュリティ」が 53.5%、「セキュリティー」が 34.2%で、付けない側が多い（S118）。規範が実態より保守的な箇所が残る
- 今の判断への示唆: 理念は 70 年変わらず、細則が見直された（S179）。文言の指針も、理念と細則を分けて持ち、細則は実態に合わせて改める前提で書く（本 skill の整理）。建議は国の府省庁の公用文の目安で、民間の画面の規範ではない

### 3. GUI の文言と用語（1980 年代〜 2000 年頃）

- 当時の制約: 整理（推測）: 画面の文言は、技術者がエラーコードと内部の用語で書いていた。Microsoft の当事者は、文言を専任で書く職が作られた経緯を回想する（S191。1 社の回想）
- 応答: Shneiderman の 8 原則は、深刻な誤りを起こせない設計を求め（S086）、プロンプト・メニュー・ヘルプで同じ用語を使うことを求める（S086）。Nielsen のヒューリスティクスの 9 番は、エラー文を平易な言葉で、問題を特定し、解決を提案する形で書くよう求めた（S081）。Windows 2000 の出荷が近い頃に、最初の「UI text writer」の職が作られた、と当事者が書く（S191）。Win32 の指針は、良いエラー文は UI の問題ではなく設計の問題だと述べる（S055）。確認は、作業を放棄しようとしているなら確認しない、と条件で絞った（S059）
- 副作用と反動: 指針自身が、自社の多くのエラー文を「Hall of Shame」の候補と書き（S056）、不要な確認は読まれずに閉じられると認める（S058）。Norman は、事故の多くは人の誤りの前に、装置や手順の不適切な設計があると書いた（S084）。整理（推測）: エラー文を直す方向に議論が寄ると、設計で防ぐ先の問いが後ろに回る
- 今の判断への示唆: エラー文を直す前に、そのエラーが起きない設計にできないかを先に問う（S063）。用語の一貫性は古い原則で、用語集の運用は新しい流行ではない（S086・S087）。Win32 の文書は更新されておらず（S175）、原則と例を分けて使う（本 skill の整理）

### 4. Web の流し読みと microcopy（1997〜2009 年）

- 当時の制約: 印刷物の書き方のまま載せた長文と、誇張した宣伝調が多かった（整理（推測）。S159 は流し読みの観察を報告する）
- 応答: NN/g は、利用者の 79% が新しいページを常に流し読みし、1 語ずつ読んだのは 16% だったと報告した（S159）。同じ頃の研究は、簡潔に 58%、流し読みしやすく 47%、客観的に 27%、3 つを合わせると 124% 使いやすさの指標が上がったと報告した（S160。1 つのサイトでの比較で、合成指標。今の UI 文言にそのまま当てはめない）。Halvorson は、コンテンツ戦略を、有用で使えるコンテンツの作成・公開・保守の計画と定義した（S182）。Porter は、短い文言（microcopy）を、小さいが強いと書いた（S183）
- 副作用と反動: 「人は読まない」は、読み書きに慣れた人の傾向だった。読むのが苦手な人は流し読みせず 1 語ずつ追い、視野が狭く、要素を見落とす（S151）。F 字は流し読みの型の 1 つで、唯一の型ではない（S162）。Spool の「3 億ドルのボタン」は、文言の効果として引かれるが、対象は匿名のサイトで（S167）、Register のボタンを外して Continue のボタンに置き換えたとあり（S167）、変えたのは文言だけでなく手順の設計である
- 今の判断への示唆: 流し読みへの対策（結論を先に・意味のある見出し・1 段落 1 論点）は今も根拠がある。ただし対象は慣れた人の行動で、読むのが苦手な人・母語でない人・支援技術の利用者では前提が変わる。数値（79%・124%・20〜28%）は、1997〜2008 年の Web の値で、今のスマートフォンの文言へそのまま当てはめない（本 skill の整理）

### 5. スタイルガイドの公開とボイス・トーン（2012 年〜）

- 当時の制約: 製品の文言・マーケティング・サポートを多数の書き手が書き、文体がばらつく（整理（推測））
- 応答: 声は変えず、調子は利用者の気持ちに合わせて変える、と Mailchimp は示した（S027。2012 年の保存コピー。S001 の現行版）。Microsoft は、文脈と利用者の気持ちに合わせて、真面目・共感・軽やかと調子を変えると述べ（S010）、Adobe Spectrum は、1 つの声で、状況に応じて調子を変えると述べる（S017）。NN/g は、調子を面白さ・堅さ・敬意・熱量の 4 軸で分析できるとした（S028）。Atlassian は声の特性と状況別の調子を持つ（S217。要旨）。Podmajersky の書籍は、ボイスチャートを作る方法を紹介する（S218。書誌・出版社の紹介文の要旨で、本文は未照合）
- 副作用と反動: Mailchimp 自身が、無理なユーモアは無いより悪い（S003）、くだけた声は文化によっては失礼になる（S093）と書く。明確さが面白さより優先される（S002）。Polaris は、声と調子を気にしすぎず、人間らしく聞こえることに集中する、と書く（S216。要旨）。これを運用負担への反動と読むのは本 skill の整理（推測）
- 今の判断への示唆: 声と調子の表は作る価値があるが、ユーモアとくだけた口調は、翻訳・多言語展開で最初に問題になる（S016・S093）。日本語の文末（です・ます／常体）と敬語の選択は、英語圏の指針に対応物が無く、別に決める（本 skill の整理。jp-style.md）

### 6. コンテンツデザインと職能の制度化（2012〜2021 年）

- 当時の制約: 政府には、起こりうる事態のすべてを利用者に理解させようとする傾向がある、と GDS の当事者が書く（S185）
- 応答: GDS は、利用者が関連する情報を見つけ、読み、理解し、去れることを目標にした（S184）。2012 年にコンテンツデザイナーが、ニーズの調査とコンテンツの計画を担った（S186）。Richards は、利用者のニーズを取り、最善の形で示す、言葉だけでなくてよいから「コンテンツデザイン」と呼ぶ、と説明した（S187）。設計原則の第 1 は、利用者のニーズから始めること（S025）。Content Design London は、コンテンツデザインを、利用者のニーズに、利用者が受け取るのに最善の形で応えることと定義した（S026）。Facebook は、Content Strategy のチーム名を Content Design に変えた（S189）。Uber は、Product Writers、UX Writers を経て Content Designers に改称した（S190）。GDS のユーザーリサーチは、印刷した文面に、安心できる所を緑、不安になる所を赤で線を引いてもらう方法を報告した（S156）。ハイライターで確かめる方法は、米国の 18F にもある（S158）
- 副作用と反動: 職名は会社ごとに違い、変遷も 1 社ずつの記録である（S189・S190・S191）。Bowman は、2 つの青を決められず 41 段階を試す文化への批判を書いた（S166。C）。ボタンの文言の効果の逸話は、手順の変更と混ざっていないかを確かめてから使う（S167）
- 今の判断への示唆: コンテンツデザインの核は、文言を磨くことではなく、ニーズから、文章・表・計算ツールなど最適な形を選ぶことである（S187・S008・S026）。文言の相談でも、まず文言で解く問題かを問う（本 skill の整理）。「content design の語は Richards が造った」「UX writer の職名は Google が最初」は、取得した範囲に根拠が無い

### 7. 部品単位の指針と国際化の道具

- 当時の制約: 部品ライブラリが共有され、同じ部品が多数の製品・チームで使われる。英語で作った UI を多言語に展開すると、文の連結・複数形・長さが壊れる（整理（推測））
- 応答: 文言の指針を部品の使い方の頁に組み込んだ（Carbon の用語集 S089、GitLab の破壊的操作・トースト・ツールチップ S067・S068・S069、Spectrum のエラー S063・S064・S065）。ツールチップを自動で消さない規則を、達成基準の違反になるからと書く例もある（S069）。国際化は、W3C が連結の問題を整理し（S101）、ICU は、連結すると訳者が語順を変えられないとして文全体を渡す方式を採り（S098）、CLDR は複数形の区分を定め、単一の形しか持たない言語にも other を使う（S099）、Mozilla は文を分割しないことと変数の位置を訳者が動かせることを求める（S096・S097）。W3C は、短い原文ほど訳文が長くなりやすいと書く（S102）
- 副作用と反動: 体系ごとに規則が食い違う（we・プレースホルダー・トーストの操作・ユーモア。`component-wording.md`）。MessageFormat 2.0 は UTS #35 で stable 表示だが、ICU の文書は draft 表記のままで、資料間の位置づけが揃わない（S231。R）
- 今の判断への示唆: 業界標準として 1 つの体系の規則を持ち込まず、採用した体系と理由を製品の指針に記録する（本 skill の整理）。文言を書く段階で連結を避け、変数と複数形を前提にした形で渡す

### 8. 国内: やさしい日本語・敬語・企業の文言指針

- 当時の制約: 災害時に、多くの外国人が日本語の災害情報を得られず、情報の面でも被害を受けた（S180。区分 B）。電子メールなどで敬語を割愛する傾向が批判された（S136）
- 応答: 弘前大学の研究室は、1 文を 24 拍程度、長くても 30 拍を超えないとする規則を作った（S149。B）。国立国語研究所は、分かりにくい外来語を、分かりやすくする工夫の検討に着手した（S091。委員会の設置は平成 14 年 8 月）。敬語の指針は、敬語をたくさん使えば丁寧になるわけではない（S131）、画一的な定型は顧客を不快にしうる（S135）と述べた。在留支援のガイドラインは、3 つのステップでやさしい日本語を作成するとし（S143）、ふりがなのない文書も用意し（S147）、日本語教師や外国人に確かめるよう求める（S148）。企業は、デザインシステムの一部として文言の指針を公開した。SmartHR は、業務アプリケーションに向くとして、ボタンのサ変の「する」を省く（S225。要旨）。エラーは、何が・なぜ・どうすればを入れる（S228。要旨）
- 副作用と反動: 東日本大震災では、情報量が増え、1 文をどうしても長くせざるを得なかった（S150。B）。短文の規則は、伝える量が増えると守れない。企業の指針は、公用文・JTF と違う決め方をすることがある（語末 -y の長音は S234、和欧間の空白は S125 と S123）。どれも告示の許容の範囲だが、同じ利用者が複数の製品で別の表記を見る（本 skill の整理）
- 今の判断への示唆: 字数・拍数の上限は、伝える量とセットで決める。表記は、規範（告示・建議）・業界の基準（JTF・企業）・利用者の実態（世論調査）の 3 つを並べて選ぶ。SmartHR の規則は、理由ごと移植する（S225 が理由を述べる）

### 9. 騙しの文言・規制・生成 AI（2019 年〜）

- 当時の制約: 整理（推測）: 断る選択肢を貶める、紛らわしい文言が、多くの EC サイトで見つかる。生成 AI が、文言の下書きと、利用者と会話する UI の両方に入ってきた
- 応答: 約 1.1 万の EC サイトの約 5.3 万のページから、1,818 件のダークパターンを見つけ、15 種類・7 分類と報告した（S199）。confirmshaming は、罪悪感や恥の感情を引き起こして意思決定に影響を与える（S200。C）。trick wording は、利用者の期待と曖昧な言語を利用して誤解させる（S201。C）。FTC のスタッフ報告は、恥を使って、選択肢を悪い判断として描き、選ばせないようにすることと整理した（S202）。インドの指針は、恐れ・恥・嘲り・罪悪感を生む表現で購入や継続へ誘導する行為と定義した（S203。B）。NN/g は、利用者が生成 AI を擬人化し、性能が高いと想定する、という機能的な役割を報告した（S195）。SmartHR は、AI の機能に、人や機械の役割を連想させる名前を付けない（S230。要旨）
- 副作用と反動: 言語モデルと共同で書くと、書き手どうしの文章が似て、語彙と内容の多様性が下がった（S196）。モデルで文章を整えると、内容は保たれるが、文体のばらつきが 21〜50% 減った（S197）。西洋中心のモデルの提案は、インドの参加者の文章を西洋の文体へ寄せた（S198）。いずれも UI の文言を対象にした研究ではない
- 今の判断への示唆: 騙しの文言は、倫理の問題であるだけでなく、規制の対象として名指しされている地域がある（時点情報。法的判断はしない）。AI で下書きを作る場合、ボイスとトーンの表と用語集で人が確かめる工程を残し、均質化を前提に点検する（本 skill の整理）
