# 部品ごとの文言の型

ボタン・見出し・ラベル・プレースホルダー・エラー・空の状態・確認ダイアログ・トースト・通知・ヘルプ・オンボーディング・メールの文言を書くときの型を、出典つきで並べたファイル。`../SKILL.md` の「部品ごとの型」から開く。文言を 1 つ書く前に、その部品の型と、出典どうしの食い違いを確かめるときに開く。

出典は各社・各機関の指針で、自社製品や自国の行政サービスの規則である。普遍的な正解ではなく、日本語の画面にそのまま移せるとも、どの出典も述べていない。英語の指針の議論（please・sorry・大文字の使い方など）を日本語へ移す部分は、すべて本 skill の整理（推測）である。食い違う出典は両論と、選ぶ条件を書く。区分 R・B・C と「引用ではない参照」（SmartHR Design System・Atlassian・Polaris など）は要旨で、逐語の引用ではなく、数値を「出典あり」として扱わない。

## 読み方

- 型: 出典が一致している点。まず守る
- 食い違い: 出典どうしで割れている点。片方を標準にせず、製品の中で決めて記録する
- 日本語での扱い: 本 skill の整理（出典なし）。他社の規則は理由ごと移す（S225 は「業務アプリケーションに合う」と理由を述べたうえで規則にしている）

## ボタン

| 項目 | 内容 | 出典 |
|---|---|---|
| 動詞を入れる | ボタンは動作を名指す。Mailchimp は動詞を入れて簡潔にするよう述べ、GOV.UK は行う動作を書くよう述べる | S030・S037 |
| 汎用語を避ける | 「OK」は情報を伝えるだけの通知か、ほかに適切なラベルが無いときだけ | S051・S089 |
| 短く言い切る | 熱量のある言い回しより、動作の語のほうが伝わる場合がある。Apple は「Send」の例を挙げる | S047 |
| 題と主ボタンをそろえる | 確認ダイアログの題と主ボタンは、起きる動作を同じ語で言う | S073・S223（要旨） |
| リンクの文言 | 行き先を想像できない「こちら」だけのリンクを避け、具体的に書く | S226（要旨） |

食い違い:

| 論点 | 一方 | 他方 |
|---|---|---|
| 大文字の使い方（英語版を持つ製品） | sentence case（S030・S037）。Fluent 2 は読みやすく訳しやすいためと述べる（S021） | Apple はボタンを title-style とする（S078） |
| サ変動詞の「する」 | 業務アプリケーションでは「追加」「削除」のように省く。SmartHR が理由つきで定める（S225。要旨） | 一般向けの画面で省くかは、出典が述べていない |

日本語での扱い（本 skill の整理）:

- ボタンの語は、画面の題・確認の題・操作の記録の語とそろえる。「保存」と「登録」のように、同じ動作に別の語を使わない（用語集で決める）
- 取り消しにも動作を書く。「キャンセル」だけでは何を取り消すか分からない場面は、「入力をやめる」「予約を取り消す」のように、結果が分かる動詞にする
- 字数の上限は、出典では確認できなかった。表示幅と、翻訳する場合の伸び（S102）で決める

## 見出し・題

- エラーや確認の題に「エラー」だけを書かない。何が起きたかが題だけで分かるようにする（S050）。Atlassian は題を短く保つ（冠詞を除いて 3〜4 語を目安）（S221。要旨。指針上の目安）
- 空の状態の見出しは短く（GitLab は 5 語以内を目安とし、調査の根拠は示さない）（S070）。可能なら肯定の文にする（S076）。Polaris は、機能名の列挙でなく行動を促す形を勧める（S220。要旨）
- 見出しとボタンと確認の題で、同じものを同じ語で呼ぶ。語は用語集で決める（本 skill の整理）。部品ごとに文体を決める考え方は SmartHR が持つ（S227。要旨。監査ログの操作名は名詞で終え、説明文はです・ます調）

## ラベルとプレースホルダー

| 項目 | 内容 | 出典 |
|---|---|---|
| ラベルは常に見せる | プレースホルダーをラベルの代わりにしない | S038・S072・S052 |
| ヒント・例にも使うか | GOV.UK はヒントや例にも使わない。理由として、入力すると消えること、すべての読み上げが読むわけではないことを挙げる | S038 |
| 緩い立場 | Carbon は、ラベルの代わりや必須情報でなければ使ってよい。Apple はヒントに使う前提で、別ラベルは有用なこともあると述べる | S072・S052 |
| 説明の押し込み | デジタル庁は、サポートテキストの代わりにプレースホルダーを使ってはならないとする | S079 |
| 感覚だけで指さない | 色や位置だけで指す文言（「赤い項目」「右のボタン」）を単独で使わない | S023 |

選ぶ条件（本 skill の整理）: 条件・形式・必須の説明は、入力前から常に見える場所（ラベルの下のサポートテキスト）に置く。例示は、消えても困らない補助に限る。支援技術での読み上げは、本 skill では確かめられない（判定は、導入されていれば designer-accessibility）。

## エラー

型（出典が一致している点）:

| 要素 | 内容 | 出典 |
|---|---|---|
| 何が起きたか・どう直すか | 平易な言葉で、問題を特定し、解決を提案する。2 つの問いに答える | S081・S061 |
| 原因を含める | 何が・なぜ・どうすれば、の 3 要素。表示の優先順も決めている（SmartHR の要旨） | S228 |
| 直し方を必ず書く | 具体的なエラー内容と訂正方法を記述する。エラーに利用者の取るべき行動は必須（S074） | S080・S074 |
| 責めない | 利用者を責めない。過失の有無にかかわらず責めない。主語を利用者にせず、事実を言う（「Wrong password」の例） | S012・S064・S040 |
| 責める語 | NN/g は invalid・illegal・incorrect を例に挙げ、冗談も避けるよう述べる | S082 |
| 機械側の語 | 「Failed to」は「unable to」に。GOV.UK は valid・invalid が情報を足さないと述べる | S057・S033 |
| 入力を消さない | エラーを出しても、入力済みの欄を消さない | S032 |
| 質問と同じ語 | エラーは、質問のラベルの語をそのまま使う | S034 |
| エラーコードは末尾 | 問い合わせ用のコードは、文の末尾に置く | S065 |
| 隠した「エラー:」 | 読み上げ向けに、隠した「Error:」を文の前に置く部品がある | S036 |
| 正直に | 原因が本当に不明なら、不正確な推測より「不明なエラー」と書く | S085 |
| 黙って失敗しない | 失敗を報告しないことは許されない | S062 |

エラーの出し方も文言のうちである。早すぎる表示・強すぎる装飾・作業を止める表示は、無作法に感じられ、認知負荷を上げる（S083）。エラーの前に、起きない設計を先に問う（S063・S086・S084）。

食い違い（日本語の画面では、出典のどれも日本語の場面を述べていない。すべて、選ぶ条件は本 skill の整理）:

| 論点 | 一方 | 他方 | 選ぶ条件 |
|---|---|---|---|
| 謝る（sorry） | GOV.UK は、入力検証で謝る必要は無く、深刻な障害のときだけ謝る（S042・S041） | Atlassian は謝罪を避ける。深刻に見せるため（S221。要旨）。Google は、謝罪の受け取り方は文化で違うと述べる（S095） | 入力の誤りは謝らず、こちらの障害は謝る。詫びる場面かを製品の指針に書く |
| 「お願いします」の類（please） | GOV.UK・Google は、手順に please を付けるのは丁寧すぎると述べる（S007・S015） | GitLab は、利用者に不便をかけたときだけ許す（S020） | 英語の議論をそのまま「ください」に移せる根拠は無い。依頼の度合いは jp-style.md の敬語の節で決める |
| 資格・権限 | GOV.UK は、資格が無い・権限が無いことをエラーの文で伝えない（S035） | 他の指針は、この線引きを書いていない | 権限が無いときは、理由と頼む先を、エラーとは別に書く（examples の例を参照） |
| 通知バナーとの関係 | 入力エラーは、通知バナーでなく、エラー要約とエラーの文で出す（S039） | 取得した範囲に反対の指針は無い | 入力エラーの文を、画面の上の通知にしない |

日本語での扱い（本 skill の整理）:

- 「〜が不正です」「〜は無効です」「〜に失敗しました」だけで終えない。何が合っていないかと、直し方を、条件と例を添えて具体的に書く。文末（です・ます／言い切り）と依頼の言い方は、製品で決めてそろえる（片方を標準にしない。`jp-style.md`）
- 数字・日付・利用者自身のデータを入れて具体的にする（Polaris の要旨が同じ方向を述べる。S219）
- エラーコードと技術用語は、末尾の補足に置く。利用者が問い合わせで言える形にする
- 「エラーが発生しました」は、原因が分かるなら特定する。分からないなら「原因を特定できませんでした」と正直に書き、次の行動（時間を置く・問い合わせる）を添える

## 空の状態

| 型 | 内容 | 出典 |
|---|---|---|
| 次の一手 | 空の画面に、明確な次の手順を置く | S048 |
| 肯定の文 | 可能なら、否定でなく肯定の文で書く | S076 |
| 主要な操作は 1 つ | 罪悪感を持たせない（要旨） | S220 |
| 遊び | Atlassian は、空の状態の題に軽い遊びを入れてよいとする（要旨）。GOV.UK は目立たない文言を目指す | S222・S005 |
| 空の理由を分ける | 初めて使う・絞り込みで 0 件・権限が無い・読み込みに失敗した、を同じ文にしない | 本 skill の整理（出典なし） |

## 確認ダイアログ

| 論点 | 一方 | 他方 | 選ぶ条件（本 skill の整理） |
|---|---|---|---|
| 確認を出すか | 取り消せる操作には出さない（Apple）。作業を放棄する操作は確認しない（Win32）。不要な確認は読まれずに閉じられる（Win32） | 重大度が高い削除では、対象の名前の入力を求める（GitLab）。低い場合は摩擦なしもよい | 取り消せるか・巻き込む範囲で分ける。取り消せるなら、確認でなく取り消しを置く |
| 文言 | 題と主ボタンが、起きる動作を言う（S073）。モーダルの主ボタンは題を反映する（S223。要旨） | 「はい／いいえ」の選択は、何をするのかを読まないと分からない | 結果を動詞で言う（「請求を取り消す」「入力を続ける」）。巻き込む件数や範囲を本文に書く |

出典: 取り消せる操作の確認は S049、確認の読まれ方は S058、放棄の確認は S059、名前の入力は S067。

## トーストと通知

- トースト: GitLab は操作をトーストに置かない（S068）。Material の実装文書は、取り消しや再試行の操作を挙げる（S077。M3 本体の指針は未取得）。自動で消える通知が時間制限に当たるかは、導入されていれば designer-accessibility で確かめる（本 skill は判定しない）
- 通知: 同じ件で通知を繰り返さない（S053）。第三者に見える場所に、私的な情報を入れない（S054）。出しすぎは通知全体の価値を下げる（S071）。Win32 の指針は、自 OS の通知の固定の表示時間を 9 秒と述べる（S060）。OS 固有の値で、Web に転用しない（本 skill の整理）
- 成功の文: Atlassian は、成功の題に定型の成功を表す語を付けず、感嘆符を避ける（S222。要旨）。熱量を上げる文言が、断る側の選択肢を貶める文言（S200）へ転用されうる、というのは本 skill の整理

## ヘルプ・ツールチップ・オンボーディング

- ツールチップは補助の情報にとどめ、必須の情報を入れない（S075）。自動で消さない（S069）
- 説明が要ると思ったら、設計の欠陥を疑う（S004）。文言で補う前に、画面を直せないかを問う
- チュートリアルや製品ツアーは、10 ステップ未満に（S066。指針上の目安。調査の根拠は示されていない）

## メール

- 1 通に伝える大事なことは 1 つ（S043）。購読の案内は、利用者が明示的に求めたときだけ（S045）。リンクは自分のドメインに限る（S046）
- GOV.UK は、メールの宛名を「Dear 氏名」の形にし、「Hi」を使わない（S044）。日本語の宛名・結びの型は出典が無い。製品の中で 1 つに決める（jp-style.md の文末と敬語の節）
- 「メールの半数超がモバイルで読まれる」（S031）は、根拠の調査が示されていない主張で、数値の出典としては使わない

## AI の機能に添える文言

- 機能に、人や役割を連想させる名前（アシスタントなど）を付けない。「AI」と、目的から付けた名前を組み合わせる（S230。SmartHR の要旨）
- 利用者が AI を擬人化すると、性能への期待につながる（S195）。人格を演じる文言は、できないことまで約束していないかを点検する
- 確信が無いときは、分かっていることと分からないことを分けて書く（S085 の「不明なエラー」の考え方の応用。本 skill の整理）
